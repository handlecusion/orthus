## 0. Executive Summary

**질문:** 국내 LLM 여러 개를 태스크별로 골라 쓰는 오케스트레이션(Fugu 방식)이, 국내 LLM 하나를 orthus 전체에 꽂는 것(현행 단일 슬롯)보다 실워크로드에서 나은가?

**구조 — 단일 파이프라인 2단 (대회 중심):**

| 단 | 기간 | 내용 | 산출물 |
|---|---|---|---|
| **1단 (필수)** | 7/8–7/12 (+버퍼 7/15까지) | 워커 3종(+VARCO 프로브) 프로파일 → 최선 단일 모델 선정 → **데모 노드 `ORTHUS_LLM` env 스왑** | 국내 모델로 도는 실동작 데모 + 태스크×모델 매트릭스. **7/15 = 1단 완료 체크포인트** |
| **2단 (대회 차별화)** | ~7/13–7/31 | A100로 규칙 선택기 이득 측정 + Phase 2 학습 오케스트레이터 | 대회 novelty: "실워크로드에서 오케스트레이션 vs 단일 +X%p" |

**핵심 결정(owner, 2026-07-08):** ① **회사 prod(Mac mini 운영계)는 배포하지 않는다** — 국내 모델은 WSL 데모 노드에만. 회사 prod의 국내 전환은 대회 후 별도 결정(그때 상용 키 + 본 실험 데이터 재사용) ② 대회 키·A100은 실험+데모 전용(출품 용도로 약관 정합) ③ 수용 기준 사전 고정, 전 후보 미달 시 미달 사실을 보고서에 명기하고 대회는 진행 ④ 임베딩은 국내화 안 함(현행 유지).

**비용:** 현금 ≈ 0원(워커=대회 API 크레딧 적용, 학습=대회 A100). 예외는 judge(Bedrock Claude) 토큰비 추산 1~2만원 + 예비 5만원. **크리티컬 패스는 돈이 아니라 일정 2개** — 7/15(1단 마감), 7/31(A100 창 종료, 2단 학습 마감).

**조기 중단 조건(사전 승인):** D0 스모크에서 워커 3종 전부 `json_only` 부적합이면 당일 저녁 일정 재협상.

## 1. 배경과 문제 정의

### 1.1 Sakana Fugu 논문 요지

Fugu는 이질적 프런티어 모델 풀(Claude-Opus-4.8 / GPT-5.5 / Gemini-3.1-Pro)을 워커로 두고, **오케스트레이터 모델이 서브태스크마다 최적 워커를 선택/조합**한다. 오케스트레이터를 2단계(단일 스텝 SFT → end-to-end 진화전략/RL)로 학습시켜 단일 최강 모델을 상회했다. 핵심 주장 3단:

1. 모델마다 강점 도메인이 다르다 (전제)
2. 태스크→모델 매칭을 잘하면 단일 모델을 이긴다 (라우팅 이득)
3. 그 매칭은 학습으로 더 좋아진다 (학습 이득)

본 실험은 이를 **국내 모델 풀 + orthus 실워크로드**에서 검증한다. 전제(1)는 1단에서, 라우팅 이득(2)과 학습 이득(3)은 2단에서.

### 1.2 orthus의 현재 구조: 단일 슬롯

orthus의 모든 LLM 호출은 팩토리 하나로 수렴한다.

- `orthus/models/registry.py:46` `get_chat_model()` — env `ORTHUS_LLM`(mock|solar) 분기로 어댑터 1개 반환. 배포 하나 = 채팅 모델 하나.
- 소비 태스크 14곳: `orthus/wiki/distill.py:286`(distill), `orthus/wiki/qa.py:111`(/ask 지식응답), `orthus/structured/query.py:293`(NL→SQL), `orthus/router/route.py:129,241`(라우팅 분류), `orthus/router/decompose.py:230,252,287,560`, `orthus/router/event_orchestration.py:316`, `orthus/router/graph.py:342`, `orthus/wiki/gap.py:478`, `orthus/wiki/backfill_claim_headline.py:74`, `orthus/agentwork/delegation.py:119`, `orthus/agentwork/service.py:2759,2824`, `orthus/mail/compose.py:103`, `orthus/connectors/base.py:169`, `orthus/router/decompose_measure.py:131,314`.
- 임베딩은 별도 슬롯 `registry.py:17` `get_embedding_model()`(6개 콜사이트, **1024차원 하드 제약** — pgvector `Vector(1024)`).

즉 orthus에는 Fugu가 전제하는 **워커 풀**(모델 N개 동시 보유)과 **선택기**(서브태스크→모델 매칭)가 없다. 본 실험은 이 두 컴포넌트를 `experiments/fugu-ko/`에 신설해 검증하고, 프로덕션 코드는 건드리지 않는다.

### 1.3 왜 지금 하는가

- 대회 제출물의 기반이 "국내 모델로 실동작하는 orthus"이고, 차별화 서사가 오케스트레이션 이득 측정이다.
- orthus는 태스크별 골든셋 재료(위키/corpus/질의 로그)와 결정론 검증 게이트(NL→SQL sqlglot, `tests/unit/test_validate.py`)를 이미 보유 — 평가 하네스 구축 비용이 낮다.
- 대회 제공 자원(국내 4사 API 키 + A100×4)이 7월 한정으로 살아 있다.

## 2. 가설 (단별 매핑)

| ID | 가설 | 검증 위치 | 판정 기준 |
|---|---|---|---|
| **H1** | 국내 모델들은 orthus 태스크별로 강점이 갈린다 | **1단** (Phase 0 프로파일) | 태스크×모델 매트릭스에서 태스크별 1위가 2개 모델 이상으로 분산 |
| **H2** | 태스크→모델 매핑(규칙 선택기)이 최강 단일 모델 대비 이득 | **2단** | 종합 품질 +3%p↑ 또는 동품질(±1%p) 비용 −30%↓ |
| **H3** | 학습된 선택기가 규칙 선택기 대비 추가 이득 | **2단** (Phase 2 SFT) | Phase 1 최고 구성 대비 +2%p↑ |

**중요 — H2를 1단에서 판정하지 않는 이유:** 1단 태스크는 실질 T2/T3/T5 셋이고 T5는 회귀(만점 기대)라 변별력이 없다. 태스크 2개짜리 정적 매핑 vs 최강 단일의 차이는 구조적으로 작아, 1단에서 H2를 말하면 과장이 된다. 1단의 정직한 산출물은 **프로파일(H1) + 단일 모델 선정**이며, 오케스트레이션 이득(H2/H3)은 2단에서 태스크·문항을 확장해 측정한다.

**가설 기각도 제출물이다:** 본 실험의 1차 목적이 대회 제출이므로, H1/H2/H3가 기각되어도 "국내 모델 풀에서 오케스트레이션 이득이 없었다"는 측정 결과 자체가 정직한 novelty로 보고된다. 따라서 2단은 H2 인정 여부와 무관하게 진행한다(구 G3 조건부 게이트 폐지).

### 3.2 임베딩 — 국내화 안 함 (owner 확정)

임베딩(`get_embedding_model()`, 6개 콜사이트)은 실험 전 구간 **현행 프로덕션 설정 그대로 고정.** ① 검색 품질을 상수로 둬야 관측 차이가 생성 LLM 교체 효과만 반영(변인 통제) ② 국내 임베딩(KURE-v1 등) 검토는 현재 계획에 없음.

### 3.3 Phase 2 오케스트레이터 (2단)

- 학습 대상: **워커 풀과 무관한 별도 경량 오픈웨이트**(HF 공개 EXAONE 7.8B 또는 Qwen 소형) — 워커가 전부 API라 선택기용 모델은 따로 내려받는다. 라우팅은 짧은 분류 출력이라 소형 + QLoRA로 충분(A100 40GB 1장 여유).
- 학습 데이터: 1단·2단 실행 로그 → (질문, 태스크 피처) → (최적 모델 라벨: 점수 argmax, 동점 시 저가) 변환. 부족 시 합성 증강.
- 진화전략/RL은 스트레치 — SFT로 H3 판정 가능하면 생략. **7/31(A100 창) 내 학습 완료 필수.**

### 4.2 LLM-judge (T2) — Bedrock Claude 확정

- **Judge = 현행 프로덕션 Bedrock Claude** (기배선 어댑터, 셋업 0일). 구안(A100 셀프호스팅 Qwen)은 vLLM 셋업+신뢰도 검증에 2~3일이 들어 7일 예산에서 기각(§8-D2).
- **Self-preference 방어 3중** (기준선이 Claude 자신이므로): ① 익명 쌍대비교 + 위치 셔플(모델 정체 비노출) ② 사람 스팟체크 15건을 **"기준선이 이긴 문항"에 집중 배치** ③ 사람-judge 뒤집힘이 15건 중 5건 이상이면 해당 태스크는 사람 라벨 우선.
- **판정 지표는 절대점수가 아니라 쌍대비교 승률** — 절대평가(1–5 루브릭)는 추세 참고용. 기준선 점수 부풀림 위에 임계를 세우지 않기 위함.
- 비용: T2 40문항 × 4모델 쌍대비교 ≈ 수백 콜, 추산 **1~2만원** (예비 5만원 내, §11).

### 4.3 메트릭 (4축)

1. **품질**: T3 게이트 통과율+실행 일치 / T2 쌍대 승률 / T5 분류 정확도. 1단 종합은 가중치 없이 **태스크별 개별 보고**(제외된 T1/T4를 포함한 구 가중치 폐기). 2단 종합 가중치는 2단 착수 시 확정.
2. **비용**: 태스크당 토큰 실측 (2단에서는 오케스트레이터 자신의 호출 비용 포함 — Fugu류 비교에서 흔히 누락되는 항목).
3. **지연**: p50/p95 (MA.8 전례 — p50 7.5s로 기능 보류 — 를 참고 임계로).
4. **안정성**: `json_only` 스키마 준수율(`orthus/models/base.py:23` 계약), 게이트 reject율, 재시도율.

### 4.4 실행/판정 규율 (간소화)

- **paired 실행**: 같은 문항을 전 모델(3종+기준선)에 — 비교 타당성의 최소선, 유지.
- **수용 기준 사전 고정 (1단 모델 선정용):** `T3 게이트 통과율 기준선 −5%p 이내 AND T5 회귀 무손실 AND T2 쌍대 승률(vs 기준선) ≥ 40% AND p95 현행 2배 이내`. 회사 prod이 빠졌으므로 이 기준은 스왑 가부가 아니라 **(a) 데모 노드에 올릴 모델 선정 (b) 대회 보고서의 "현행 프런티어 대비 국내 모델 수준" 정직 기록**에 쓴다. 전 후보 미달이어도 대회는 최선 후보로 진행하되 미달 사실 명기.
- 폐기: 3회 반복(1회 실행+실행 메타 기록으로 대체), bootstrap CI 게이트(분석 참고로 강등), build/test 분할(1단), 다중비교 보정. 판정은 "명백히 이김/명백히 짐/비슷함" 3단계.

### 6.2 orthus 코드 재사용 (수정 0, import만)

orthus의 주요 LLM 소비 함수는 이미 `chat_model` 주입 파라미터를 갖는다(`chat = chat_model or get_chat_model()` — `distill.py:286`, `qa.py:111`, `structured/query.py:293` 확인). 따라서:

- `orthus.models.adapters.openai_compat.OpenAIChat`을 모델 수만큼 인스턴스화해 풀 구성. **registry.py 무수정.**
- 태스크 러너는 orthus 함수를 `chat_model=pool[selected]`로 직접 호출. 프로덕션 경로/플래그 무변경.
- NL→SQL 게이트(sqlglot 5종)가 곧 T3 채점기.
- 실행 DB = WSL 데모 노드(회사 스냅샷). **회사 prod DB/wiki-store 무접촉.**
- **예외 명시:** D4의 데모 노드 env 스왑 이후에는 데모 노드가 실제로 wiki-store에 쓴다(실험 하네스의 read-only 원칙과 별개) — 방어는 스왑 직전 스냅샷 + distill 눈검사(§5.1 D4).
