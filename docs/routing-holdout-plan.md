# 라우팅 홀드아웃 — 설계 (design-only)

> 상태: **설계 검토용**. 구현/측정 미착수.
> 계기: E2 A.X-2차 재측정(2026-07-14)에서 사전 등록 게이트 **A3 실패** — 배정 활성화가
> baseline이 맞히던 3문항을 새로 침묵 누락시켰다. 3건 전부 **라우팅 오류**였다.
> 선행: `docs/model-orchestration.md` §11(홀드아웃 재검증), `analysis/e2-final-remeasure-plan.md`

## 0. 이 측정이 답해야 할 질문

1. **Q1 — 라우팅은 이미 측정되지 않았나? (§11 T5, p=1.00)**
   측정됐다. **다른 모집단에서.** §1.2가 이 설계의 존재 이유다.
2. **Q2 — 라우팅 오류는 모델 탓인가, 설계 탓인가?**
3. **Q3 — 오라우팅의 비용은 비대칭인가?**
   실측상 `wiki→structured`는 **답이 완전히 소실**됐고(3/3), `structured→wiki`는 오히려
   **답을 되찾았다**(V2-16). 한 숫자로 합치면 이 비대칭이 지워진다.
4. **Q4 — 라우팅 오류를 *회수*할 수 있는가?** 회수되면 라우팅 정확도 자체가 덜 중요해진다.
5. **Q5 — 회수의 대가는?** "0행 → 위키 재질의"는 **정답인 '0건입니다'를 환각으로 바꿔치기**할
   위험이 있다. 이걸 재지 않고 켜면 zero-answer 안전장치를 되돌리는 셈이다.

## 1. 무엇이 실제로 깨졌나

### 1.1 측정된 사실 (E2 A.X-2차 원자료)

| 사실 | 값 | 출처 |
|---|---|---|
| 리프 중 **규칙 사각지대**(`_rule_based_route()==None` → LLM이 결정) | **47%** (36/76) | raw jsonl |
| 신규 침묵 누락 | 3건 (V2-24 · V2-26 · V2-30) | e2_final_eval |
| 그 3건의 정체 | 전부 **wiki→structured 오라우팅** | leaf mode 대조 |
| 그 3건의 DB 결과 | 대부분 **`status=executed, row_count=0`** / 일부 `rejected:unknown_column` | `query_runs` |
| 캐스케이드(A.X 2차) 발동 | 27회 호출 · 4회 채택 · **오류 0** | `audit_log` |
| 캐스케이드가 이 3건을 살렸는가 | **아니오** | 위 두 줄의 교집합 |

**캐스케이드는 평면을 못 고친다.** SVC는 실패 신호를 보면 **같은 structured 평면에서** 2차
모델로 SQL을 다시 쓴다. 답이 `notion_rows`에 없으면 A.X가 다시 써도 여전히 0행이다.
교정 범위가 **SQL 품질**이지 **평면 선택**이 아니다. 이 3건은 구조적으로 캐스케이드 밖이다.

**0행은 두 가지를 뜻한다.**
- (a) *평면이 틀렸다*: 답이 위키에 있는데 DB를 봤다 → 회수해야 한다.
- (b) *진짜 없다*: "완료 티켓 몇 개?" → 0건이 **정답**이다 → 회수하면 안 된다.

`row_count=0` 하나로는 (a)와 (b)를 **구분할 수 없다.** 이것이 이 설계의 중심 난제다.

### 1.2 ★ 왜 §11 T5(p=1.00)로 끝내면 안 되는가 — **모집단이 틀렸다**

§11 홀드아웃은 라우팅을 **제대로** 쟀다. 규칙이 가로채는 문항을 자동 제외했고(사각지대만),
결과는 gpt-4o-mini 92.9% · Solar 92.9% · A.X 96.4% · EXAONE 96.4%, **p=1.00**.

그런데 **문장이 프로덕션이 라우팅하는 것과 다르다.**

```
T5 홀드아웃 (측정된 것)   "우리 팀에서 가장 많이 밀린 업무가 몇 건이나 쌓여 있어?"
                          ← 사람이 쓴 완결된 사용자 질문

프로덕션이 라우팅하는 것   "조명 일관성에서 @image_1과 @video_1의 어떤 요소를
                           정확히 일치시켜야 하는가?"
                          ← decompose가 쪼개 만든 리프
```

`/ask`는 순수 검색이 됐고, 복합 질문은 오케스트레이터가 **decompose로 쪼갠 뒤 리프마다
라우팅**한다. E2 v2x에서 38문항 중 **30문항이 분해**됐다. 즉 프로덕션 라우팅 입력의
**절대다수가 리프**인데, T5는 그걸 한 문항도 재지 않았다.

**그리고 오류율이 실제로 갈린다:**

| 모집단 | Solar 라우팅 오류 |
|---|---|
| T5 홀드아웃 (사람이 쓴 질문, n=28) | **7.1%** |
| E2 루프의 규칙-사각지대 리프 (n=25) | **≥12%** (확인된 3건 / 앵커 있는 문항만 검증 가능 → 실제론 더 높을 수 있음) |

> **결론: "라우팅은 모델 간 차이 없음(p=1.00)"은 프로덕션 분포에서 검증된 적이 없다.**
> 이 설계의 1차 목적은 **올바른 모집단에서 다시 재는 것**이다.

## 2. 모집단 — 규칙 사각지대 **× 리프 분포**

두 조건을 **동시에** 만족해야 한다.

### 2.1 조건 A — 규칙 사각지대만

`classify()`는 2단이다.

```
_rule_based_route(q)  →  걸리면 그대로 반환 (LLM 미호출)
                      →  None이면 get_chat_model_for(TASK_ROUTING) 이 결정
```

규칙이 처리하는 질문으로 모델을 재면 **신호가 0으로 희석된다** — 거기선 전 모델이 글자까지
동일하다. 실측 사각지대 비율 47%이므로 규칙-포함 셋은 **모델 간 차이를 자동으로 절반 이하로
축소**한다. (§11 T5 홀드아웃은 이 조건을 이미 지켰다 — 28/28 사각지대.)

### 2.2 조건 B — **decompose가 만든 리프** 분포

§1.2가 이유다. 문항을 사람이/LLM이 "사용자 질문"으로 쓰면 T5의 실수를 반복한다.

**생성 절차 (프로덕션 경로를 그대로 태운다):**

```
회사 콘텐츠 → 복합 질문 생성 → 프로덕션 decompose(Solar) 실행 → 나온 리프가 모집단
                                    ↑ 라우팅 비교 시 리프는 고정. 라우팅 모델만 바꾼다.
```

리프를 **한 번 만들어 고정**하는 것이 핵심이다. 안 그러면 decompose 모델 차이가 라우팅
측정에 새어 들어온다(교란). 리프 생성은 프로덕션 decompose 모델(Solar) 1회로 고정한다.

**단일 질문도 자연 비율로 포함**한다 — E2 v2x 기준 분해 30 : 단일 8 ≈ **8:2**.

## 3. 정답 라벨 — 의견이 아니라 **구성 + 양방향 검증**

"올바른 평면"을 사람이 판정하면 그 판정이 곧 편향이다. **답이 어디 사는지를 알고 시작**한다.

### 3.1 생성 (label by construction)

| 버킷 | 생성 재료 | 라벨 |
|---|---|---|
| **S-answerable** | `notion_rows`(company) 행 — 협업업무표 794 · 로드맵 279 · 직원 · 파트너사 등 | `structured` |
| **W-answerable** | company `wiki_pages` 12,050 — 슬랙 전사·문서 등 DB 행이 아닌 지식 | `wiki` |
| **TN (true-negative)** | 스키마상 유효하나 **실제 0행**인 조건 ("X 상태인 티켓 몇 건") | `structured` + **정답=없음** |

### 3.2 양방향 검증 (negative verification)

라벨을 **믿지 않고 확인**한다. 각 문항을 **두 평면 모두**에 태운다.

```
S-answerable :  structured가 앵커를 낸다  AND  wiki가 못 낸다   → 채택
W-answerable :  wiki가 앵커를 낸다        AND  structured가 0행 → 채택
둘 다 답한다   →  라우팅이 틀릴 수 없는 문항  →  **제외**
둘 다 못 답한다 →  답이 없는 문항            →  **제외**
```

**"둘 다 답한다"의 제외가 결정적이다.** 회사 위키는 **같은 노션 행에서 컴파일**됐다. 따라서
DB 행 기반 질문의 상당수를 위키도 답한다. 그런 문항을 남기면 어느 쪽을 골라도 맞으니
**라우팅 정확도가 실제보다 좋게 나온다.** 라우팅이 진짜로 갈리는 건 (a) 집계·카운트(위키가
못 셈) (b) 전사·슬랙처럼 DB 행이 아닌 지식 — 두 부류뿐이다.

→ **탈락률이 높을 것이므로 넉넉히 생성한다(목표의 3배).**

### 3.3 오염 방지

- `e2.json` / `e2_v2x.json` / `t5*.json`과 **문자열 및 근사 중복 금지**. 그 셋들은 태워졌다.
- 복합 질문 생성을 **한 모델에 맡기지 않는다.** 생성기 어투가 그 모델 라우팅에 유리할 수 있다.
  **3모델이 균등 생성**하고 문항별 생성기를 기록해, "자기 생성 문항에서만 잘하는가"를 교차 검정.

## 4. 측정 대상 — 모델만이 아니라 **세 후보**

| 후보 | 내용 | 비용 | 선행 확률 |
|---|---|---|---|
| **C1 모델 스왑** | `routing` 배정을 Solar → A.X / EXAONE | 0 (설정) | **미지** — T5는 틀린 분포에서 p=1.00. **리프 분포에서 처음 잰다** |
| **C2 규칙 확장** | 결정론 신호 추가(슬랙 user id·전사·인용 등장 → wiki) | 코드 소량, **LLM 0콜** | 중간 — 좁지만 확실 |
| **C3 교차평면 회수** | structured가 **0행/게이트거부**면 그 리프를 wiki로 재질의 | 코드 + 지연 | **높음** — 오류 비용 자체를 제거 |

> ⚠️ **C1에 A.X를 채택하더라도 운영 제약이 남는다** — A.X는 **초당 3회 팀 상한**이고 라우팅은
> `/ask`마다 도는 **핫패스**다(§11의 A.X 라우팅 기각 사유). 정확도가 이겨도 이 제약을 별도
> 판단해야 한다. EXAONE에는 이 제약이 없다.

**C3가 근본이다.** C1·C2는 라우팅을 더 잘 맞히려는 시도이고, C3는 **틀려도 회수되게** 만든다.
라우팅은 결국 "데이터가 어디 사는지에 대한 추측"인데, 시스템은 **그냥 열어볼 수 있다.**

### C3 안전 변형 (측정 대상)

| 변형 | 발화 조건 | 위험 |
|---|---|---|
| **C3-a** | 게이트 **거부**일 때만 위키 재질의 | 낮음 (SQL이 틀렸다는 명백한 증거) — 회수 범위 좁음 |
| **C3-b** | 0행 **AND** 위키 검색이 강한 근거를 낼 때만 | 중간 — "강한 근거" 임계 필요 |
| **C3-c** | 0행이면 무조건 위키 재질의 | **높음** — TN 환각. 아마 기각 |

C3-b의 임계는 **이 홀드아웃에서 정한다**: TN 버킷의 위키 근거 점수 분포와 W-answerable의
분포가 **분리되는가**. 분리 안 되면 C3-b는 성립하지 않고 C3-a만 남는다.
**분리 여부 자체가 측정 결과다** — 미리 임계를 정하지 않는다.

## 5. 지표 — 비대칭을 지우지 않는다

| 지표 | 정의 | 왜 |
|---|---|---|
| **M1 치명 오류율** | `wiki→structured` 오라우팅 비율 | **답이 완전히 소실**된다. 실측 3/3이 이 방향 |
| **M2 경미 오류율** | `structured→wiki` 오라우팅 비율 | 위키가 부분 답을 내기도 한다(V2-16은 오히려 개선) |
| **M3 회수율** | C3에서 오라우팅된 리프가 최종 답을 되찾은 비율 | C3의 존재 이유 |
| **M4 TN 환각율** | 정답이 "없음"인데 그럴듯한 답을 지어낸 비율 | **C3의 대가.** 0이어야 한다 |
| **M5 지연 증분** | C3 발화 시 추가 지연 (p50/p95) | 0행이 structured 리프의 **~26%**라 무시 못 함 |

**M1과 M2의 합산 보고 금지.** 합치면 이번 A3 실패의 성격이 그대로 지워진다.

## 6. 사전 등록 게이트 (측정 **전에** 고정)

기본값 = **현상 유지**(라우팅 = Solar, 회수 없음). 게이트를 통과한 후보만 바꾼다.

| 게이트 | 조건 |
|---|---|
| **R1** | **C1 채택**: M1이 Solar 대비 개선 **AND McNemar p < 0.05**. 유의하지 않으면 **Solar 유지**(단순성 우선). A.X 채택 시 **핫패스 RPS 3 제약을 별도 판단**. |
| **R2** | **무회귀**: 어떤 후보도 M1을 baseline(gpt-4o-mini) 대비 악화시키지 않는다. |
| **R3** | **C2 채택**: 규칙-발화 대조군 **회귀 0건** AND 사각지대 M1 개선. |
| **R4** | **C3 채택**: **M4 TN 환각율 = 0** AND M3 회수율 > 50% AND M5 p95 증분이 예산 내. **M4가 0이 아니면 즉시 기각** — zero-answer 안전장치를 되돌리는 변경은 받지 않는다(owner 확정, 완화 없음). |

**게이트를 통과한 후보가 없으면 아무것도 바꾸지 않는다.** 그건 실패가 아니라 결과다.

## 7. 무효 조건 (하나라도 걸리면 측정 폐기)

- **I1** 주 모집단 전 문항이 `_rule_based_route(q) is None` — 로드 시 assert.
- **I2** 주 모집단이 **리프 분포**를 따른다(§2.2) — 분해:단일 ≈ 8:2, 리프는 프로덕션 decompose 산출.
- **I3** 배정이 실제로 물렸다 — `prod_spy.preflight()` 통과(콜 전수 `FallbackChat`).
- **I4** 라벨 양방향 검증 통과(§3.2). 미통과 문항은 셋에 없다.
- **I5** 기존 골든셋(`e2*`, `t5*`)과 중복/근사중복 0건.
- **I6** **전 경로 `scope="company"`.** company DB에 `e2_kb_gen`이 만든 personal-scope 위키
  페이지 **24,673개**가 있다. `scope="all"`로 조회하면 합성 페이지가 위키 평면에 섞여
  라벨링이 통째로 무효가 된다. (기존 하네스는 이미 `scope="company"` 고정 — 유지할 것.)
- **I7** 측정 중 공유 Postgres에 **다른 부하 없음**(pytest 동시 실행 금지 — TS-A 재발 방지).

## 8. 표본 크기

McNemar(불일치 쌍 기준). 사각지대 모델 불일치율 **19%**(E2 실측) 가정.

| 탐지하려는 효과 | 필요 불일치 쌍 | 필요 문항 수 |
|---|---|---|
| 큰 효과 (불일치 중 80%가 한쪽) | ~20 | **~105** |
| 현실적 효과 (불일치 중 70%가 한쪽) | ~47 | **~250** |

**주 셋 = 사각지대 리프 250** (S/W 균형) **+ TN 40** **+ 규칙-발화 대조군 40**.

대조군 40의 역할: **모델을 바꿔도 결과가 안 변하는 것**을 확인한다. 변하면 하네스가 틀린
것이다(측정하려던 것을 측정하고 있지 않다는 신호 — I3의 이중 방어).

측정 자체는 싸다 — 라우팅은 문항당 **LLM 1콜**. 330 × 3모델 ≈ 1,000콜(A.X 상한 포함 수십 분).
**비싼 쪽은 라벨링**(문항당 두 평면 실행 + 3배 과생성)이며, 한 번 만들면 재사용한다.

## 13. ★ 측정 결과 (2026-07-15) — **LLM 라우터가 상수보다 못하다**

주 셋 **290문항**(규칙 사각지대 × 리프 분포) · 대조군 40 · TN 40.
무효 조건 전부 통과: I1 290/290 사각지대 · **대조군 전건 모델 무관**(하네스 무결성) · I6 company scope.

### 13.1 지표 (M1/M2 비합산)

| 구성 | 정확도 | **M1 치명** (wiki→str) | M2 경미 (str→wiki) |
|---|---|---|---|
| solar (현행 배정) | 60.3% | **113/222 = 51%** | 2/68 = 3% |
| A.X | 63.1% | 102/222 = 46% | 5/68 = 7% |
| EXAONE | 60.7% | 112/222 = 50% | 2/68 = 3% |
| gpt-4o-mini (현행 prod) | 61.7% | 106/222 = 48% | 5/68 = 7% |
| **C2 규칙확장 + wiki 기본값 (LLM 0콜)** | **90.7%** | **16/222 = 7%** | 11/68 = 16% |

**전 LLM이 위키 질문의 절반을 DB로 보낸다.** 그리고:

```
"무조건 wiki"라고만 답하는 상수   76.6%
LLM 중 최고 (A.X)               63.1%   ← 상수보다 13%p 낮다
```

### 13.2 게이트 판정

| 게이트 | 후보 | 결과 |
|---|---|---|
| **R1** | C1 모델 스왑 (A.X / EXAONE / gpt) | ❌ **기각** — 어떤 쌍대 차이도 유의하지 않다(McNemar p=.312/1.000/.618). §1.2의 재측정 결론: **모집단을 고쳐도 모델 간 차이는 없다.** 단 절대 성능이 전부 낙제다. |
| **R3** | C2 규칙확장 + wiki 기본값 | ✅ **채택** — 개선 98 · 악화 10 · **p=0.000**. 대조군 회귀 0. **LLM 0콜·지연 0.** |
| **R4** | C3-c (0행이면 wiki 재질의) | ❌ **기각** — TN 환각 **1/9**. "이름이 홍길동인 파트너는 얼마나 있나요?"(정답 0명)에 위키가 **"1명입니다"**라고 답했다. 완화 없음(§12-3). |
| **R4** | C3-a (**게이트 거부일 때만**) | ✅ **채택(좁게)** — 12/290 발화 · 회수 10/12(83%) · TN 발화 0건. 게이트 거부는 SQL이 깨졌다는 뜻이라 **"0건입니다"라는 정답을 애초에 만들 수 없다**(구조적 안전). |

> ⚠️ **C3-a의 M4=0/0은 공허한 통과다** — TN이 한 번도 그 경로를 태우지 않았다. 근거는 실측이
> 아니라 **구조**(거부된 쿼리는 참인 0건 답을 낳을 수 없다)다. 그렇게 읽어야 한다.
>
> 💡 TN 31/40이 C3를 발화시키지 않은 이유도 구조적이다 — 집계 SQL은 `COUNT(*)`로 **"0"이 담긴
> 행 1개**를 낸다(`row_count=1`). 진짜 "0건입니다"는 애초에 C3 트리거에 닿지 않는다.

### 13.3 독립 검증 (E2의 진짜 리프 — 이 셋 밖)

- **A3 실패 3건(V2-24·V2-26·V2-30) 전부 C2가 고친다.**
- C2가 바꾸는 E2 사각지대 리프 7건이 **전부 structured→wiki 방향**. **새 M1을 만들지 않는다.**
- 생성기 편향 없음 — 어떤 모델도 자기 생성 문항에서 유독 잘하지 않는다(A.X 생성분에서 오히려
  gpt-4o-mini가 최고). C2는 전 생성기 부분집합에서 88~94%.

### 13.4 **C2는 공짜가 아니다**

M2 = 11/68(16%) — **사각지대의 진짜 구조화 질문 일부를 잃는다.** 실제 사례: E2의 V2-21
("시설관리 문의는 누구와…") 은 structured가 직원 명단을 정확히 냈고 A3에서 되찾은 6건 중
하나였는데, C2는 이걸 위키로 보낸다.

**거래의 실체: 구조화 11건을 잃고 위키 97건을 되찾는다(M1 113→16).** 순이득 +30%p.

### 13.5 왜 이런 일이 벌어지는가 (구조적 설명)

**진짜 구조화 질문(집계·필터·목록)은 결정론 규칙이 먼저 다 잡아채서 LLM에 도달조차 하지
않는다.** 그래서 규칙 사각지대에 남는 것은 **대부분 위키가 답할 것들**이다(실측 라벨
222:68 = 77:23). LLM은 그 사전분포를 모른 채 매번 새로 추측하고, 절반을 틀린다.

라우팅은 "데이터가 어디 사는지에 대한 추측"인데, **사각지대에서는 그 추측의 정답이 거의 항상
'위키'다.** 추측할 필요가 없다.

### 13.5b E2 루프 재측정 — **A3가 닫혔다** (2026-07-15, C2+C3-a 반영 후)

C2(#719)와 C3-a를 프로덕션 코드에 넣고 E2 A.X-2차 루프를 **같은 golden/config**로 다시 쟀다.

| 기준 | A.X만 (§13.2 이전) | **C2+C3-a** |
|---|---|---|
| A1 zero-answer | 0% vs 11% ✅ | **0% vs 13%** ✅ |
| A2 페어드 순손실 없음 | ✅ (p=0.344) | ✅ (p=0.508) |
| **A3 신규 침묵 누락 0** | ❌ **3건** | ✅ **0건** |
| 총 침묵 누락 | 6 vs baseline 9 | **1 vs baseline 5** |

**사전 등록 게이트 3/3 통과.** 이전에 A3를 깨뜨린 3건(V2-24·26·30)이 전부 wiki로 재라우팅돼
살아났고, 신규 누락은 0이다. C3-a는 측정 중 실제로 발동했다(게이트거부 4건 — `column
properties 없음` 3 + `parse_failed` 1 — 을 wiki로 회수, audit 확인).

**단 여전히 "전반적 개선"은 유의하지 않다**(McNemar p=0.508). C2+C3-a가 한 일은 "더 좋게"가
아니라 **A3라는 회귀를 제거한 것**이다 — 이제 배정을 켜도 답이 조용히 사라지지 않는다.
배정 활성화(운영, node.env)의 마지막 차단 근거가 사라졌다.

### 13.6 권고

1. **C2 채택** — `routing` 작업에서 **LLM을 제거**한다. 수량 신호(`얼마나 되/있/많`, `총 몇`,
   `몇 건/명/번` 등)를 결정론 규칙에 추가하고, 나머지 사각지대는 **wiki 기본값**.
   부수효과: `/ask` 핫패스에서 LLM 1콜이 사라진다(지연·비용 감소).
2. **C3-a 채택(좁게)** — structured가 **게이트 거부**면 그 리프를 wiki로 재질의.
   0행 트리거는 **넣지 않는다**(R4 기각).
3. **C1 기각** — 라우팅 모델 스왑은 무의미하다. `routing` 배정은 어차피 사라진다(1번).
4. **다음 단계** — C2를 넣고 **E2 루프를 재측정**한다. A3(신규 침묵 누락)가 닫히면 배정 계층
   활성화 판정을 다시 할 수 있다. C2 없이 배정만 켜는 것은 여전히 권고하지 않는다.
