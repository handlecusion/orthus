## 0. 문제 정의 — 그리고 이 계획이 측정부터 시작하는 이유

### 0.1 현황

decompose(복합질문 분해)는 모델 오케스트레이션 전환에서 **현행(gpt-4o-mini)이 국내 3모델을 전부 이기는
유일한 작업**이다 (`docs/model-orchestration.md:657`, §11.3):

| 작업 | n | gpt-4o-mini (현행) | Solar (배정) | A.X | EXAONE | p (McNemar) |
|---|---|---|---|---|---|---|
| decompose | 16 | **93.8%** (놓침 0) | 81.2% (놓침 2) | 56.2% | 68.8% | **p=.22** |

배정은 성능이 아니라 벤더 금지·지연·안전 근거로 Solar를 유지했고, §11.3b는 이 칸을 "명시적으로 손해를
감수하는 칸"으로 기록했다. 손해의 일부는 E3 프리필터 확장(recall 100%, 모델 무관)이 상쇄하지만,
**모델 자체의 판단력 격차는 남아 있다**.

### 0.2 이 격차는 아직 '측정된 사실'이 아니다

n=16에서 93.8% vs 81.2%는 **15/16 vs 13/16, 즉 2문제 차이**고 McNemar p=.22다. 랩의 반복 교훈
(R1 in-sample 착시, R2 채점 앵커, R3 오탐 0 착시 — 실험 지도 아티팩트 §01)을 그대로 적용하면:

- 지금의 "격차"는 우연과 구분되지 않는다. 파인튜닝으로 이걸 "닫았다"고 주장해도 같은 16문항에서는
  **증명이 불가능하다** (2문제가 뒤집히면 p는 더 나빠질 뿐).
- 따라서 이 실험의 1단계는 학습이 아니라 **홀드아웃 확장(n≥150) + 베이스라인 재측정**이다.
  "지표가 표본보다 먼저다" (`experiments/fugu-ko/embedding/LAB-NOTES.md`).

### 0.3 그럼에도 파인튜닝을 하는 이유

1. **방향성**: 벤더 금지로 국내 모델 전환은 확정이고, decompose는 배정표에서 유일하게 "지고 들어가는"
   칸이다. API 모델(Solar)은 우리가 개선할 수 없지만 오픈웨이트는 개선할 수 있다.
2. **대회 산출물**: fugu-ko 대회(A100×4, 7/31)의 자연스러운 다음 실험이다. 임베딩 파인튜닝
   (A.X-Encoder, PR #792)에 이은 생성 모델 파인튜닝 트랙.
3. **작업 성격**: decompose는 좁고 구조화된 작업(yes/no 게이트 + JSON 분할)이라, 규모와 무관하게
   파인튜닝(LoRA든 벤더 관리형이든)으로 프론티어 API를 따라잡기 가장 좋은 후보 작업 유형이다.

## 2. 목표와 성공 기준 (사전 등록 — DF0에서 수치 확정 후 동결)

**주 지표 (primary)**: 확장 홀드아웃 H2(n≥150, §5)에서 문항 단위 정답률.
문항 정답 = 게이트 판정 일치(compound 여부) **AND** (compound인 경우) 분할 수 `expected_parts` 일치.
현행 §11.3 채점과 동일 정의 — DF0에서 채점 코드로 고정한다.

| 게이트 | 기준 | 판정 |
|---|---|---|
| **G1 비열등** | FT 모델 ≥ gpt-4o-mini − 5%p (H2, 같은 문항) | 통과 시 "현행 수준" 주장 가능 |
| **G2 우월(대 Solar)** | FT 모델 > Solar API, McNemar p<0.05 (H2) | 통과 시 "파인튜닝이 격차를 닫았다" 주장 가능 |
| **G3 함정 안전** | H2 함정(비복합) 오분해율 ≤ 5% (E3 §5와 동일 임계) | 실패 시 배포 불가 — 오분해는 조용한 오답 |
| **G4 형식 안정** | JSON 파싱 실패율 ~0 (guided decoding 허용, §6.3) | 실패 시 서빙 레버로 보완 후 재측정 |
| **G5 지연** | 게이트 1콜 p50 ≤ 700ms (A100 vLLM 기준; Solar 698ms 동급) | 프로덕션 hot path 예산 |

G1+G3+G4 통과 = **실험 성공** (대회 보고 + 프로덕션 후보). G2까지 통과하면 완승.
G1 실패 시 §9의 폴백 사다리로 종료 — 억지로 홀드아웃에 맞추지 않는다(R1 교훈).

**비열등 마진 5%p 근거**: n=160에서 5%p는 ~8문항. 대략적 검정력: 불일치쌍 15% 가정 시 n≈160으로
10%p 차이를 α=0.05·power 0.8로 검출 가능. 정확한 검정력 계산은 DF0 prereg에서 확정하고 동결한다.

## 3. 범위

**In scope**
- 게이트(`_DECOMPOSE_SYSTEM`)와 분할(`_SPLIT_SYSTEM_TMPL`, deps 변형 포함) 두 표면의 파인튜닝.
- 확장 홀드아웃 H2 구축 + 전 베이스라인 재측정 (gpt-4o-mini · Solar · EXAONE · A.X API + 4개 벤더
  파인튜닝 후보 zero-shot — K-EXAONE·VARCO·Solar Pro·A.X-K1, §4 결정 1).
- 벤더 파인튜닝 경로 확인(DF(-1)) → 확인된 경로로 SFT(자체호스팅 LoRA 또는 벤더 관리형, 방식은 §5 DF3에서 분기) 실행,
  vLLM/벤더 엔드포인트 인메모리 채점, E2E 스모크.

**Out of scope**
- `_SYNTHESIZE_SYSTEM`(조각 합성) — 별도 골든셋이 없고("rides the decompose loop") 채점 앵커가 다르다. 후속.
- 프로덕션 배선(`ASSIGNMENTS` 변경, 서빙 인프라, 플래그) — **owner 게이트** 별도 단계. 본 실험은
  임베딩 선례와 동일하게 "배선하지 말고 인메모리 채점으로 품질만 먼저 본다".
- 프리필터/규칙 변경 — E3는 완결됐고 공유 토큰셋은 불변 제약.
- 프롬프트 개선 실험 — 변인 통제를 위해 프롬프트는 프로덕션 고정. (단 DF1의 few-shot 베이스라인 arm은
  예외로 1회 측정한다 — §9 폴백 사다리의 최저가 대안이 실제로 충분한지 확인용.)

## 4. 핵심 결정 3건 — 대안 비교

### 결정 1: 파인튜닝 대상 모델 — 대회 확정 4종 폐쇄 풀 (2026-07-18 정정)

초안은 A.X-4.0-Light(SKT)+Kanana-1.5(Kakao)를 후보로 뒀으나 **틀렸다** — 이번 대회에서 파인튜닝이
가능한 모델은 **아래 4종으로 완전히 닫혀 있다**(owner 확인 2026-07-18). Kanana는 이 풀에 없어 후보에서
전량 제외하고, A.X는 "A.X-4.0-Light"가 아니라 대회가 제공하는 특정 모델 **A.X-K1**로 교체한다.

| 벤더/모델 | fugu-ko 기존 실험에서의 위치 | 파인튜닝 방식 | 라이선스/제약 |
|---|---|---|---|
| **LG K-EXAONE** (`K-EXAONE-236B-A23B`, 현재 FriendliAI Dedicated로 추론 서빙 중) | decompose 배정표 `TASK_DELEGATION_EXTRACT`(오탐 최소, `orthus/models/orchestration.py:114`) 담당. | **SKT A.X-K1** | decompose zero-shot 최저(56.2%) — 파인튜닝으로 역전시키는 게 이번 실험의 핵심 베팅 | **TBD** | 라이선스 미확인. 추론 API가 팀당 **RPS 3** 제한이었던 이력(`fugu-ko-experiment.md`) — 파인튜닝 API/쿼터도 낮을 가능성 |

**핵심 미확정 사항**: 4개 벤더 각각이 (a) 오픈웨이트 체크포인트를 내주는지(A100 자체호스팅
LoRA/SFT — 기존 A100 인프라 재사용 가능), (b) 벤더 자체 콘솔/API로 관리형 파인튜닝을 제공하는지
(데이터 업로드 → 벤더가 학습 → 전용 엔드포인트 발급), (c) 그 중간(가중치는 비공개지만 대회 한정
파인튜닝 API를 여는지) 중 무엇인지 **모델별로 다를 수 있고 전부 미확인이다.** 이 확인은 §5의 새 선행
단계 **DF(-1)**에서 하며, 그 결과가 나오기 전엔 주력 모델을 확정하지 않는다.

**확인 결과에 따른 분기**:

- 오픈웨이트 체크포인트를 내주는 벤더 → 기존 A100 LoRA 인프라(`experiments/fugu-ko/train/tier{2,3}.py`,
  D6–D9의 `sft_worker.py`/`build_sft_data.py` 패턴) 그대로 재사용. 가장 통제 가능하고 예산 예측이 쉽다.
- 관리형 파인튜닝만 제공하는 벤더 → DF2에 "학습 데이터를 그 플랫폼의 업로드 스키마로 변환" 어댑터
  단계 추가. 콜 수/쿼터/과금을 그 시점에 확인(A.X는 특히 쿼터 낮을 가능성 — 위 표 참고).
- 4개 전부 확인되면 **4-way 병행 진행**(사전 우선순위 없이 zero-shot dev 스크리닝 → 상위 성과 벤더에
  학습 예산 집중), 일부만 확인되면 확인된 벤더만 진행하고 미확인 벤더는 DF6 보고에 "확인 불가로
  미실행"으로 명시한다(no-silent-caps 원칙).
- **236B-A23B(K-EXAONE) 같은 초대형 MoE가 오픈웨이트 자체호스팅으로 확인되면 단일 A100(40–80GB)로는
  어차피 불가능** — 그 경우 K-EXAONE은 자동으로 "관리형 API만 가능한 벤더" 취급으로 넘어간다(§8 리스크).

### 결정 2: 학습 데이터 전략

| 전략 | 라벨 품질 | 비용/리스크 | 판단 |
|---|---|---|---|
| **(a) 결정론 조합 생성** ✅ 주력 | **구성상 완벽** — 원자 질문 2–3개를 접속 표현으로 합성하면 `compound/parts/sub_questions`가 정의상 참 | 템플릿 표면 과적합 위험 → 함정 혼합 + Solar 패러프레이즈로 완화 | 채택 |
| (b) gpt-4o-mini 교사 증류 | 교사 수준 상한 | OpenAI 약관(출력으로 경쟁 모델 학습 금지) + 벤더 금지 정신 위배 소지 | **기각** — owner 결정 불필요하게 만드는 리스크. (a)로 충분 |
| (c) 실로그(`query_runs`) 라벨링 | 실분포 반영 | 라벨러가 필요(사람 or LLM) · PII redaction 경유 필수 | 보조 채택 — 자연 분포 게이트 음성(단일 질문) 소스로만, 라벨은 사람 검수 |

핵심 통찰: **decompose는 정답을 생성으로 만들 수 있는 드문 작업이다.** 원자 질문 A, B를 "A랑 B 각각
알려줘"로 합치면 게이트 라벨(yes)과 분할 라벨([A, B])이 구성상 알려진다. 교사 모델이 필요 없다.

### 결정 3: "현행 수준" 인정 기준

| 기준 | 문제 |
|---|---|
| 기존 16문항에서 승리 | 2문제 차이 — 통계적으로 무의미, R1 재발 |
| **확장 H2에서 비열등(G1) + 함정 안전(G3)** ✅ | 사전 등록 임계 + 동결 홀드아웃 — 채택 |
| E2E 답변 품질 승률 | 채점 앵커 민감(R2) — 보조 지표로만 (DF5 스모크) |

## 5. 단계 계획 (DF(-1)–DF6)

각 단계 말미의 **게이트**를 통과해야 다음으로 간다. 실패 시 그 자리에서 중단하고 기록한다.

### DF(-1) — 벤더 파인튜닝 경로 확인 (0.5–1일, 전체 선행 조건)

- 4개 벤더(K-EXAONE/VARCO/Solar Pro/A.X-K1) 각각에 대해 확인: ① 오픈웨이트 체크포인트 배포 여부
  (라이선스 포함), ② 벤더 관리형 파인튜닝 콘솔/API 존재 여부(엔드포인트, 데이터 포맷, 쿼터, 과금),
  ③ VARCO는 추가로 텍스트 챗 컴플리션 엔드포인트 자체(`api.varco.ai/ko/reference`).
- 확인 경로: 각 벤더 문서(Upstage `console.upstage.ai/docs`, adot.ai 포털, VARCO
  `api.varco.ai/ko/docs`, FriendliAI dedicated 콘솔) + 필요 시 대회 운영진(MZC) 문의.
  `<로컬 키 저장소>/handoff.html`은 **추론 키만 확인됨** — 파인튜닝 자체는 이 단계에서 신규 확인.
- 산출물: `experiments/fugu-ko/analysis/df-1-vendor-finetune-audit.md` — 벤더별 (a)/(b)/(c) 판정 +
  근거 링크/캡처 + 확인 불가 항목 명시.
- **게이트**: 최소 1개 벤더의 경로가 확인돼야 DF2 이후 진행 가능. 4개 전부 미확인이면 실험은 §9
  폴백 사다리로 즉시 종료(파인튜닝 자체가 불가능하므로 "격차는 손해로 남긴다"가 유일한 정직한 결론).

### DF0 — prereg + 채점기 동결 (0.5일)

- §11.3 decompose 채점 정의를 코드로 고정: `experiments/fugu-ko/df_score.py` (프로덕션
  `should_decompose`/`split_question` 실경로 호출, e3_prefilter.py 패턴). tier 3 고정.
- 성공 기준(§2 G1–G5) 수치·검정력 계산 확정 → `experiments/fugu-ko/analysis/df0-prereg.md`.
- 기존 16문항으로 채점기 스모크: §11.3의 93.8/81.2가 재현되는지 확인 (main 코드 — 52커밋 stale 재발 방지).
- **게이트**: 기존 수치 재현 ± 1문항. 실패 시 §11.3 측정과의 diff부터 규명.

### DF1 — 홀드아웃 H2 구축 + 전 베이스라인 (1.5일)

- **H2 구성 (n≥150, 목표 160)**: ① 복합 60 (2분할 40 · 3분할 15 · 의존형 5 — 회사 위키/notion_rows
  실주제 기반 수작업+생성 혼합), ② 함정 60 (§7 함정 분류 5족 × 12), ③ 자연 분포 40 (실로그 샘플,
  PII redaction 경유, 사람 라벨). **구축 완료 즉시 해시 동결** — 이후 학습·튜닝 어느 단계도 H2를 보지 않는다.
- 라벨 검증: 구성상 라벨 + 국내 LLM 2종 교차 판정(E4 검증된 판정자) + 불일치분 사람 확정.
- 베이스라인 측정: gpt-4o-mini · Solar · EXAONE · A.X (기존 프로덕션 API 4종, `orthus/models/registry.py`
  경유) + few-shot Solar arm(§3 예외) + DF(-1)에서 확인된 4개 벤더(K-EXAONE/VARCO/Solar Pro/A.X-K1)
  zero-shot. **VARCO는 기존 프로덕션 베이스라인에 없으므로 이 단계가 첫 측정**(챗 엔드포인트가
  DF(-1)에서 확인된 경우에 한함).
- **게이트**: H2에서 gpt-4o-mini vs Solar 격차가 유의(p<0.05)로 확인되는가?
  - **유의하지 않으면** — "격차는 측정 착시였다"가 실험의 결론이다. 파인튜닝 없이 종료하고
    §11.3b의 "손해 감수" 문구를 갱신한다. **이것도 성공적 종료다** (R1 선례).
  - 유의하면 계속.

### DF2 — 학습 데이터 파이프라인 (1.5일)

- `experiments/fugu-ko/decompose_ft/gen_data.py`:
  - 원자 질문 뱅크 ~800개: 위키 페이지/notion_rows 주제에서 생성(`embedding/gen_questions.py` 패턴,
    시드 고정 — T2 함정 회피) + 기존 골든 단일 질문.
  - 조합 생성기: 접속 표현 배열(각각/와/랑/그리고/비교/~하고 ~도/열거) × 원자 2–3개 → 복합 예제.
    형태소 자연스러움은 Solar 패러프레이즈 1패스(라벨 불변 검증 포함).
  - 함정 생성기: §7 5족 템플릿 + Solar 패러프레이즈.
  - 자연 음성: 실로그 단일 질문 (redaction 경유).
- 목표 규모: SFT ~4–6k 예제 (게이트:분할 ≈ 2:1, 게이트 내 양:음 ≈ 1:1.5 — 함정 과표집).
- **누수 방어**: H2·t7·t7_holdout 전 문항과 (i) 정규화 exact match (ii) 임베딩 유사도 상위 검사
  (Solar 임베딩, 임계 사전 고정) 이중 필터. 원자 질문 주제 family 격리(gen_train_data.py의
  family map 패턴) — H2 복합 문항이 참조한 주제 family는 학습에서 제외.
- **일반화 설계**: 함정 5족 중 2족(§7에서 지정)은 **학습에서 완전 제외** → H2에서 미학습 함정족
  성능으로 표면 휴리스틱 과적합 여부를 판정한다.
- **게이트**: 누수 검사 0건 + 생성 라벨 표본 100개 사람 검수 오류 ≤ 2%.

### DF3 — SFT 실행, 경로별 분기 (1–1.5일, DF(-1) 결과에 따라 갈림)

공통: 멀티태스크 혼합 학습(게이트 예제 `{"decompose":...}` + 분할 예제 `{"sub_questions":...}`,
deps 변형 `_SPLIT_DEPS_SYSTEM_TMPL` 소량 포함), **프로덕션 프롬프트 원문**을 system으로 고정,
dev = t7.json(22) + 생성 dev 300(H2 아님) 기준 체크포인트 선택, **H2 접근 금지**, seed 3개 고정.

#### 경로 A — 오픈웨이트 자체호스팅으로 확인된 벤더 (예상: EXAONE 계열이 유력, DF(-1) 확정 시까지 가정)

- 레시피: TRL SFTTrainer + peft LoRA (r=32, α=64, lr 1e-4→cosine, 2–3 epoch, bf16).
- GPU: 공유 A100 박스, `CUDA_VISIBLE_DEVICES` 배정 확인 후 사용(GPU0=EXAONE SFT 선점 이력, 임베딩
  핸드오프 §3 관례). 체크포인트 크기가 D6–D9 규모(1.2B–32B)면 run당 15분–3.5시간 예상(D6–D9 실측
  준용); **`K-EXAONE-236B-A23B` 자체가 오픈웨이트로 확인되면 단일 A100 불가 — 이 경우 경로 B로 전환**.

#### 경로 B — 벤더 관리형 파인튜닝만 제공되는 벤더

- 레시피: 벤더 콘솔/API 스펙에 맞춰 학습 데이터(§DF2 산출물)를 그 플랫폼 업로드 포맷으로 변환하는
  변환기를 `decompose_ft/vendor_adapters/<vendor>.py`로 작성 → 업로드 → 학습 잡 제출 → 완료 대기 →
  전용 엔드포인트 수령. 하이퍼파라미터는 벤더가 노출하는 범위 내에서만 조정.
- 리스크: 학습 소요 시간·큐 대기·쿼터가 A100 자체호스팅보다 예측 어려움 — DF(-1)에서 확인한 값을
  §10 일정에 반영해 재조정한다.

- **게이트(공통)**: dev에서 base(zero-shot) 대비 +10%p 이상. 미달 시 데이터 진단(오류 분석) 후 1회
  재시도, 그래도 미달이면 사전 지정 순서(DF(-1)에서 확인된 벤더 우선순위, 다음으로 데이터 규모 2배
  arm)로 진행.

### DF4 — H2 최종 측정 (0.5일) — **1회만**

- vLLM 서빙(guided_json 켠 arm/끈 arm 각 1회 — G4 분해용) → `df_score.py`로 H2 전 문항.
- FT 모델 + DF1의 전 베이스라인과 같은 문항 대응표로 McNemar.

- **게이트**: §2 G1–G5 판정. 여기서 실험의 주 결론이 난다.

### DF5 — E2E 스모크 + 지연 (0.5일)

- company 스냅샷 노드에서 orchestrate 실경로에 vLLM 엔드포인트를 `OpenAIChat(base_url=...)`로 주입

- 채점은 **인용 위키 페이지 앵커** 기준 (R2 교훈 — 키워드 일치 금지).
- 지연: 게이트 1콜 p50/p95 (G5), 분할 포함 전체 p50.
- **게이트**: E2E 회귀 0 + G5 통과.

### DF6 — 보고 + 후속 결정 자료 (0.5일)

- `experiments/fugu-ko/analysis/df-results.md`: 전 수치, 오류 분석(특히 미학습 함정족), 대회 보고 소재.

## 6. 세부 설계 노트

### 6.1 왜 게이트와 분할을 한 모델에 멀티태스크로 넣나

프로덕션이 한 슬롯(`TASK_DECOMPOSE`)이다. 두 모델로 쪼개면 서빙 비용 2배 + 배선 변경이 필요해진다.
같은 프롬프트 형식을 유지하므로 혼합 학습이 자연스럽고, 작업 간 간섭은 dev에서 작업별 분리 리포트로 감시한다.

### 6.2 uncertain 라벨

프로덕션은 `uncertain`→False다. 학습 라벨은 yes/no만 쓴다(uncertain을 가르치면 회피 학습 위험).
스키마의 uncertain은 미학습 상태로 남겨 프로덕션 계약을 깨지 않는다.

### 6.3 guided decoding은 서빙 레버로 분리

JSON 유효성은 vLLM `guided_json`으로 구조적으로 보장 가능하다. 단 이는 모델 능력이 아니므로 G4는
guided on/off 두 arm으로 나눠 재고, 본 지표(G1–G3)는 guided-on 기준으로 판정한다(프로덕션에서도 켤 것이므로).

### 6.4 프리필터와의 상호작용

H2 측정은 홀드아웃 관례대로 tier 3 고정. 단 프로덕션 default는 tier 0이므로, DF6 보고에
tier 0/3 각각의 도달 문항 수를 병기해 "모델 개선이 실제로 발현되는 트래픽 비율"을 명시한다.

## 7. 함정 분류 (H2·학습 데이터 공용)

기존 홀드아웃 함정 7문항 + `e3_control.json`에서 귀납한 5족. **F4·F5는 학습 제외족**(§DF2 일반화 설계).

| 족 | 패턴 | 예 (홀드아웃 실문항) |

## 8. 리스크 / 함정 (랩 교훈 매핑)

| 리스크 | 근거 선례 | 방어 |
|---|---|---|
| in-sample 착시 — 생성 데이터 분포에서만 강한 모델 | R1 (+7.7%p 기각) | H2 동결 + 1회 측정 + 미학습 함정족 |
| 채점 앵커가 결론을 만든다 | R2 (58%↔83% 반전) | 주 지표는 게이트+분할 수(결정론), E2E는 인용 앵커 |
| 함정 오탐 — "각각 보이면 쪼갠다" 휴리스틱 학습 | R3 (오탐 0 착시), E3 대조군 | G3 임계 5% + 함정 과표집 + F4/F5 제외족 검증 |

## 9. 폴백 사다리 (G1 실패 시 — 사전 지정)

1. **few-shot Solar** (DF1에서 이미 측정됨): G1 통과면 파인튜닝 없이 이걸 채택 제안 — 최저가.
2. **SVC 캐스케이드**: Solar 게이트 + A.X 2차 검증 (E6 선례 — 다른 실수를 하는 모델 쌍).
3. **현상 유지**: Solar + E3 tier 3 (§11.3b의 현행 결론 유지). 실패 기록 자체가 대회 보고 소재다.

어느 폴백도 "홀드아웃에 맞춰 한 번 더"를 허용하지 않는다.
