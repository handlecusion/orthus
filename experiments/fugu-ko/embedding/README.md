**상태(2026-07-16): 실측 완료. §5는 측정 오류로 폐기 → §8.6이 정정본이다.
실제 질의 형태 재검증까지 끝나 남은 교란 없음(§8.6e).**

> ## 결론: **Solar가 품질·지연 둘 다 유의하게 낫다.** 교체는 **config 한 줄**이면 된다.
>
> | 축 | 결과 | 강도 |
> |---|---|---|
> | **품질** | **MRR +0.08(veconly) / +0.11(hybrid)** | **유의**(p<0.001, §8.6) |
> | **지연** | **p50 69ms vs 241ms — 분포 완전 분리** | **압도적**(z=7.7, p<0.0001, §6) |
> | 원가 | 5.5~18배 비싸나 **절대액 무의미**($0.29 / $4.14) | 결정 무관(§7) |
>
> **필요한 작업: `ORTHUS_EMBEDDING_*`를 `embedding-passage`로 바꾸고 전량 재임베딩. 끝.**
> 블렌드 재보정·비대칭 배선·4096 마이그레이션은 **전부 불필요**(§8.6).
>
> ### ✅ 평가셋 교란 — 해소됨(§8.6e)
>
> "평가셋이 실제보다 길고 문장형이라 대칭에 유리했을 수 있다"는 의문은 **실제 질의 형태
> (21자/의문형 49%)에 맞춘 셋으로 재측정해 기각**했다 — 4개 조건 전부 대칭 우세 방향이고
> 2개가 유의하다. 대칭 우세는 질문 형태가 아니라 `embedding-query`의 모델 특성이다.

  "Solar의 코사인이 낮음"이 아니라 "**query 모델**의 코사인이 낮음"이었다.

## 1. 국내 4종 임베딩 API 존재 여부 (라이브 실측)

`probe_embed.py` 결과:

| 모델 | 임베딩 API | 근거 |
|---|---|---|
| **Solar (Upstage)** | ✅ **있음** | `POST https://api.upstage.ai/v1/embeddings` → 200. 모델 `embedding-query` / `embedding-passage`(query·passage 비대칭 쌍, alias `solar-embedding-1-large-*`). native 4096-d |
| A.X (SKT) | ❌ 없음 | `awf-gw.adot.ai/v1/embeddings` → 404. 가이드에도 LLM+STT만 |
| EXAONE | ❌ 없음 | Friendli dedicated → 422 `"This model does not support the embedding endpoint"` |
| VARCO | ❌ 없음(문서 근거) | 공식 서비스 카탈로그에 임베딩/벡터 제품 자체가 없음. D0에서 chat 엔드포인트조차 없어 이미 드롭 |

> **결론: 우리 대회 키로 열리는 임베딩 API는 Solar 하나뿐.** 비교도 Solar vs 현행 OpenAI 1:1이다.

> ⚠️ **정정 (2026-07-17).** 위 표는 **API**만 조사한 것이고, 초판은 이를 *"국내에 임베딩
> 모델이 Solar뿐"*으로 서술했다 — **사실이 아니다.** 오픈웨이트로는 존재한다:
>
> | 모델 | 정체 | 검증 |
> |---|---|---|
> | `skt/A.X-Encoder-base` | ModernBERT 인코더 백본 0.1B · 16K ctx · **hidden 768**(실측) · MLM | **§15에서 파인튜닝 후 실측** — 최선 변형이 Solar의 90.0%(p=0.056) |
> | `EXAONE-BI/FinTexTS-Embedding` | 임베딩 모델 · linq-v2(Mistral) 기반 · 4096-d · **금융 특화·영어** | 미측정(도메인 불일치) |
>
> 즉 정확한 서술은 *"대회 키로 열리는 **API**는 Solar뿐이고, **오픈웨이트로는 존재하나
> 파인튜닝이 필요하다**"*이다. `docs/model-orchestration.md` §14.2도 같은 정정 대상.
> 실측 결과는 아래 §15.

## 2. 배선 난이도 — 낮음

- 기존 `OpenAIEmbedding`(`orthus/models/adapters/openai_compat.py`)이 OpenAI-호환 `/embeddings`를
  그대로 때리므로 **config만 바꿔 붙는다**(Solar는 OpenAI SDK 호환).
- **차원 제약 문제 없음.** 코드가 1024를 강제(`openai_compat.py:170`, pgvector `vector(1024)`)하는데
  Solar도 `dimensions` 파라미터로 원하는 길이를 낸다(1024/512 실측). 배치도 지원(50건 1콜 1.8s).
  - ⚠️ **단 matryoshka 절단이 아니다**(§8.4) — 4096-d의 앞 1024차원과 1024-d 벡터는 cos≈0.04로
    사실상 직교다. 배선엔 무영향이지만 "큰 차원이 정보 상위집합"이라는 추론은 무효다.
- ⚠️ `EMBEDDING_SLOTS`에 solar 슬롯은 없다(`registry.py`) — base_url/model만 갈아끼우면 `openai`
  슬롯으로 동작하지만, 정식 채택 시엔 슬롯 추가가 깔끔하다.
- **비대칭 임베딩 미배선 → 오히려 다행이다(§8.6).** Solar는 query용/passage용이 분리돼 있는데
  현재 `EmbeddingModel.embed(texts)` Protocol엔 mode 인자가 없어 색인/질의가 **같은 호출**을
  쓴다(`orthus/models/base.py:13`). **그 "같은 호출"이 바로 대칭이고, 대칭이 유의하게 낫다.**
  - **→ 배선하지 마라.** 비대칭은 4개 조건 전부에서 유의하게 나쁘다(p<0.001, §8.6a).
    `embedding-query`가 passage 공간에서 멀리 떨어져 임베딩하기 때문이다(1위 코사인 중앙값
    0.489 vs 대칭 0.624).
  - 결과적으로 **교체가 config 변경 한 줄로 끝난다** — `ORTHUS_EMBEDDING_MODEL=embedding-passage`.
  - (참고: `BedrockEmbedding`도 `input_type`이 생성자 고정이라 질의/문서를 구분하지 못한다 —
    **Solar 때문에 생긴 결함이 아니라 원래 있던 것**이고, 이번 결과대로면 그게 손해가 아닐 수도
    있다. Cohere 계열에서 별도 검증이 필요하다.)

## 3. 평가셋 설계 — 왜 이렇게 만들었나

### 3.1 기존 골든셋은 죽어 있다

`orthus/wiki/eval_retrieval.py`의 20케이스로 현행 OpenAI를 돌리면 **hit@5 = 0/20**이다.
Solar가 나빠서가 아니라 그 골든셋이 현재 DB와 불일치한다(예전 컴파일 상태 기준 수작업,
`개발자-온보딩` 같은 정답 슬러그가 지금 DB에 없음). **기준선이 0점이면 비교가 성립 안 하므로**
새로 만들었다.

### 3.2 정답을 역방향으로 만든다

현재 DB에 실재하는 company `page` 83개를 층화 표집하고(atlas 35 / nova 25 / company 15 /
orbit 8 → `sample_pages.json`), **각 페이지의 실제 내용을 LLM에게 보여주며 "이 문서를 찾으려는
사람이 물어볼 질문 1개를 써라"**고 시킨다. 질문을 그 페이지에서 만들었으니 **정답이 그 페이지임을
우리가 이미 안다** → 채점 가능.

### 3.3 제목을 그대로 쓰면 안 된다

orthus 검색은 vector(의미) + lexical(키워드 문자열) 하이브리드다. 질문에 제목이 그대로 있으면
**lexical arm이 문자열만 보고 맞혀서 임베딩 품질과 무관하게 둘 다 만점**이 된다. 그래서 프롬프트에
"제목 단어를 부분 문자열로도 쓰지 말고 다른 표현으로 바꿔라"를 넣었고, 생성 후 누출 건수를 센다.

### 3.4 생성기 3종 — 편향 교차검증

질문을 gpt로만 만들면 **GPT 표현이 GPT 임베딩에 유리할 수 있다**(생성기 편향). 그래서 **같은 83개
페이지**에 대해 3종이 각각 질문을 쓴다. 표본 페이지는 공유해야 "같은 문제를 다르게 물어본 것"이 된다.

| 생성기 | 경로 | 상태 |
|---|---|---|
| `gpt` | prod 슬롯(gpt-4o-mini) | ✅ 83개 생성됨 |
| `claude` | 로컬 `claude -p` CLI(OAuth) | ✅ 83개 생성됨 |
| `solar` | Upstage `solar-pro` chat | ⬜ **owner 실행 필요**(회사 데이터 외부 전송) |

같은 페이지를 어떻게 다르게 묻는지 (실측 예시):

| 페이지 | gpt-4o-mini | claude |
|---|---|---|
| `June Goals Status` | 6월에 설정한 목표의 진행 상황은 어떻게 되나요? | 6월에 세운 목표들이 지금 각각 어느 정도 진행됐는지 정리된 문서가 있나요? |
| `Update Management` | 출연자에게 제공되는 소프트웨어 업데이트 관리는 어떻게 이루어지나요? | 출연자를 대상으로 한 갱신 내역은 누가 담당해서 처리하나요? |

**해석 규칙:** 생성기가 바뀌어도 승패의 **부호가 일정하면 진짜 신호**다. 각 임베딩이 **자기 벤더가
쓴 질문에서만** 이기면 생성기 편향이다. 하네스가 이 교차표를 자동으로 찍는다.

### 3.5 남은 한계

- **"페이지 1개 = 정답 1개" 가정.** 관련된 다른 페이지가 상위에 와도 MISS로 센다 →
  **절대 수치는 비관적이다. 모델 간 상대 비교로만 읽어라.**
- **83문항은 통계적으로 넉넉하지 않다.** ±몇 %p는 노이즈다. 큰 차이만 신호로 읽어라.
- **company scope 전용.** personal scope는 미검증.

## 4. 런북 — 품질 실측 (owner 직접 실행)

### 4.0 왜 owner가 직접 돌려야 하나

Claude Code 샌드박스가 **회사 위키 원문을 외부 API(api.upstage.ai)로 보내는 것을 하드 블록**한다.
표본을 1만 → 83건으로 줄여도 동일하게 차단됐다 — 스케일이 아니라 *"기밀 데이터 → 미신뢰 목적지"*
조합 자체가 트리거이고, **에이전트 자율 실행으로는 승인 불가 카테고리**다. 데이터 소유자가 직접
실행하는 것은 별개 문제이며, 그 판단은 owner 몫이다.

> ⚠️ **아래를 실행한다 = 회사 위키 청크 원문을 Upstage로 전송하기로 결정한다.**
> 기본값 약 23만자(1,583청크). §4.2 dry-run이 정확한 분량을 먼저 보여준다.

### 4.1 사전 준비

```bash
cd <repo>
set -a && source ~/.orthus/nodes/company/node.env && set +a
```

필요한 것(전부 충족 확인됨): company DB 기동(`make up`), `node.env`, `keys.json`(Upstage 키 —
`FUGU_KEYS`로 경로 override 가능), `.venv`(`uv sync --extra dev`).

### 4.2 dry-run — 외부 전송 없이 검증 + 노출량 확인

```bash
.venv/bin/python experiments/fugu-ko/embedding/mirror_retrieve.py --dry-run
```

기대 출력(2026-07-16 실측):
```text
distractor: 10070개 중 1500개 표집 (seed=20260716)
pool: 1583 chunks | 생성기: {'claude': 83, 'gpt': 83}

[DRY RUN] Solar 전송 없음. 실제 실행 시 외부로 나갈 분량:
  - 회사 위키 청크 1583건 (약 225,642자) → embedding-passage
  - 질문 166건 (2개 생성기) → embedding-query
  - 목적지: https://api.upstage.ai/v1/embeddings
[체크] keys.json: True
[체크] prod 임베딩 슬롯: text-embedding-3-small:1024
[체크] lexical arm: 첫 케이스 후보 16건
```

**"약 N자"가 실제로 외부로 나갈 전부다.** 이 숫자를 보고 진행 여부를 결정하라.

### 4.3 (선택) Solar 질문 생성 — 3번째 생성기

`solar` 슬라이스까지 원하면 먼저:

```bash
.venv/bin/python experiments/fugu-ko/embedding/gen_questions.py --generator solar
```

⚠️ 이것도 회사 위키 원문을 Upstage chat API로 보낸다(같은 이유로 내가 못 돌림).
안 돌려도 gpt·claude 2종으로 편향 교차검증은 성립한다 — **다만 "Solar 자기편향" 칸은 비게 된다.**

### 4.4 실제 실행

```bash
.venv/bin/python experiments/fugu-ko/embedding/mirror_retrieve.py
```

- 소요: 수 분. 벡터는 `*.npy`로 캐시된다 → 재실행 시 API 재호출 없음.
  **재임베딩하려면 `.npy`를 지워라.** pool 구성이 바뀌면 캐시는 자동 무효화된다.
- 결과: 콘솔 교차표 + `mirror_results.json`(케이스별 rank).

### 4.5 노출량 조절

| 목적 | 명령 | 노출 | 신뢰도 |
|---|---|---|---|
| 기본 | (옵션 없음) | 1,583청크 ≈ 23만자 | 실용적 균형 |
| 노출 최소 | `--distractors 300` | ~380청크 | 낮음(후보가 적어 둘 다 쉽게 맞힘) |
| 프로덕션 충실 | `--full-corpus` | **전 company 청크 ~10k** | 가장 높음 |
| ❌ 금지 | `--distractors 0` | 83청크 | **무의미**(정답만 있어 랭킹 과제 불성립) |

> **왜 distractor가 필요한가:** 프로덕션은 질의가 ~1만 청크와 경쟁해 이긴다. 정답 83개만 pool에
> 넣으면(프로젝트 필터 후 ~35개) 두 모델 다 쉽게 맞혀 **차이가 안 보인다.** 기본값 1500은 노출을
> 통제하면서 랭킹 과제를 성립시키는 타협점이다. `--seed`로 표집이 재현된다.

### 4.6 결과 읽는 법

하네스가 **생성기 × 모델** 교차표를 찍는다:

```text
[veconly]  (veconly=임베딩 순수 영향, hybrid=사용자 체감)
  질문 작성     OpenAI hit@5   Solar hit@5     차이
  gpt                 0.xxx         0.xxx   +0.xxx
  claude              0.xxx         0.xxx   +0.xxx
```

| 지표 | 의미 |
|---|---|
| `veconly` | **임베딩 신호만 격리** → 교체의 순수 영향 |
| `hybrid` | 실제 프로덕션 랭킹(vector+lexical) → **사용자 체감** |

판단 순서:
1. **부호가 생성기마다 뒤집히면** → 생성기 편향. 결론 내지 마라.
2. **부호가 일정하면** → 진짜 신호. 그 다음 크기를 본다.
3. **`solar_hybrid` ≥ `openai_hybrid`면 교체 가능.** veconly가 좀 져도 hybrid가 동등하면
   lexical arm이 받쳐준다는 뜻이라 실사용 리스크는 낮다.
4. 83문항 기준 **±몇 %p는 노이즈**다.

### 5.2 hybrid가 뒤집힌 진짜 이유 — 블렌드 보정 아티팩트

`orthus/wiki/retrieve.py::_merge_candidates`는 이렇게 섞는다:

```python
base = max(vec, lex)          # ← 벡터 점수를 lexical 점수와 직접 크기 비교
combined = base + 0.15 * min(vec, lex_norm)
```

lexical 점수는 `0.45 + ...` 로 **0.45~1.0 밴드에 보정**돼 있다. 그런데 두 임베딩의 코사인
분포가 다르다 (`diagnose_scale.py` 실측, gpt 슬라이스 30문항):

| | 1위 점수 중앙값 | lexical(0.579)을 이긴 비율 |
|---|---|---|
| OpenAI | **0.592** | **53%** |
| Solar | **0.515** | **17%** |

**Solar의 코사인이 구조적으로 0.077 낮게 깔린다.** 순위는 더 좋은데(veconly가 증명) 절대
점수가 낮아 `max(vec, lex)`에서 자기 벡터 팔이 lexical에 먹힌다 — 83%의 경우에.
즉 hybrid의 마이너스는 **"Solar 임베딩이 나쁘다"가 아니라 "블렌드 상수가
text-embedding-3-small 분포에 맞춰져 있다"**는 뜻이다.

이를 검증하려고 **RRF**(순위만 쓰는 스케일 무관 융합)로 재채점했더니 부호가 갈렸다(5.1) —
아티팩트가 제거되자 hybrid의 일관된 OpenAI 우세가 사라졌다.

> **배포 함의:** 현행 블렌드 그대로 Solar로 갈아끼우면 **Solar의 (약간 더 나은) 벡터 신호를
> 83% 버리게 된다.** 교체한다면 블렌드 재보정이 **선택이 아니라 필수**다.
> 후보: (a) 벡터 점수 정규화 후 블렌드, (b) RRF 같은 순위 융합 전환, (c) 모델별 보정 상수.
> **(b)는 OpenAI 유지 시에도 프로덕션 랭킹을 바꾸므로 별도 검증이 필요하다.**

## 6. 지연/처리량 실측 (2026-07-16) — **교체의 실질 근거**

`latency.py`. **회사 데이터를 쓰지 않는다** — 지연은 내용이 아니라 토큰 수·왕복 시간에
달렸으므로 실제 워크로드의 **길이만 맞춘 합성 한국어**로 쟀다(청크 p50=210자, 질문 p50=34자).
교대 실행(네트워크 변동 통제) + 워밍업 후, 모델당 40회(질의)/5회(배치). 측정 시 load 0.87/8코어.

### 6.1 질의 지연 — `/ask`마다 1회, 사용자 체감 경로

| | p50 | p90 | p99 | 범위 |
|---|---|---|---|---|
| OpenAI (3-small) | 241ms | 276ms | **706ms** | 118~706ms |
| **Solar** (embedding-query) | **69ms** | **79ms** | **89ms** | **61~89ms** |

- **p50 −172ms (71% 빠름).** 그라운딩 1회 = 임베딩 1회이므로 **매 `/ask`에 그대로 더해진다.**
- **꼬리가 8배 낫다** (p99 89ms vs 706ms). 체감 품질엔 평균보다 꼬리가 중요하다.
- **분포가 완전히 분리된다** — Solar의 최악(89ms) < OpenAI의 최선(118ms). 40 표본 중 겹침 **0**.
  Mann-Whitney **z=7.7, p<0.0001**.

> **이 실험에서 유일하게 명백한 신호다.** 품질은 검정력이 없어 못 잡았지만(§5),
> 지연은 검정이 무의미할 만큼 압도적이다. 대조가 극명하다:
> 품질 = 불일치 27쌍·p=0.248 / 지연 = 분포 무겹침·p<0.0001.

**재현 확인 — 독립 2회 실행이 거의 동일하다(우연 아님):**

| 실행 | OpenAI p50 | Solar p50 | 차이 |
|---|---|---|---|
| 1회차 (n=40, load 0.87) | 241ms | 69ms | −172ms (71%) |
| 2회차 (n=30, load 0.40) | 245ms | 71ms | −174ms (71%) |

### 6.2 배치 처리량 — 교체 시 1회성 재임베딩 원가

| | 건당 (1회차) | 건당 (2회차) | 33,570청크 전량 |
|---|---|---|---|
| OpenAI | 9.8ms | 10.2ms | **약 5.5~5.7분** |
| Solar | 11.1ms | 10.5ms | **약 5.9~6.2분** |

**진짜 무승부다.** 1회차의 Solar 소폭 열세(11.1 vs 9.8)는 **2회차에서 재현되지 않았다**
(10.5 vs 10.2) → 측정 잡음이었다. 마이그레이션 비용은 **의사결정에 영향을 주지 않는다**
— 둘 다 6분 안팎이고, 실제론 병렬화하므로 이보다 짧다.

> **질의 지연은 재현되고 배치는 안 된다는 대조가 중요하다.** 같은 스크립트·같은 조건에서
> 한쪽(−172/−174ms)은 소수점까지 반복되고 다른 쪽은 부호가 뒤집혔다 →
> 질의 지연 차이가 실재한다는 방증이다.

### 6.3 ⚠️ 이 결과의 최대 교란: 지리

**OpenAI = 미국 리전 / Upstage = 한국 리전.** 이 박스는 한국에 있으므로 Solar가
**지리적 이점**을 갖는다. 즉 6.1의 172ms 상당 부분은 모델 성능이 아니라 **RTT**다.

**그래도 이 이점은 진짜다** — prod central(`acme-macstudio`)도 한국에 있으므로
운영 환경에서 그대로 실현된다. 다만:

- **해외 리전으로 배포하면 뒤집힌다.** 그때는 재측정 필수.
- "Solar 모델이 더 빠르다"가 아니라 **"한국에서 쓰면 더 빠르다"**가 정확한 표현이다.

> 맞힌다(각 방향 2건 엇갈림). 포화 지점에서 총합만 같아진 우연이다.

### 8.3 그래도 내릴 수 있는 실용 판단 (통계 ≠ 의사결정)

- **비대칭 배선 → 생략 권고.** 측정된 이득이 veconly **1문항(+1.2%p)**. Protocol 수술 +
  4~6개 호출지점 수정의 값어치로는 부족하다. *"차이 없음이 증명됐다"가 아니라 **"측정 가능한
  상한이 이미 작업 비용 미만"***이라는 논증이다. → **교체 비용이 줄어든다.**
- **4096 마이그레이션 → 근거 없음.** 불일치 쌍 **0**(83문항 top-5 완전 동일) + `dimensions`가
  matryoshka 절단이 아님(아래) → 저장/인덱스 4배를 정당화할 신호가 전무하다.

### 8.4 부수 발견 — `dimensions`는 matryoshka 절단이 아니다

4096-d 벡터의 **앞 1024차원 vs 1024-d 벡터를 실측하니 정규화 후 cos = 0.039**(사실상 직교).
Upstage의 `dimensions`는 앞을 자르는 게 아니라 **다른 표현을 낸다**(별도 projection 추정).

- 배선에는 무영향(어느 쪽이든 1024를 받으면 됨).
- 단 **"matryoshka이므로 큰 차원이 정보 상위집합"이라는 추론은 무효**다.
  (초기 문서에 "matryoshka식 절단 지원 확인"이라고 썼던 것을 정정했다.)

### 8.5 진짜 설계 오류 — hit@5가 정보를 버렸다 (수정 완료)

§8.2를 "천장효과 + 슬라이스 선택 실수"로 진단했지만 **그건 표면이었다.** 슬라이스를 3배로
늘려도 못 구제한다:

| | 값 |
|---|---|
| gpt 83문항 불일치 쌍 (실측) | **1** |
| 249문항으로 3배 확대 시 추정 | ~3~8 |
| **80% 검정력에 필요**(승률 63% 가정) | **114** |

→ **슬라이스 확대만으로는 필요량의 수 %에 불과하다.**

**진짜 원인:** 순위를 **top-5까지만 관측**했다(`rank_of([...][:K])`, K=5). 후보를 40개 뽑아
놓고 **6위든 40위든 전부 `None`(실패)로 뭉갰다.** 그래서:
- 정답이 **1위 → 3위로 밀리는 실제 열화가 "변화 없음"**이 된다.
- 이진 hit@5만 남아 불일치 쌍이 0~4로 붕괴 → 어떤 결과도 검정 불가.

**수정:** 관측 깊이를 **40위**로 넓히고, **RR(=1/rank) + Wilcoxon signed-rank**로 검정한다.
그러면 **불일치 쌍이 아니라 순위가 바뀐 모든 문항**이 표본이 된다. 스텁 실증:

| 지표 | 실질 표본 (83문항 기준) |
|---|---|
| 이진 hit@5 | 불일치 **4쌍** |
| **RR + Wilcoxon** | 순위변화 **23** (≈**6배**) |

`hit@5`는 `rank<=5`로 그대로 유도되므로 **기존 지표와 호환**된다(§8.1 수치는 유효).

> **교훈:** "표본이 작다"의 해법이 항상 "표본을 늘려라"는 아니다. **지표가 정보를 버리고
> 있으면 먼저 지표를 고쳐야 한다.** 여기선 관측 깊이 하나로 검정력이 6배 올랐고, 슬라이스
> 3배는 그보다 못했다. → LAB-NOTES S11.

### 8.6 ⭐ 재측정 결과 — 결론이 뒤집혔다 (이 문서의 정정본)

수정된 하네스(관측 깊이 40 + RR/Wilcoxon + 전 슬라이스 249문항)로 재측정한 결과.
**§5는 이 절로 대체된다.**

#### (a) 비대칭이 오히려 나쁘다 — 벤더 의도와 반대

| 비교 | MRR 비대칭 | MRR 대칭 | p |
|---|---|---|---|
| 1024 veconly | 0.855 | **0.908** | **0.000** |
| 1024 hybrid | 0.724 | **0.860** | **0.000** |
| 4096 veconly | 0.843 | **0.901** | **0.000** |
| 4096 hybrid | 0.713 | **0.828** | **0.000** |

**4개 조건 전부 대칭이 유의하게 이긴다.** `embedding-query`/`embedding-passage`는 Upstage가
쌍으로 제공하는 **의도된 사용법**인데, 우리 데이터에선 **passage 모델로 질의까지 임베딩**하는
쪽이 낫다.

**메커니즘(측정으로 확인):** `embedding-query`는 passage 공간에서 **멀리 떨어진 곳**에 임베딩한다.

| | 질의-청크 코사인 (전체 쌍 평균) | 1위 코사인 중앙값 |
|---|---|---|
| 비대칭(query 모델) | 0.141 | **0.489** ← lexical(0.579) **아래** |
| 대칭(passage 모델) | 0.274 | **0.624** ← lexical **위** |
| (OpenAI 참고) | — | 0.592 |

→ 순위도 나쁘고, `max(vec,lex)`에서 lexical에 먹혀 hybrid도 나쁘다. **§5.2가 "Solar 코사인이
구조적으로 낮다"고 한 건 절반만 맞다 — 낮은 건 `query` 모델이고, `passage` 모델은 OpenAI보다
높다.**

#### (b) 그래서 Solar가 OpenAI를 유의하게 이긴다 (같은 249문항)

| 지표 | 사용법 | OpenAI MRR | Solar MRR | 차이 | p | 판정 |
|---|---|---|---|---|---|---|
| veconly | **대칭** | 0.828 | **0.908** | **+0.080** | **0.0001** | **Solar 유의 우세** |
| veconly | 비대칭(§5) | 0.828 | 0.855 | +0.027 | 0.199 | 검출못함 |
| hybrid | **대칭** | 0.747 | **0.860** | **+0.112** | **0.0000** | **Solar 유의 우세** |
| hybrid | 비대칭(§5) | 0.747 | 0.724 | −0.023 | 0.265 | 검출못함 |

**§5의 "차이 없음"은 표본 부족이 아니라 측정 오류였다.** 같은 249문항에서 올바른 사용법 +
순위 지표로 재면 **p<0.001로 유의**하다. §5의 "1,055문항 필요"는 무효다.

#### (c) 4096은 오히려 1024보다 못하다

| 지표 | MRR 4096 | MRR 1024 | p |
|---|---|---|---|
| veconly | 0.843 | **0.855** | **0.017 유의** |
| hybrid | 0.713 | **0.724** | 0.104 검출못함 |

`dimensions`가 matryoshka가 아니므로(§8.4) 큰 차원이 낫다는 보장이 없고, **실측은 오히려 반대**다.
→ **스키마 마이그레이션 근거 없음**(저장/인덱스 4배를 쓰고 성능이 내려간다).

#### (d) 결론: 교체 작업이 **config 한 줄**로 줄었다

| 항목 | 이전 판단 | **정정** |
|---|---|---|
| 비대칭 배선 | "생략 권고"(값어치 없음) | ❌ **하면 안 됨** — 유의하게 해롭다 |
| 블렌드 재보정 | "**필수**"(§5.2) | ✅ **불필요** — 대칭 코사인(0.624)이 lexical(0.579) 위라 잘 섞인다 |
| 4096 마이그레이션 | "근거 없음" | ❌ **하면 안 됨** — 유의하게 나쁘다 |
| 전량 재임베딩 | 필요 | ✅ 여전히 필요(`model_version` 혼재 금지) |

**현행 Protocol은 색인/질의에 같은 모델을 쓴다 — 그게 바로 대칭이다.**
즉 `ORTHUS_EMBEDDING_MODEL=embedding-passage`로 바꾸는 **config 변경만으로 최적 구성이 된다.**
배선 작업이 필요 없는 게 아니라, **배선하면 나빠진다.**

#### (e) 실제 질의 형태 재검증 — ✅ 해소됨, 결론 유지

**제기된 의문:** 평가셋(34자/의문형 94%)은 실제 질의보다 길고 문장형이다. **긴 의문문은
passage를 닮아 대칭에 유리했을 수 있다** — `embedding-query`는 짧은 질의용으로 학습됐을
테니 실제 형태에선 비대칭이 이길지 모른다.

**먼저 모집단 오류부터 정정한다.** 초판은 `query_runs`(5,635건)를 실제 질의라고 썼는데,
그 테이블은 **structured(NL→SQL) 분기 로그**다(`compiled_sql` 100%) — **임베딩을 아예
타지 않는다.** wiki 질의의 실제 로그는 `ask_cache.question_redacted`(성공 19) +
`data_gaps.question`(실패 53)이다.

| | 평가셋(verbose) | **평가셋(`--style real`)** | **실제 wiki 질의(n=72)** |
|---|---|---|---|
| 길이 p50 | 34자 | **15자** | **21자** |
| 의문형 비율 | 94% | **48%** | **49%** |

*(의문형 판정기 버그도 함께 수정 — `"찾아줘"`의 `줘`를 의문형으로 세어 실제 비율을
62~68%로 부풀렸다. 지시형을 먼저 배제해 49%로 정정. `gen_questions.py::is_interrogative`)*

**결과 (`--generators gpt-real`, 83문항, MRR/Wilcoxon):**

| 조건 | MRR 비대칭 | MRR 대칭 | 차이 | p |
|---|---|---|---|---|
| 1024 veconly | 0.865 | **0.907** | −0.042 | 0.055 검출못함 |
| 1024 hybrid | 0.856 | **0.908** | −0.052 | **0.022 유의** |
| 4096 veconly | 0.886 | **0.919** | −0.034 | 0.113 검출못함 |
| 4096 hybrid | 0.858 | **0.906** | −0.049 | **0.037 유의** |

**4개 조건 전부 대칭 우세 방향이고 2개가 유의하다. 부호 역전 없음 → (a)의 결론 유지.**
효과 크기도 verbose(−0.05~0.14)와 같은 대역이다. 즉 **대칭 우세는 문장 길이/형태의
artefact가 아니라 `embedding-query`의 모델 특성**이다(질의-청크 코사인 0.141, (a) 메커니즘).

**주의 — 이 슬라이스에서 p가 커진 건 표본이 83이라서지 효과가 작아서가 아니다.**
verbose 249문항 대비 1/3이다. 4개 부호가 모두 같은 방향인 게 더 강한 신호다.

**부수 관찰 2개:**
- **hit@5는 천장에 붙어 무용지물이었다.** 기준선 veconly 0.916 / hybrid 0.964 →
  불일치쌍 1~2개(p=1.000). §8.5의 "이진 지표는 정보를 버린다"가 이 슬라이스에서
  극단적으로 재현됐다. 순위 지표가 없었으면 **아무것도 못 봤다.**
- **4096 vs 1024의 부호가 뒤집혔다**(veconly +0.021, p=0.041 — 여기선 4096이 낫다).
  verbose 249문항에선 1024가 유의하게 나았다(§8.6c). **n=83에서 겨우 유의한 반대
  방향이므로 어느 쪽도 신뢰하지 않는다** — 어차피 4096은 저장/인덱스 4배라
  이 정도 불안정한 이득으론 마이그레이션 근거가 못 된다. **1024 유지.**

**제목 누출:** real 셋 13/83(verbose 6/83). 전부 고유명사·기술용어(OGDM, PCM, MVP,
TIC-FT)로 동의어가 없어 실제 질의도 똑같이 누출한다("nova가 어떤 서비스야"). 게다가
**lexical arm은 두 arm이 공유**하고 veconly는 lexical을 아예 안 보므로 비대칭 vs 대칭
비교에는 영향이 없다.

  순위 지표(RR/Wilcoxon)로 바꾸니 **같은 249문항에서 p<0.001**이 나온다. 부족했던 건 표본이
  아니라 **지표의 정보량**이었다(§8.5). `power.py`의 계산 자체는 맞지만, **애초에 정보를 버리는
  지표에 검정력을 물은 게 틀렸다.**
  - 단 `--style real` 슬라이스는 여전히 n=83이라 4개 조건 중 2개만 유의하다(§8.6e).
    `claude-real`/`solar-real`을 추가하면 249로 는다. **부호가 4/4 일관이라 우선순위는 낮다.**
- **"페이지 1개 = 정답 1개" 가정** — 절대 수치는 비관적. 상대 비교로만 유효.

## 15. A.X-Encoder 파인튜닝 — 오픈웨이트 국내 인코더 vs 상용 API (2026-07-17)

**질문:** §1의 정정("API는 Solar뿐이나 오픈웨이트는 존재")을 실측한다. `skt/A.X-Encoder-base`
(0.1B ModernBERT, 한국어 특화, KLUE 86.10)를 회사 위키로 파인튜닝하면 현행 프로덕션
임베딩(Solar)을 이기는가? **배선 없이 인메모리 채점만.**

### 15.1 결론

| arm (veconly/strict) | MRR | Solar 대비 | Wilcoxon p |
|---|---|---|---|
| **Solar (프로덕션 `embedding-passage:1024`)** | **0.7040** | — | — |
| **A.X-ft-page** (page-only positive 2,521쌍) | **0.6336** | **90.0%** | 0.056 검출못함 |
| A.X-ft (전체 pool positive 9,797쌍) | 0.4908 | 69.7% | <0.001 유의 |
| A.X-zeroshot (파인튜닝 전) | 0.1287 | 18.3% | <0.001 유의 |

**판정: 중단.** 최선 변형이 Solar의 90.0%로 판정 기준 95%에 못 미친다. 단 p=0.056이라
"Solar가 유의하게 낫다"고 말할 수는 없다 — **"못 넘었다"이지 "졌음이 증명됐다"가 아니다.**
현행 Solar 슬롯(§14.6) 유지.

**부수 결론(강함):** **MLM 백본은 파인튜닝 없이 검색에 못 쓴다** — zero-shot MRR 0.129,
무관한 두 문장의 코사인이 0.774(이방성). 모델 카드가 retrieval을 언급하지 않는 이유다.
파인튜닝이 0.129 → 0.634로 **4.9배** 끌어올렸다.

### 15.2 ★ 이 실험의 진짜 발견 — 학습 분포가 결과를 지배했다

첫 학습(전체 pool)은 **69.7%**였는데, positive를 page-only로 바꾸자 **90.0%**가 됐다
(+0.143 MRR, p<0.001). **20%p가 모델 능력이 아니라 학습셋 구성에서 나왔다.**

원인: wiki pool 10,153 = **page 2,618(26%) + claim 7,535(74%)**이고 claim은 page를 컴파일한
원재료라 본문이 거의 같다. pool 전체로 학습하면 positive의 74%가 claim이라 **claim 문체를
정답으로 배운다.** top-1 kind 분포가 그 증거다:

| arm | top1=page | top1=claim | **정답 페이지의 claim을 1위로** |
|---|---|---|---|
| Solar | 122 (73%) | 44 (27%) | 33건 (20%) |
| A.X-ft | 58 (35%) | 108 (65%) | **76건 (46%)** |

pool이 74% claim인데 **Solar는 73%를 page로 뽑는다** — 페이지 형식(`# 제목 / ## Concise
Definition`)을 선호하는 강한 내재 편향이 있다. 반면 A.X-ft는 pool 분포를 그대로 따라
kind에 중립적이고, **166건 중 76건(46%)에서 "정답 페이지의 claim"을 1위로 올렸다** —
지식은 맞혔는데 granularity가 틀렸다. strict 0.49 → lenient 0.79 도약의 정체다.

> **교훈: 학습 positive 분포를 eval 표적 분포에 맞춰라.** 이걸 놓치면 모델 능력이 아니라
> 자기 설정 실수를 측정하게 된다.

### 15.3 ★ 인계문서 T3보다 깊은 누수 — claim까지 빼야 한다

인계문서는 *"평가 83페이지를 학습에서 빼라"*고 했다. **그대로 따르면 실험이 무효다:**

```
평가 페이지 <slug>          : "<운영비 관련 한 문장>"
그 claim   <slug>-<hash>   : "<운영비 관련 한 문장>"   ← 페이지와 글자 단위로 동일
```
(실측 예: 어느 운영비 페이지와 그 claim의 본문이 문장 하나까지 같았다. 구체 수치는
저장소에 남기지 않는다 — 요점은 "page 본문 = claim 본문"이라는 구조다.)

`wiki_links.rel='supports'`로 평가 83페이지를 떠받치는 **claim 247개**(83페이지 전부가 보유)를
추가 제외했다. 안 뺐으면 정답 본문을 그대로 외운 모델을 평가할 뻔했다. 하드 네거티브도
같은 이유로 family(같은 지식) 단위로 걸렀다 — 형제 claim을 네거티브로 주면 "같은 지식을
서로 밀어내라"고 가르치는 꼴이다.

### 15.4 ★ 선행 하네스의 측정 버그 2개 (고쳐서 씀)

1. **`rank_of`가 부분 문자열 매칭** — `expected in slug`라 claim slug(`<page>-<hash>`)와
   **평가 83/83 전 케이스가 충돌**한다. `confirmation` ⊂ **다른 페이지** `message-confirmation`
   까지 정답 크레딧을 받는다. → `score_ax.py`는 strict(정확일치) 대표 + lenient(페이지∪claim)
   보조 2지표로 교체.
2. **케이스별 project 필터** — 프로덕션 `retrieve()`의 기본은 `project=None`(전 프로젝트)인데
   (`orthus/wiki/retrieve.py` §130-131) 하네스는 케이스마다 project로 좁혀 orbit 질문이
   279청크만 상대했다. 하네스 자신도 모순이다 — `build_pool` 주석은 *"prod ranks against
   ~10k chunks"*라면서 채점 루프는 좁힌다. **선행 실험이 보고한 hit@5 0.95 천장효과의 유력한
   원인.** → 제거하고 프로덕션 기본값(전 10,153 pool)에 맞췄다.

### 15.5 공정성 설계

- **pool·질문·관측깊이(40)·lexical arm 전부 공유.** lexical은 프로덕션
  `orthus.wiki.retrieve` import(재구현 금지).
- **ft/ftp/zs 3 arm이 `ax_encoder.encode` 하나를 공유** — 유일한 차이가 가중치다.
  sentence-transformers를 안 쓴 이유: 공유 A100의 torch/transformers 섀도잉 위험 +
  `datasets` 미설치 + **zs arm만 손수 짜면 경로가 갈려 공정성이 깨진다**. MNRL은 20줄.
- **잘림 0건** — pool 최대 253토큰 < `MAX_LEN` 256. A.X도 Solar와 같은 전문을 본다.
- **표집 시드 고정**(`FUGU_SAMPLE_SEED=20260717`) — 선행 실험은 `ORDER BY random()`이라
  평가셋이 지워지자 재현 불가였다(T2). 두 실행 동일 해시 확인.
- **생성기 2종 교차검증.** 단 학습 질문이 solar-pro라 **`solar-real`은 어투 일치 이점이 있는
  낙관적 슬라이스**이고 **`gpt-real`이 보수적**이다. ftp는 gpt-real 0.6135 / solar-real
  0.6537로 **양쪽 다 Solar에 미달** — 결론이 생성기에 좌우되지 않는다.

### 15.6 남은 질문 (미측정)

- **ftp의 데이터량 교란.** page-only는 2,521쌍뿐이다(page가 2,618개라 1문항/페이지 상한).
  ft는 9,797쌍이었다. **3~4문항/페이지로 ~10k page-only 쌍을 만들면 남은 10%가 닫힐 수
  있다** — 이 실험의 가장 값어치 있는 후속.
- **하이퍼파라미터 미탐색.** batch 64 · 3ep · lr 2e-5 · negs 4 고정(dev MRR 0.927로 수렴).
- **SPLADE 경로**(`yjoonjang/splade-ko-v1`가 같은 백본으로 sparse retrieval) 미측정.
- **T4(한국어 특화 이점)** — 코퍼스가 한글 15.9%/영어 48.2%라 이점이 안 난다는 가설은
  **직접 검증되지 않았다.** 90%까지 온 걸 보면 "한국어 특화가 무의미하다"기보다
  "0.1B가 상용 API를 못 넘었다"에 가깝다.
- **배선은 미검토**(이기지 못했으므로). 이겼다면 768→1024 projection 또는 스키마 변경 필요.
