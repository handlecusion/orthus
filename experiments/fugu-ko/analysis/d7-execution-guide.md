## 1. 이게 무슨 실험인가 (배경 이야기)

### 1.1 등장인물

- **워커(worker):** 한국어 질문을 받아 데이터베이스(DB)에서 답을 찾아오는 AI 모델.
  우리에겐 3명의 워커가 있다 — **Solar, A.X, EXAONE** (전부 국내 모델, API 키 보유).
- **규칙기(규칙 선택기):** "무조건 Solar에게 시켜"라는 단순한 규칙. 현재 챔피언.
  홀드아웃 시험에서 **60.5%** 정답률.
- **학습기(학습 선택기):** 질문마다 "이번엔 어느 워커가 잘할까"를 AI로 배워서 고르는
  방식. 이게 규칙기를 이기게 만드는 것이 대회의 목표.
- **오라클(oracle):** 신(神) 관점. 매 문제마다 정답을 낸 워커가 한 명이라도 있으면
  맞았다고 쳐주는 이론적 상한선. **67.8%**. 즉 규칙기와 오라클 사이에 **+7.3%p의
  "이길 여지(headroom)"**가 실제로 존재한다.

### 1.2 지금까지의 성적표 (D5 → D6)

D6에서 국내 모델 13종으로 학습기를 만들어 전부 겨뤄봤지만 **13전 13패**였다.
이유를 파보니:

> Solar가 틀리는 이유는 **질문 문장에 있지 않고 DB 내용물의 함정에 있다.**
> 예: DB에 저장된 값이 `'직원 '`(뒤에 공백), 이모지 섞인 이름 등. 질문만 보고는
> 이걸 절대 알 수 없으니, "질문을 읽고 워커를 고르는" 학습기는 배울 신호 자체가 없다.
> 게다가 그 함정은 DB마다 달라서, 한 DB에서 배운 패턴이 새 DB로 **전이되지 않는다.**

그래서 D6의 결론은 "규칙(무조건 Solar)이면 충분하다"였다.

### 1.3 D7의 새 관점 — "고르는 시점"을 바꾼다

D6의 학습기는 전부 **일을 시키기 전에**(질문만 보고) 워커를 골랐다. D7의 핵심
아이디어는 이렇다:

> **일단 세 워커에게 다 시켜보고, 나온 답들을 보고 나서 고르자.**
>
> 답안지를 보면 힌트가 넘친다 — 어떤 답은 아예 에러가 났고, 어떤 답은 빈 값이고,
> 어떤 답은 SQL(DB 질의문)이 존재하지 않는 값을 찾고 있다. 이 힌트들은 질문이
> 아니라 **지금 눈앞의 DB에서 직접 측정**되기 때문에, "새 DB로 전이가 안 된다"는
> D6의 병목이 아예 사라진다.

### 1.4 이미 확인된 증거 (2026-07-16 실측)

D6 때 저장해 둔 워커 답안 기록을 다시 분석해 보니 (아래 4.1의 진단 스크립트):

| 발견 | 수치 |
|---|---|
| Solar 오답 180건 중 "에러 또는 빈 답"이라 **즉시 오답임을 알 수 있는 것** | 46건 (26%) |
| Solar가 **맞았는데** 에러/빈 답인 경우 (억울하게 갈아탈 위험) | **0건** |
| "에러/빈 답이면 다른 워커로 갈아타기"만 해도 | **60.5% → 62.9% (통계적으로 유의, p≈0.008)** |
| 그래도 남는, 더 똑똑한 검증이 필요한 문제 | 24문항 (+5.2%p 여지) |

특히 두 번째 줄이 중요하다: 이 시험의 채점 방식에서 **빈 답은 무조건 오답**이다
(정답이 빈 값인 문제가 0개라서). 그러니 "빈 답이면 갈아타기"는 **절대 손해 볼 수
없는** 안전한 개선이다. D6에서 다수결 투표(vote2of3)가 오히려 −2.6%p로 진 것과
근본적으로 다른 이유다 — 투표는 "여럿이 일치하면 옳다"는 *틀린* 가정에 걸었고,
이번 것은 "빈 답은 틀리다"는 *참인* 가정에 건다.

### 1.5 D7이 만들 것 — 3단 로켓

1. **[1단] 실행 증거 검증기 (주력):** 세 워커의 답을 받아서, 각 답의
   (질문, SQL, 실행 결과)를 보고 "이 답이 맞을 확률"을 매기는 작은 AI를 학습한다.
   기본은 Solar 유지, 검증기가 확신할 때만 갈아탄다.
2. **[2단] 다수 샘플 + 자가 수정:** Solar에게 같은 질문을 5번 다르게 풀게 해서
   실행 결과가 수렴하는 답을 고르고, 전부 미심쩍으면 "네 SQL이 찾는 값 `'직원'`은
   없고 `'직원 '`(공백 포함)이 있어"라는 증거를 주며 한 번 다시 풀게 한다.
3. **[3단] 파인튜닝 워커 (A100의 진짜 용처):** 3,000문항 라벨에서 "정답을 낸
   워커의 SQL"만 모아 EXAONE-4.0을 학습시켜 **4번째 워커**를 만든다. 고르기만
   해서는 오라클 67.8%가 천장이지만, 더 나은 워커는 천장을 뚫을 수 있다.

## 2. 용어 사전 (모르는 말이 나오면 여기로)

| 용어 | 뜻 |
|---|---|
| SQL | 데이터베이스에게 "이 조건에 맞는 걸 찾아줘"라고 시키는 질의문. 워커가 한국어 질문을 SQL로 번역해서 실행한다. |
| 홀드아웃(holdout) | 학습에 **절대 쓰지 않고** 숨겨둔 시험지. 이걸로 채점해야 "외운 것"이 아니라 "실력"을 잰다. 우리 주 시험지는 463문항. |
| 헤드룸(headroom) | 규칙기 점수와 오라클 점수의 차이 = 이론상 이길 수 있는 최대 폭. |
| degenerate(불량 답) | 실행 에러가 났거나 결과가 빈 답. 이 시험에선 무조건 오답. |
| McNemar 검정, p값 | "이 점수 차이가 우연인가 실력인가"를 재는 통계 검정. **p가 0.05보다 작으면** 우연이라 보기 어렵다(=유의하다)고 판정. |
| 부트스트랩 | 시험지를 무작위로 다시 뽑아 수천 번 채점해 보는 방법. "다시 시험 봐도 이길 확률"을 알려준다. |
| 사전선언 | 실험 **전에** "이 방법, 이 시험지, 이 기준으로 판정하겠다"를 못 박는 것. 결과 보고 유리한 기준을 고르는 자기기만(D6의 rigged 실증)을 막는다. |
| 워크트리(worktree) | 같은 코드 저장소를 여러 폴더로 나눠 쓰는 것. 이 실험은 `.worktrees/fugu-ko-selector-v2` 폴더 안에서만 한다(본 코드에 영향 없음). |
| A100 | 원격 GPU 서버(`ssh a100`). 모델 학습용. 크레딧 만료 ~7/31. |

### 4.1 사전 진단 — 지금 바로 5초 안에 실행 가능 ✅

D7의 근거가 되는 수치를 직접 재현해 본다. **API 호출도 DB 접속도 없이** 저장된
기록만 읽으므로 안전하다.

```bash
cd experiments/fugu-ko
$PY train/diag_exec_signal.py
```

**기대 출력** (숫자가 아래와 같으면 정상):

```
n=463 acc= {'solar': 61.1, 'ax': 48.4, 'exaone': 42.8}    ← 세 워커의 홀드아웃 점수
solar wrong 180 / degenerate 46 / 위양성 0                 ← 오답 180 중 46이 즉시 감지, 억울한 케이스 0
[결정론 fallback] 62.9% vs static 61.1% (득8/실0, McNemar p≈0.007812)
잔여 회수 대상(내용 검증 필요) 24문항, tag=Counter({'filter': 11, 'count': 6, ...})
```

> 읽는 법: "에러/빈 답이면 갈아타기"라는 공짜 안전장치만으로 +1.8%p(유의),
> 그 위에 학습기가 노릴 몫이 +5.2%p 남아 있다.

### 4.2 학습 데이터 재캡처 — 검증기의 교과서 만들기 🔨

**목적:** 기존 3,000문항 라벨(`labeled2.jsonl`)에는 "맞았다/틀렸다"만 있고
**워커가 쓴 SQL과 실행 결과가 저장돼 있지 않다.** 검증기는 그걸 보고 배워야
하므로, 라벨링을 한 번 다시 돌리며 SQL·실행 결과·에러를 통째로 저장한다.

**할 일:** `train/label2.py`를 복사해 `label3.py`를 만들고, 워커 응답에서
`compiled_sql`, 실행 결과 숫자셋, 에러 메시지를 JSON에 추가 저장하게 고친다.

**실행 (예정 형태):**

```bash
cd experiments/fugu-ko
# 오래 걸리는 작업(API 3,000문항 × 3워커)이므로 세션이 끊겨도 죽지 않게 setsid로:
setsid bash -c "$PY train/label3.py --models solar,ax,exaone \
  > train/logs/label3.log 2>&1" < /dev/null &
tail -f train/logs/label3.log   # 진행 상황 구경 (Ctrl+C로 구경만 중단, 작업은 계속)
```

**⚠️ 주의 (D6에서 실제로 겪은 함정):**
- 1,000개 이상 연속 질의하면 DB 연결이 고갈돼 응답이 대량 실패한다.
  `vote_holdout.py` 안의 `_query_retry`(재시도+엔진 재생성+대기) 패턴을 그대로 재사용할 것.
- 끝나면 **무결성 검증**: 재실행한 solar 정답률이 기존 기록(≈61%)과 비슷한지 확인.
  크게 다르면 캡처가 잘못된 것이니 결과를 쓰지 말 것.
- 산출물(`labeled3.jsonl` 등)은 즉시 A100에 백업.

### 4.3 검증기 학습 — D7의 심장 🔨

**목적:** (질문, SQL, 실행 증거) → "이 답이 맞을 확률"을 내는 작은 모델을 학습.
교과서는 4.2의 산출물 (3,000문항 × 3워커 = 9,000개의 정오 라벨).

**핵심 설계 (이 부분이 D6과 다른 지점):**
- 입력 피처는 **추론 시점에 눈앞의 DB에서 직접 재는 값**으로 구성한다:
  - SQL이 찾는 값이 그 컬럼에 실제로 존재하는가 (`SELECT EXISTS` 확인 질의 — 읽기 전용)
  - 공백 제거/이모지 제거하고 다시 찾으면 존재하는가 (DB 함정 감지)
  - 결과 개수가 질문 유형과 어울리는가 (개수 질문인데 목록 반환 등)
  - 후보들끼리 실행 결과가 얼마나 뭉치는가
- 결정 규칙은 보수적으로: **기본은 Solar. 검증기가 Solar 답을 기각하고 다른 답을
  높은 확신으로 통과시킬 때만 갈아탄다.** (D6 교훈: 함부로 갈아타면 진다)

**실행 (예정 형태):** 학습 자체는 가벼워서 A100 1장 몇 분 거리.

```bash
ssh a100 'cd /data/tta/fugu-ko && export HF_HOME=/data/tta/hf-cache TMPDIR=/data/tta/tmp \
  PYTHONPATH=/data/tta/fugu-ko:/data/tta/fugu-ko/train:/data/tta/pylibs && \
  setsid bash -c "CUDA_VISIBLE_DEVICES=0 python -u train/verifier.py > train/logs/verifier.log 2>&1" < /dev/null &'
```

### 4.4 Self-consistency + 자가 수정 🔨

**목적:** Solar에게 같은 질문을 온도(무작위성)를 달리해 5번 풀게 하고, **실행
결과가 같은 답끼리 묶어** 가장 큰 묶음을 채택한다(정답 SQL들은 결과가 수렴하고
오답은 흩어지는 성질 이용 — NL2SQL 분야 표준 기법). 전 후보가 검증기에서 기각되면
확인 질의에서 얻은 증거(예: "`'직원'`은 없고 `'직원 '`이 있음")를 넣어 딱 한 번
다시 풀게 한다.

**주의:** API 호출이 5배가 되므로 비용/속도는 미리 어림하고 시작. 판정 규칙(몇
표 이상이면 채택 등)은 **홀드아웃을 보기 전에** 학습셋 쪽에서 튜닝해 고정할 것.

### 4.5 파인튜닝 워커 — A100 4장의 주 용처 🔨

**목적:** 3,000 라벨에서 "정답을 낸 워커의 SQL"만 골라 (스키마+질문 → 정답 SQL)
데이터셋을 만들고, EXAONE-4.0(32B는 QLoRA, 소형은 full)을 학습시켜 4번째 워커를
만든다. 여러 DB 스키마(425종 spec)를 프롬프트에 넣고 학습하므로 새 DB에는 그 DB의
스키마를 보여주는 것으로 대응한다.

**⚠️ A100 함정 (전부 D6에서 실제로 터졌던 것):**
- 루트 디스크가 100% 차 있다. 작업/캐시/임시파일 전부 `/data/tta/*` 밑으로.
  (`HF_HOME=/data/tta/hf-cache TMPDIR=/data/tta/tmp`)
- pip 설치는 반드시 `pip install --no-deps --target=/data/tta/pylibs <패키지>`.
  `--no-deps`를 빼먹으면 torch가 딸려 들어와 GPU 환경 전체가 깨진다.
- transformers 5.13은 EXAONE-3.5와 호환 안 됨 → **EXAONE-4.0만 사용**.
- 새 학습을 걸기 전에 이전 작업이 안 도는지 확인:
  `ssh a100 'pgrep -f "verifier.py|sft_worker.py|tier[23]v.py" | wc -l'` 이 `0`이어야 함.

### 4.6 공정 판정 — "진짜 이겼다"를 선언하는 절차

D6의 제일 값진 교훈이 이 절차다. **순서를 지키지 않은 승리는 무효다**
(유리한 판을 골라 이기는 법은 `rigged.py`가 +9.2%p로 실증했다 — 그래서 안 믿는다).

1. **사전선언 문서 작성** (이 폴더에 `d7-prereg.md`): 방법(검증기+SC+SFT 워커 중
   무엇을 쓸지), 판정 시험지, 채점 방식(gold ⊆ 반환셋, 단일 답만 인정), 통계 기준
   (McNemar p<0.05 **그리고** fresh 재현 + 부트스트랩 P(이김)>95%)을 실험 전에 고정.
2. **새 홀드아웃 생성:** 오늘의 진단(4.1)은 기존 463 시험지를 "본" 것이므로, 확증은
   **새로 만든 held-out DB 2~3개, 총 900문항 이상**에서 한다.
   `gen2.py` → `build_unseen_v2.py` → `label2.py`(또는 label3) 재사용.
   n을 키우는 이유: +3~5%p 차이를 유의하게 재려면 463문항으로는 빠듯하다.
3. **헤드룸 게이트 먼저:** 새 시험지에서 규칙기·오라클 점수부터 재서 이길 여지가
   있는 판인지 확인(+5%p 미만이면 시험지를 더 키운다).
4. **본판정:** 시스템을 **한 번만** 돌려 채점. `eval_v2.py` 재사용.
5. **재현:** 또 다른 fresh 시험지에서 같은 결과가 나와야 최종 "이겼다" 선언.

**공정성 규칙 (사전선언에 포함):**
- 최종 출력은 **단일 답** (여러 워커 답을 합쳐 "다 뱉기" 금지 — 그건 D6에서 밝힌 채점 착시).
- 추론 중 정답(gold) 접근 금지.
- DB에는 읽기 전용 확인 질의(`SELECT`/`EXISTS`)만 허용.
- 여러 워커를 호출하는 것 자체는 허용 (D6가 vote2of3를 "배포 가능"으로 인정한 선례).

## 6. 자주 하는 질문 (FAQ)

**Q. 이미 62.9%가 나왔는데 그냥 이긴 것 아닌가?**
A. 아니다. 두 가지 이유: ① 그 수치는 기존 시험지를 "보고 나서" 잰 것이라 정식
승리 선언에는 새 시험지가 필요하다(§4.6). ② "에러/빈 답이면 갈아타기"는 학습이
아니라 또 하나의 규칙이라, 심판이 "그럼 규칙기에도 그걸 넣겠다"고 하면 무승부가
된다. **진짜 승부는 그 위의 +5.2%p(내용 검증)와 파인튜닝 워커**에서 난다.

**Q. 왜 D6의 13개 모델은 전부 졌는데 이건 될 거라고 보나?**
A. D6 모델들은 질문 텍스트만 봤고, 거기엔 답이 없다는 게 D6의 결론이다. D7은
워커가 낸 답과 SQL, 그리고 **지금 눈앞의 DB를 직접 확인한 증거**를 본다. "한 DB에서
배운 게 다른 DB로 전이 안 된다"는 병목은, 애초에 전이가 필요 없는(그때그때 재는)
피처를 쓰면 사라진다. 그 방향이 맞다는 실측 증거가 4.1이다(억울한 갈아타기 0건).

**Q. 돈/자원은 얼마나 드나?**
A. 로컬 단계(4.1~4.2, 4.4)는 국내 모델 API 호출 비용뿐이다(3,000문항 × 3워커
재캡처 + 홀드아웃 라벨링). A100은 검증기(1장 몇 분)와 파인튜닝(2~3장 며칠)에
쓴다. **A100 크레딧이 ~7/31 만료**이므로 파인튜닝을 하려면 그 전에.

**Q. 실험이 회사 서비스(운영 DB)에 영향을 주나?**
A. 없다. 전용 격리 DB(`orthus_company_0706`, 2026-07-06 스냅샷 복원본)만 쓰고,
모든 질의는 읽기 전용이다. 프로덕션 코드도 건드리지 않는다.
