## 0. 한 줄 결론

**"실행해 보고 결정론 신호로 다시 묻는" 캐스케이드가 (b) 규칙표를 골든에서 +1문항(→오라클
100%), 합성 hard 분포에서 +3.6%p(86.4→90.0%, 오라클 90.9%의 99%)만큼 이긴다. 비용은 평균
호출 1.05×, 손실 0, LLM 판단 0회.** 반면 다수결 투표는 비용이 2.15×인데 정확도는 더 낮다
(89.1%) — **상관 오류(오답 수렴)에 취약**하기 때문이다.

| 구성 | 골든 18 | 합성 test 110 | 평균 호출 | 손실 |
|---|---|---|---|---|
| (b) static 규칙 (현 채택안) | 17/18 = 94.4% | 95/110 = 86.4% | 1.00× | — |
| (d1) 투표 2-of-3 | 18/18 = 100% | 98/110 = 89.1% | 2.15× | 0 |
| **(d2) 캐스케이드 solar→exaone** | **18/18 = 100%** | **99/110 = 90.0%** | **1.05×** | **0** |
| oracle (이론 상한) | 18/18 = 100% | 100/110 = 90.9% | — | — |
| *(c) 학습 선택기 (G3 기각)* | *92.3%* | *87.3%\** | *2.00×* | — |

\* (c)의 87.3%는 **구 라벨** 기준이라 직접 비교 불가 — §5 드리프트 참조. 위 (a)/(b)/(d)/oracle은
전부 **같은 신선 라벨** 위에서 내부 일관되게 재계산했다.

## 1. Phase A — 오류 비상관 실측 (신규 LLM 콜 0회)

G3의 F8("골든에선 static이 이미 오라클")이 역으로 남긴 사실을 정면으로 쟀다.

**쌍별 오답 상관 = 완전 비상관.**

| 쌍 | 공통 오답 / 합집합 | Jaccard |
|---|---|---|
| solar ∩ ax | 0 / 5 | **0.00** |
| solar ∩ exaone | 0 / 2 | **0.00** |
| ax ∩ exaone | 0 / 5 | **0.00** |

골든 18문항 중 **2개 이상 모델이 동시에 틀린 문항은 0개**다(전원 정답 12 / 1개만 오답 6).
오라클 100%의 정체가 이것이다 — 세 모델은 **서로 다른 문항에서 틀린다.**

→ **H-E1a 지지의 전제 확보.** 앙상블(투표/캐스케이드)이 원리적으로 먹을 파이가 실재한다.

## 2. 캐스케이드 — 결정론 트리거 4종

`gate_fail`(sqlglot 게이트 실패) · `not_executed` · `empty_rows`(0행) · `zero_answer`(결과
number-set == `{0}`). **전부 결정론 신호이며 모델 confidence를 보지 않는다** — 절대룰
(confidence routing 금지) 정합, P3 policy gate 철학("결정은 결정론 코드가")의 연장.

**골든에서 회수한 유일 문항 t3-13** (정답 28 = 회사 미팅 기록 전체 건수):

```
solar   → SELECT COUNT(*) … WHERE db_name='회사 미팅 기록'
                            AND properties->>'미팅 기록' IS NOT NULL   → [[0]]  ✗
          (존재하지 않는 컬럼 '미팅 기록'에 유령 필터 → 0)
exaone  → SELECT COUNT(*) … WHERE db_name='회사 미팅 기록'             → [[28]] ✓
```

유효한 SQL로 **자신 있게 0을 반환**하는 S8과 같은 실패 모드다. `zero_answer` 트리거가
이것을 결정론으로 잡아낸다.

**캐스케이드 일반화 검사 — 1차 모델을 바꿔가며 (골든 18):**

| 1차 | 2차 | 단독 | 캐스케이드 | 발동 | 회수 | 손실 |
|---|---|---|---|---|---|---|
| solar | exaone | 17/18 | **18/18** | 1 | 1 | 0 |
| ax | solar | 14/18 | 15/18 | 1 | 1 | 0 |
| exaone | solar | 17/18 | 17/18 | **0** | 0 | 0 |
| **baseline (현행 gpt-4o-mini)** | solar | 14/18 | **18/18** | 4 | 4 | 0 |
| **baseline** | exaone | 14/18 | **18/18** | 4 | 4 | 0 |

**F-E1f — 캐스케이드는 "실패 모드가 검출 가능한 1차"에서만 작동한다.** exaone의 유일 오답
(t3-03: 부분 집계 누락)과 ax의 오답 3건(t3-10/15/r09: GROUP BY 과분해로 *그럴듯한 숫자*를 반환)은
어떤 트리거에도 안 걸리는 **"확신에 찬 오답"** 이다. solar가 1차로 적합한 이유는 정확도(94%)만이
아니라 **잔여 오답의 성격이 검출 가능한 zero형**이기 때문이다. 이건 배정 근거를 정확도 한 축에서
"정확도 × 실패모드 검출가능성" 두 축으로 넓힌다.

**★ 부수 발견 (제품 관점에서 가장 실용적):** **현행 gpt-4o-mini를 1차로 두고 국내 모델을 안전망으로만
붙여도 14/18 → 18/18(오라클)** 이다. baseline의 오답 4건이 **전부** 트리거 검출 가능형
(zero 1 / empty 2 / gate_fail 1)이기 때문이다. 모델을 갈아치우지 않고도 국산 모델 도입 이득을
얻는 **최저 리스크 채택 경로** — 호출 1.22×, 미측정 노출 0.

## 3. Phase B — 합성 hard 분포 실측 (신규 189 + 189 + 84콜)

**왜 재실행이 필요했나:** `labels_*.jsonl`은 정오(bool)와 status만 저장하고 **rows를 버렸다.**
골든에서 회수를 만든 트리거가 `zero_answer`(number-set 검사)라 rows 없이는 재현 불가 →
합성 test structured 63문항 × 3워커를 재실행해 rows를 확보했다. 합성 test는 **(c)가 (b)를
이겼던 유일한 분포**라 E1의 진짜 판정이 여기서 난다.

| 구성 | 정답 | 정답률 | 호출 |
|---|---|---|---|
| (a) 단일 solar | 95/110 | 86.4% | 1.00× |
| (a) 단일 ax | 93/110 | 84.5% | 1.00× |
| (a) 단일 exaone | 96/110 | 87.3% | 1.00× |
| (b) static 규칙 | 95/110 | 86.4% | 1.00× |
| (d1) 투표 2-of-3 | 98/110 | 89.1% | 2.15× |
| **(d2) 캐스케이드 solar→exaone** | **99/110** | **90.0%** | **1.05×** |
| oracle | 100/110 | 90.9% | — |

캐스케이드 발동 5/63 = 7.9%, 회수 4, **손실 0**. 오라클(100)까지 **1문항** 남는다.

**태그별 — hard 유형에서도 작동하는가**

| tag | n | solar | 투표 | 캐스케이드 | oracle |
|---|---|---|---|---|---|
| filter | 32 | 26 | 28 | **29** | 30 |
| groupby | 14 | 13 | 14 | 14 | 14 |
| count | 13 | 7 | 7 | 7 | 7 |
| ambig | 4 | 3 | 3 | 3 | 3 |

이득은 `filter`형(유령 필터 → 0행)에 집중된다 — 트리거 설계(§2)와 정확히 일치하는 기전이다.
`count`/`ambig`형의 오답은 오라클도 못 넘는(전원 오답) 문항이라 어떤 앙상블도 못 건드린다.

## 4. ★★★ F-E1c — 다수결은 상관 오류에 지고, 캐스케이드는 면역이다

골든에서 오답 수렴은 0/18이었지만(2개 이상 틀린 문항 자체가 없음), **합성 hard 분포에서는
7/63문항에서 2개 이상 모델이 같은 오답 number-set에 합의**했다(그중 2건은 3모델 전원 합의).

결정적 사례 **g1-0616**:
- solar + ax가 **같은 오답**에 수렴 → 다수결이 그 오답을 "확정"한다.
- 그런데 solar의 그 답은 `zero_answer` 트리거에 걸린다 → 캐스케이드는 exaone(정답)으로 회수.

**투표는 "누가 인기 있나"를 묻고, 캐스케이드는 "이 답이 망가져 보이나"를 묻는다.** 후자는 다수와
무관하므로 상관 오류에 면역이다. 이것이 투표(89.1% @ 2.15×)가 캐스케이드(90.0% @ 1.05×)에
**정확도·비용 양쪽에서 지는** 이유다.

## 5. ★★ F-E1d / F-E1e — 재현성 함정 두 가지 (국내 API 채택 실무 교훈)

### TS15 — 세 모델 모두 `temperature=0`에서 비결정적이다

같은 63문항을 연속 2회 실행한 자기일치도:

| 모델 | SQL 완전 동일 | 정오 동일 | 1회차 → 2회차 |
|---|---|---|---|
| solar | 47/63 (74.6%) | **63/63** | 49 → 49 |
| ax | 29/63 (46.0%) | 53/63 | 47 → 47 |
| exaone | 48/63 (76.2%) | 60/63 | 50 → 51 |

`temperature=0`을 보냈음에도 **동일 SQL 재현율이 46~76%** 다. solar는 SQL이 흔들려도 정오가
완벽히 안정적(63/63)인 반면, **ax는 정오까지 10/63 흔들린다.** → 국내 관리형 API에서
`temperature=0`은 결정성을 보장하지 않는다(서빙 스택의 배치/커널 비결정성). 단일 측정으로
모델을 비교하면 그 자체가 노이즈에 오염된다.

**부수적 함의:** 이 비결정성은 캐스케이드의 근거를 오히려 강화한다 — 같은 질문이 언제든
"망가진 답"을 낼 수 있으므로, 실행 후 결정론 검증이 정적 배정보다 안전하다.

### TS16 — EXAONE 합성 라벨이 스테일이다 ((c) 학습 입력 품질 한계)

같은 63문항에서 exaone structured 정오: **구 라벨 32/63(50.8%) → 재실행 50·51/63(79.4·81.0%).**
run-to-run 잡음(3/63 ≈ 5%)으로 설명 불가한 **18문항 체계적 이동**이며, 그중 15건은
`executed → executed`(실행은 됐는데 답이 달라짐)라 status 오류로도 설명되지 않는다.
**골든 t3는 안정적**(재실행 드리프트 solar 0 / ax 1 / exaone 1)이라 서비스 전체 장애가 아니라
**dedicated 엔드포인트 상태 변화**로 추정된다(원인 특정 불가).

**함의(정직성):** (c) 학습 선택기가 학습한 정오 벡터의 **exaone 열이 실제보다 열등하게 라벨링**돼
있었다 → G2/G3의 학습 입력 품질 한계로 기록해야 한다. **단 G3의 기각 결론(= (b)로 충분)은
"골든 헤드룸이 구조적으로 0"이라는 골든 기반 논거였고 골든은 안정적이므로 결론 자체는 유지된다.**
(오히려 exaone이 실제로 더 강했다면 오라클 헤드룸은 더 좁아지므로 기각 방향이 강화된다.)

## 6. 판정 — 사전 고정 기준(§5) 대조

| 기준 | 요구 | 투표 | 캐스케이드 |
|---|---|---|---|
| 골든 ≥ (b)+1문항 | +1 | ✅ +1 (18/18) | ✅ +1 (18/18) |
| 합성 test ≥ 87.3% | 87.3% | ✅ 89.1% | ✅ **90.0%** |
| 손실 0 | 0 | ✅ 0 | ✅ 0 |
| 호출 예산 | 투표 ≤3× / 캐스 ≤1.3× | ✅ 2.15× | ✅ **1.05×** |
| p95 지연 ≤ 단일 2배 | — | ✅ (병렬 시 max) | ✅ (7.9%만 2콜) |

**→ 둘 다 채택 기준을 통과하나, 캐스케이드가 모든 축에서 투표를 지배한다(정확도 ↑, 비용 ½, 상관
오류 면역). 최종 채택 = 캐스케이드. 투표는 미채택(비용 대비 열위)으로 기록.**

## 7. 산출물 — 배포 가능 규칙 (LLM 판단 0회)

```
1차: (b) 배정 모델로 실행                      … solar
검증: sqlglot 게이트 통과 & 실행됨 & 0행 아님 & 결과 number-set ≠ {0}
     └ 통과 → 그대로 답한다                    … 92.1%의 문항 (호출 1×)
     └ 실패 → 2차 모델 재실행                  … exaone
              └ 2차가 non-empty → 2차 채택
              └ 2차도 empty/zero → 1차 유지 (진짜 0인 답을 보존)
```

- **평균 호출 1.05×** (합성 실측 발동률 7.9%; 골든 전 28문항 기준 1.29×).
- **LLM 콜 추가는 발동 시에만**, 선택기 추론은 0회 — (c)가 매 호출마다 추가하던 선택기 추론
  비용이 없다.
- **모델 confidence 미사용** — 전부 결정론 신호. 절대룰(confidence routing 금지) 정합.
- 기존 (b) 규칙표(§6.6)를 **대체하지 않고 그 위에 얹는다**: 배정은 그대로, 검증만 추가.

## 8. 한계 (정직성)

- **미측정 노출 1건.** solar 1차 캐스케이드는 골든 전 28문항 중 8회 발동하는데, 그중 6회는
  2차도 empty라 무해 확인, 1회는 실측 회수(t3-13), **1회(t3-r05)는 채점 불가 문항이라 교체
  결과의 정오를 알 수 없다.** baseline 1차에서는 미측정 노출 0.
- **"진짜 정답이 0"인 질문에서의 오발동은 이 코퍼스에서 검증 불가** — 골든 채점 18문항 중 gold에
  0이 포함된 문항이 **0개**라 반례 자체가 없다. §7의 "2차도 empty면 1차 유지" 규칙이 구조적
  방어지만, 정답이 0인 문항이 흔한 코퍼스에서는 재측정이 필요하다.
- **캐스케이드의 구조적 한계:** 트리거 미발동 오답("확신에 찬 오답")이 합성에서 9/63 남는다.
  이건 앙상블이 아니라 **답의 정합성 검증**(예: 결과 자릿수/스키마 sanity)이 필요한 영역 —
  E1 스코프 밖.
- **표본:** 골든 채점 가능 18문항, 합성 structured 63문항. 골든 이득은 1문항이라 통계 검정
  불가 — 합성 63(회수 4, 손실 0)과 **2회 독립 재실행에서 동일 재현**이 견고성의 근거다.
- **routing에는 미적용** — 규칙(ax) = 오라클이라 헤드룸 0(보고서 §6.5). E1은 DB질의 전용.

## 10. 인사이트 — 이 실험이 의미 있는 이유

### 10.1 ★★★ 예측 문제를 검증 문제로 바꿨다

(b) 규칙과 (c) 학습은 겉보기에 다르지만 **같은 질문**을 푼다: *"이 질문은 누가 잘 풀까?"* —
**예측**이다. 그리고 G3가 보여줬듯 **그 예측 문제는 이미 풀려 있었다**(규칙 = 오라클, 헤드룸 1문항).
더 정교한 예측기를 만들 여지가 구조적으로 없었다.

E1은 다른 질문을 던졌다: *"이 답이 틀렸는지 알아볼 수 있나?"* — **검증**이다.

> **정답을 만드는 것보다 틀린 답을 알아보는 것이 훨씬 쉽다.**
> 어떤 SQL이 맞는지 맞히려면 스키마·의도·데이터를 다 이해해야 한다. 그런데 **결과가 `0`이거나
> 비어 있으면** 이해 없이도 알아볼 수 있다. 유효한 SQL이 아무것도 못 찾았다는 건 대개 **모델이
> 없는 컬럼을 지어냈다**는 뜻이지, 진짜 답이 0이라는 뜻이 아니다.

이 비대칭이 결과의 전부다. 예측(선택기)은 A100·학습·상시 추론비를 쓰고도 졌고, 검증은 **if문 네
줄**로 오라클에 닿았다. **이것이 E1이 D5(학습 선택기)보다 값싸면서 더 큰 이득을 낸 이유다.**

### 10.2 ★★ 안전 장치가 품질 장치였다 (orthus 고유의 자산)

이 방법이 **공짜**인 이유는 orthus가 이미 **결정론 검증기**를 갖고 있기 때문이다 — sqlglot 게이트 +
실DB 실행. 그런데 그건 원래 **품질이 아니라 안전**을 위해 만든 것이다(설계원칙 1·4: "LLM이 SQL을
실행하게 두지 않는다").

**즉 안전을 위해 만든 장치가 품질 신호로도 작동한다.** 대부분의 LLM 앱은 이 검증기가 없어서
test-time compute를 하려면 "LLM judge"나 "self-consistency" 같은 **비싸고 불확실한** 대체물을 쓴다.
orthus는 **실행 결과라는 ground truth에 가까운 신호**를 이미 손에 쥐고 있었고, 그걸 안 쓰고 있었을
뿐이다.

→ **일반화: 자기 시스템에 이미 있는 결정론 검증기(스키마 검증, 실행 성공 여부, 결과 sanity)를 품질
신호로 재활용하는 것이 test-time compute를 가장 싸게 도입하는 길이다.**

### 10.3 ★★ 다수결의 통념을 데이터로 반박했다

"여러 모델에 물어보고 다수결"은 앙상블의 상식인데, **우리 데이터에서 그 상식은 졌다**(89.1% @ 2.15×
vs 캐스케이드 90.0% @ 1.05×). 이유는 **오답 수렴** — 합성 63문항 중 7문항에서 2개 이상 모델이 *똑같은
오답*에 합의했고(3모델 전원 2건), 다수결은 그 오답을 확정한다.

**차이의 본질은 묻는 질문이다.** 투표는 *"누가 인기 있나"*(모델 간 합의 = 상대적)를 묻고, 캐스케이드는
*"이 답이 망가져 보이나"*(답 자체의 속성 = 절대적)를 묻는다. **후자는 다수와 무관하므로 상관 오류에
구조적으로 면역**이다.

> **골든만 봤다면 놓쳤다.** 골든 18문항의 오답 수렴은 **0건**이라 "투표는 안전하다"는 결론이 나올
> 뻔했다. 어려운 분포에서 실측하고서야 위험이 드러났다 — **결론을 내기 전에 분포를 바꿔 보라**는
> 보고서 §9.5의 재확인.

### 10.4 ★ 모델 선택의 두 번째 축 — "실패가 검출 가능한가"

캐스케이드가 작동하려면 **1차 모델의 잔여 오답이 검출 가능한 종류**여야 한다.

| 1차 | 정확도 | 잔여 오답의 성격 | 캐스케이드 결과 |
|---|---|---|---|
| **Solar** | 94.4% | **`0` 반환 (시끄러움)** | 17 → **18/18** ✅ |
| EXAONE | 94.4% | 부분 집계 누락 (조용함) | 17 → 17/18 — **트리거 미발동** |
| baseline | 77.8% | **전부 zero/empty/gate_fail** | 14 → **18/18** ✅ |

**정확도가 같은 94.4%인데 캐스케이드 성패가 갈린다.** → **"정확도"만으로 1차를 고르면 안 된다 —
정확도 × 실패모드 검출가능성이다.** 이건 배정 규칙표(§6.6)의 근거를 한 축 넓히는 발견이다.

### 10.5 ★ 트러블슈팅이 곧 발견이었다

E1의 헤드라인 3개 중 **2개(TS15 비결정성, TS16 라벨 드리프트)가 가설 검정이 아니라 "재현이 안 되는데
왜지?"를 파고든 데서 나왔다.** 노이즈로 치부했다면 둘 다 없었다. 그리고 실제 지출을 보면 —
**462콜 중 273콜(59%)이 "이 측정을 믿을 수 있는가"를 검증하는 데** 들어갔다(순수 판정은 오프라인 0콜).
**평가 인프라가 곧 실험의 일부**라는 §9.6의 재확인이다.

## 11. 제품 적용 — 현재 구조를 어떻게 바꿀 것인가

> **📄 정식 설계 문서는 옆에 있다: `structured-verification-cascade.md` (SVC, 같은 디렉토리).**
> 본 절은 **요약**이고, 계약·절대룰 정합·대안 비교·마일스톤/게이트는 그 문서가 SoR이다.
> 구현으로 진행하기로 하면 **main 기반 워크트리 + 일반 PR**로 옮겨 작업한다(실험 격리 유지).
>
> **전제:** 아래는 **국내 모델 도입과 무관하게** 성립한다. 캐스케이드가 요구하는 것은 "국산 모델"이
> 아니라 **오류가 비상관인 두 번째 모델**뿐이다. baseline(gpt-4o-mini) 1차 실험이 이를 보여준다.

### 11.1 현재 구조의 한계 (실측된 것)

orthus의 DB질의는 `orthus/structured/query.py::_query_structured`에서 **단 한 번** 컴파일·검증·실행하고
끝난다. 검증 게이트(`assistant/validate.py`)는 **"유효하지 않은 SQL"은 막지만 "유효한데 틀린 SQL"은
그대로 통과시킨다** — 그리고 그 통과분이 사용자에게 **숫자 하나로, 확신에 차서** 전달된다.

실측된 피해: **현행 운영 모델(gpt-4o-mini)이 골든 DB질의 18문항 중 4문항을 틀리는데, 그 4문항이
전부 `0`/빈 결과/게이트 실패**다. 즉 **"틀렸다는 신호를 시스템이 이미 손에 쥐고 있으면서 버리고
있다."**

### 11.2 제안 — `structured` 경로에 결정론 재질의 한 층 (최소 변경)

**핵심 변경 1곳:** `orthus/structured/query.py::query_structured`(:268) — 기존 `_query_structured`를
감싸는 얇은 재시도 층. **컴파일/검증/실행 로직(`_query_structured` 본문)은 한 줄도 안 건드린다.**

```python
def query_structured(user_id, question, *, scope="all", project=None, chat_model=None):
    query_id = uuid.uuid4()
    with audit("assistant.run", correlation_id=query_id):
        first = _query_structured(query_id, user_id, question, scope, project, chat_model)

        # ── 결정론 재질의. flag off / 트리거 미발동이면 즉시 return → 기존 동작 byte-identical
        trigger = _retry_signal(first)      # gate_fail | not_executed | empty_rows | zero_answer
        fallback = get_fallback_chat_model()          # 미설정이면 None
        if trigger is None or fallback is None or chat_model is not None:
            return first                              # chat_model 명시 주입(실험/테스트)은 불개입

        with audit("structured.fallback") as span:
            second = _query_structured(uuid.uuid4(), user_id, question, scope, project, fallback)
            # 2차도 비어 있으면 "진짜 0"으로 보고 1차 유지 (오발동 방어 — §8 한계 대응)
            adopted = _retry_signal(second) is None
            span.add_meta(trigger=trigger, adopted=adopted,
                          primary=..., fallback=fallback.model_id)
        return second if adopted else first
```

필요한 신규 조각은 **셋뿐**이다:

| 조각 | 위치 | 내용 |
|---|---|---|
| `_retry_signal(result)` | `structured/query.py` | 순수 함수. `not validation.passed` / `status != "executed"` / `row_count == 0` / 결과 정수집합 == `{0}`. **모델 confidence를 보지 않는다** |
| `get_fallback_chat_model()` | `models/registry.py` | 현행 `get_chat_model()`(:46)은 **인자를 받지 않는 단일 슬롯**이다. 그 구조를 깨지 않고 **선택적 형제 함수**를 추가 — 미설정이면 `None` 반환(fail-closed) |
| `llm_fallback_model` | `settings.py` | `ORTHUS_LLM_FALLBACK_MODEL`. **미설정 = 기능 off**(현재 설정에 존재하지 않음 = 신규) |

감사는 `audit("structured.fallback")` 스팬에 `trigger`/`adopted`/`primary`/`fallback`을 기록한다
(설계원칙 3). **새 테이블 불필요** — 기존 `query_runs.result_meta`로 충분하다.

### 11.3 절대룰 정합성 (PR이 거부되지 않을 근거)

| 룰 | 정합 여부 |
|---|---|
| **confidence routing 금지** | ✅ 트리거는 **실행 결과의 결정론 속성**(게이트 통과·행 수·결과 숫자)이지 모델 확신도가 아니다. LLM 판단 0회 |
| **검증 게이트 우회 금지** | ✅ 2차 SQL도 **동일 게이트를 그대로 통과**해야 실행된다. 우회 경로 없음 |
| **LLM-only 실행 금지** | ✅ 채택 여부를 결정론 코드가 정한다(P3 policy gate 철학의 연장) |
| **read-only** | ✅ 재시도도 `SELECT` 전용 · `orthus_ro` 롤 |
| **감사** | ✅ 호출 단위 `audit()` 스팬 추가 |

→ **"LLM은 초안을 만들고, 실행 안전은 typed guard가 통제한다"**(설계원칙 1)에 정확히 부합한다.
이번엔 그 guard가 **안전에 더해 품질까지** 통제한다.

### 11.4 단계적 채택 경로 (리스크 순)

| 단계 | 내용 | 기대 효과 (실측 기반) | 리스크 |
|---|---|---|---|

(+22.2%p). 조직 내 "모델 교체" 논쟁을 우회한다.

### 11.5 적용되지 않는 곳 (경계 명시)

- **지식응답(wiki QA)** — 결정론 검증기가 없다. "답이 비었는가" 정도는 되지만 "답이 틀렸는가"는
  판정 불가. 여기에 같은 방법을 쓰려면 LLM judge가 필요한데, 그건 비싸고 E4가 보여줄 편향 문제를
  안는다. **E1의 결론을 여기로 확대 적용하면 안 된다.**
- **라우팅** — 규칙 = 오라클(헤드룸 0). 재질의할 이유가 없다.
- **"정답이 진짜 0인 질문"이 흔한 코퍼스** — §8의 미측정 리스크. `_retry_signal`의 `zero_answer`
  항목만 끄고(`empty_rows`/`gate_fail`만 유지) 쓰는 보수적 변형이 가능하다.

### 11.6 후속 측정이 필요한 것

1. **프로덕션 분포에서 트리거 발동률** — 실험 코퍼스에서 7.9%(합성)~28.6%(골든 전 28문항)로 폭이 크다.
   실사용 질문에서 몇 %가 발동하는지가 **곧 추가 비용**이다. `audit("structured.fallback")` 스팬을
   먼저 **관측 전용(shadow mode: 트리거만 기록, 재질의 안 함)** 으로 1~2주 돌려 보는 것을 권한다.
2. **"정답이 0"인 질문의 실제 빈도** — shadow mode의 발동 로그를 사람이 스팟체크하면 바로 나온다.
3. **2차 모델 선정** — 오류 비상관이 핵심이므로 **같은 벤더의 더 큰 모델보다 다른 벤더**가 유리할
   가능성이 높다(실험은 교차 벤더만 측정했다). 이건 shadow mode 로그로 저렴하게 비교 가능하다.
