## 1. 지금까지의 발견은 **탐색(exploratory)이지 증거가 아니다**

2026-07-16에 나온 아래 수치는 **동결 홀드아웃 463을 들여다본 뒤** 만든 규칙을 **그 똑같은
463에서** 잰 것이다. 가설의 출처로는 정당하나 **승리 근거로는 무효**다.

| 탐색 결과 (무효 — 가설 출처로만) | 수치 |
|---|---|
| solar 오답 180 중 degenerate(에러/빈답) | 46 |
| null 폴백(에러/빈/0) 정책 | 61.1% → 65.0% (+3.9p, 18득/0실, p=1e-5) |
| 결정론 SQL 수리(GROUP BY 제거) | t3u-129 실증 1건 ([1] → [11] 정답) |

### 1.1 자백 — 이 판은 나에게 유리하게 기울어 있다

1. **시험지를 보고 규칙을 만들었다.** 오답 24개를 열어보고 패턴을 찾았다 = 테스트셋 개발.
2. **"결과 0 = 무조건 오답"은 이 벤치마크의 구멍이다.** gold에 0이 없는 것은 실력이 아니라
   **생성기 버릇**(필터 값을 DB 실재값에서만 뽑음). 현실에서 "핫픽스인 업무 몇 개?"의 정답은
   정당하게 0일 수 있다(실측: `협업업무표.상태='핫픽스'`는 DB에 0건). 이 규칙은 프로덕션에
   내보내면 **해롭다**.
3. **상대(규칙기)가 약체다.** D6 챔피언은 "무조건 solar"(60.5%)뿐인데, 내가 만든 폴백·수리도
   전부 규칙이다. 이걸 학습기 쪽에 넣고 약한 규칙기와 비교하면 그게 rigging이다.
4. **홀드아웃이 학습셋과 같은 질문 템플릿을 쓴다**(`build_unseen_v2.py`가 `gen2.gen_items`
   재사용). 파인튜닝 모델이 표현만 외워도 이긴다.

→ §2~§5가 이 넷을 각각 막는다.

### 1.2 구조적 승부처 — 규칙이 근본적으로 못 가는 땅 (2026-07-16 실측)

동결 홀드아웃 463 분석(탐색용, 승리근거 아님):

| 구획 | 비율 | 누가 잡을 수 있나 |
|---|---|---|
| oracle (세 워커 중 하나라도 정답) | 68.0% | 고르기·투표의 **천장** |
| **세 워커 전부 오답** | **32.0% (148문항)** | 고르기·투표로는 **영원히 0%**. 더 나은 SQL을 쓰는 **워커(SFT)만** 도달 |

- 148 all-wrong은 **15개 근본원인**(47개 고유 (db,필터값))으로 뭉친다. 예: `'직원'`(6행)
  vs `'직원 '`(공백 18행) 혼동 — 정답 18인데 세 워커가 전부 공백을 무시.
- **양날:** 15종이면 내가 규칙으로 다 적을 수 있다(→R+ 승) **그러나** 근본원인은 *종류(class)*를
  이룬다(공백DB 혼동·엉뚱컬럼·IN쪼개기·유령필터…). 규칙은 **본 인스턴스만**, 학습기는 그
  *종류를 배워* 새 DB의 **못 본 인스턴스**로 일반화할 수 있다.
- **∴ 정정당당한 승부처 = 새 DB의 "학습셋에 없던 근본원인".** R+는 학습셋 15종만 안다.
  fresh 셋의 새 함정을 학습기가 "고침의 종류" 일반화로 잡고 R+가 놓치면 = **규칙으로는 못 하는
  정당한 승리.** 매번 완전히 새로우면(전이 실패) 둘 다 지고 oracle이 답 — 그것도 정직한 결과다.

**주력 학습기 = SFT 워커(c2, §4).** 검증기(c1)는 R+와 같은 신호로 정면승부라 tie 위험이
크다(신호 대부분이 hand-codable). SFT 워커는 oracle 천장(68%)에 묶이지 않는 **유일한** 접근이라
이 32% 땅의 구조적 주인이다.

## 3. 상대 = R+ (강화된 규칙기). **내가 만든 규칙은 전부 상대에게 준다.**

R+ = 다음을 **전부 장착한** 결정론 시스템. 학습 0회.

```text
R0  always solar (single call)                     (D6 챔피언)
R1  + 자기일관성: solar k=5 재실행 → 실행결과 다수결 (파일럿 실측 +8.7p, 학습 아님)
R2  + null 폴백: 다수결 답이 에러/빈/{0} → ax → exaone
R3  + SQL 수리: 총계질문 + GROUP BY → GROUP BY 제거 후 재실행 (repair.py)
R4  + SQL 수리: 총계질문 + 군더더기 NOT NULL → 제거 후 재실행
R5  + 학습셋 파일럿에서 발견되는 **모든** 결정론 신호/수리 (§5에서 동결)
```

자기일관성(R1)은 학습이 아니라 추론시점 일반 기법이라 **상대(R+)에 준다** — 학습기는 78%대의
강한 R+를 이겨야 한다. 이게 정정당당함의 핵심이다(§0).

**규칙:** 학습셋 파일럿에서 내가 새 실패 모드를 발견하면 **먼저 R+에 규칙으로 넣는다.**
학습기 전용으로 남겨두지 않는다. R+는 "인간이 성실히 규칙을 짰을 때의 최선"이어야 한다.

**보고 의무:** 최종 표에 R0~R5·oracle을 **전부** 싣는다. 학습기를 R0(약체)하고만
비교하지 않는다. 승리 판정의 상대는 항상 **R+(=R5, 최강)**이다.

## 4. 학습기 (c) — 사전 고정

**c2. SFT 워커 (주력 — §1.2 구조적 승부처의 유일한 주인).** EXAONE-4.0을
(스키마+질문 → 정답 SQL)로 파인튜닝해 **4번째 워커**를 만든다. R+의 selection/repair가
근본적으로 못 가는 all-wrong 32%를, 더 나은 SQL 생성으로 회수한다(oracle 천장에 안 묶임).
학습 타깃 = 학습셋에서 **정답을 낸 워커의 SQL**(없으면 spec에서 결정론 생성한 canonical SQL).
스키마는 프롬프트에 제시(새 DB 대응). 판정 = §2 fresh 셋(신규 표현이라 템플릿 암기 무효,
신규 DB라 값 암기 무효). 32B QLoRA 또는 소형 full FT — 백본은 학습셋 val로 고르고 동결.

**c1. 실행증거 검증기 (보조).** 입력 = (질문, SQL, 실행결과, 결정론 probe 피처). 출력 =
후보가 맞을 확률. c2 SFT 워커까지 후보에 포함(solar → 수리안 → SFT → ax → exaone). 검증기가
현 채택안을 기각하고 다른 후보를 margin τ 이상으로 통과시킬 때만 교체(τ는 **학습셋 val에서만**
튜닝 후 동결). c1은 R+와 같은 신호로 겹치므로 tie 위험 — **주 승리 주장은 c2**, c1은 c2 위에
얹는 추가 회수분으로 본다.

**probe 피처는 라이브 DB에서 측정** (읽기전용 `SELECT`/`EXISTS`만). 학습 DB에서 외운 상수
금지 — 그게 D6 피처주입(①)이 −1.5p로 해로웠던 이유다.

## 6. 승리 판정 기준 (사전 고정 — 사후 변경 금지)

**주가설 H1:** `c2(SFT 워커 포함 시스템) > R+` (같은 fresh 판정셋, 같은 채점).

**동시에 전부** 충족해야 "이겼다"라고 쓴다:

| # | 기준 |
|---|---|
| 1 | **McNemar p < 0.05** (c1 vs **R+**, R0 아님) |
| 2 | **부트스트랩 10,000회 P(c1 > R+) > 95%** |
| 3 | **재현**: 독립 fresh 셋에서 1·2를 다시 통과 |
| 4 | **정답 0 문항 슬라이스에서 c1이 R+ 대비 유의하게 나쁘지 않음**(비열등) |
| 5 | 단일 답만 인정 — 여러 후보 답 union 금지(D6 §3.5 recall artifact) |
| 6 | 추론 중 gold 미접근, DB는 읽기전용 SELECT만 |

**하나라도 실패 → "D6 결론 유지: 규칙이면 충분"으로 보고한다.**

**부가 보고(승패와 무관하게 반드시 싣는다):** R0→R1→R2→R3→R4 각 단계의 기여도.
"학습기 +Xp" 옆에 "그중 규칙으로 얻은 몫 Yp"를 나란히 적는다.

## 8. 예상되는 반박과 답 (미리 적어둔다)

```text
     + db_name 스냅 (c2와 동일 글루를 규칙기에도 동등 제공)
     + null 폴백(→ax→exaone)
     + 결정론 SQL 수리 2종(repair.py: 총계질문 GROUP BY 제거 · 군더더기 NOT NULL 제거)
보고 시 R0(solar 단독)~R+ 사다리 전 단계 병기.
```

### 10.3 fresh 판정셋 (`golden/t3_fresh_holdout.json` — 본 명세 확정 후 생성)

| 항목 | 값 |
|---|---|
| DB | 학습 6종·구홀드아웃 6종과 무겹침: **미사용 실DB(≥3행) 최대 8종 + 합성 2종**(워크스페이스 버릇 반영 — 끝공백·이모지 명칭, 합성임을 명시; 격리 DB에 삽입) |
| 질문 표현 | **신규 템플릿만**(T_COUNT_F/T_FLT_F/T_GB_F/T_AMBIG_F/T_FLT2_F) — 기존 `gen2.T_*` 문장과 템플릿 문자열 중복 0 |
| 규모 | **n ≥ 900** (spec × 패러프레이즈) |
| 정답 0 문항 | **~10%** — DB에 없는 값 필터, gold=[0] (0을 반환해야 정답) |
| gold | spec에서 결정론 실행으로 산출·동결 |
| 워커 GT | 생성 직후 solar(k=5)/ax/exaone 실행 캡처(SQL 포함) → `analysis/raw/fresh_worker_sql.jsonl` 동결 |
| 헤드룸 게이트 | `oracle − R+ < 3%p`면 판정 중단·보고 (§2와 동일) |

### 10.4 본판정 절차

① fresh 생성 → ② 워커 GT+R+ 재료 캡처 → ③ 헤드룸 게이트 → ④ c2 생성(A100) 1회 →
⑤ §6 기준 판정(McNemar p<0.05 ∧ 부트스트랩 P>95% ∧ 정답0 슬라이스 비열등 ∧ 단일 답) →
⑥ 독립 fresh 셋(다른 DB 구성)으로 재현. 실패 시 §9 문안 그대로 보고.
