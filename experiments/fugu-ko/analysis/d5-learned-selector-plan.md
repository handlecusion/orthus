## 0. 무엇을 검증하나 (H3, 정직한 프레이밍)

**H3: 질문 내용까지 보는 학습 선택기(c)가 작업 라벨만 보는 규칙 선택기(b) 대비 품질 추가 이득이 있는가.**

### G0 — 상한(headroom) 실측이 이 계획의 출발점 (2026-07-08 완료)
기존 raw 데이터로 "오라클 선택기"(문항마다 정답 낸 모델을 골랐다고 가정한 이론 상한)를 계산:

| 태스크 | static(b) 최강 | oracle 상한 | headroom |
|---|---|---|---|
| DB질의(18) | 94% (solar) | 100% | **+1문항** (`t3-13`: solar 오답, ax/exaone 정답) |
| 라우팅(21) | 95% (ax) | 95% | **0** (전 모델 공통 오답 1문항) |
| 지식응답(30, 승1/무0.5) | 23.0 (solar) | 25.0 | **+2점** (3문항) |

→ **골든셋 기준 (c)의 품질 상한은 (b)+1~2문항.** 따라서 이 실험의 결론은 두 방향 모두 유효하다:
- (c) > (b): 문항 단위 선택이 실제로 잡힌다 — Fugu (c) 재현.
- (c) ≈ (b): **"우리 도메인에선 규칙 선택기로 충분하다"** — 이것도 논문 대비 가치 있는 실증 결론(부정적 결과의 정직 보고). 단, 이 판정은 골든이 아니라 **합성 test의 불일치(disagreement) 부분집합**에서 내린다(§4) — 골든만으론 표본이 얇아 c≈b가 자명하기 때문.

### 왜 그래도 하는가
1. **논문 (a)/(b)/(c) 3종 세트 완주** — 대회 보고서의 완결성.
2. **일반화**: (b)의 배정은 골든 79문항 실측에 최적화된 규칙. 실사용 분포(새 질문 유형)에서 문항 단위 선택이 강한지 검증하려면 (c)가 필요.
3. **A100 활용 증거**: 지원받은 GPU로 SFT까지 수행하는 스토리.

## 1. 선택기 문제 정의

- **입력**: `(task_label, question_text)` — orthus는 태스크를 이미 알므로(4.2/4.3장) task 조건부 선택은 realizable.
- **출력**: 워커 slug ∈ {solar, ax, exaone}.
- **학습 타깃**: 문항별 **모델별 정답 벡터**(multi-label) → 추론 시 `argmax P(correct)`, 동률이면 static(b) 배정으로 tie-break. (best-model 단일 라벨 분류보다 라벨 노이즈에 강하고, 불일치 문항에서만 신호가 나는 구조를 자연스럽게 반영)
- **배포 형태**: `selectors/learned.py::select(task, question)` — static_map과 동일 인터페이스(코드 레이어, env 아님).

### 학습 대상 태스크 (결정론 채점 가능한 것만)
| 태스크 | 채점 | 학습 포함 |
|---|---|---|
| DB질의(T3형) | 실DB ground-truth (t3_gold 확장) | **포함(주력)** |
| 라우팅(T5형) | 기대 route 일치(구성상 자동) | **포함** |
| 지식응답(T2형) | judge 필요(비용/노이즈) | **학습 제외**, 평가만 |
| 오케 결정(T6/T7/T8) | fast-path 지배 + LLM 도달분 소량 | 제외(D4에서 결론 완료) |

## 2. G1 — 학습 데이터 생성 (~1,000문항, 자동 라벨)

### 생성 (합성 + 실사용 시드)
- **DB질의 ~600**: 실DB(`orthus_company` notion_rows) 스키마에서 프로그램 생성 — {count-single, groupby, 필터, 정렬/limit, 메타} × 실제 DB명/컬럼/값. **이모지·장식 DB명, count vs groupby 모호형 등 D2에서 모델이 갈린 유형을 의도적으로 과표집**(불일치 문항이 학습 신호의 전부이므로). LLM 패러프레이즈로 표현 다양화(생성만, 라벨은 코드).
- **라우팅 ~400**: route별(구조화/지식/그래프) 템플릿 × 실제 엔티티/slug + 실사용 `query_runs` 로그 시드 패러프레이즈.
- **골든 79문항은 학습에 절대 미포함**(정규화 텍스트 dedupe로 누출 차단) — 최종 holdout.

### 라벨 (자동, LLM 판단 없음)
1. 각 문항을 3워커로 실행(orthus 실파이프라인, `chat_model=` 주입).
2. DB질의: 생성 시점에 정답 스펙을 함께 만들었으므로 t3_gold 방식 숫자집합 대조. 라우팅: 기대 route 일치.
3. 산출: `(task, question, correct_solar, correct_ax, correct_exaone)` JSONL.

### 비용/시간
- API ~3,000콜(1,000×3). solar/exaone 무료키 여유, **A.X RPS3 스로틀이 병목**(min_interval 0.4s → 1,000콜 ≈ 수십 분, 재시도 여유 포함 반나절). judge 0콜.
- **G1 게이트**: 생성 후 **불일치율**(모델 간 정답 갈린 문항 비율) 보고. 불일치 < 10%면 hard-type 추가 과표집 1회. 그래도 낮으면 그 자체가 "모델들이 이 도메인에서 수렴 — (b)로 충분" 증거로 보고서에 기록.

## 3. G2 — 선택기 3티어 학습 (A100)

| 티어 | 모델 | 역할 | A100 |
|---|---|---|---|
| ① | TF-IDF + 로지스틱 회귀 | 하한 베이스라인 — "단순 통계로 되는가" | 불필요 |
| ② | KLUE-RoBERTa-base(~110M) fine-tune | 주력 — 한국어 인코더 분류 | 수 분 |
| ③ | 소형 LLM LoRA SFT — **2.4B(EXAONE-3.5-2.4B) + 7.8B(EXAONE-3.5-7.8B) 두 사이즈** | 스트레치 — 지시형 선택 + 스케일 축, A100 활용 증거 | 수십 분 |

- 공통: 입력 `[task] question`, 출력 3-way multi-label(①②) / 지시형 텍스트 라벨(③). split = 합성 70/15/15(train/val/test), 골든은 별도 holdout.
- 티어 간 비교 자체가 보고 소재: "선택기에 얼마짜리 모델이 필요한가." ③을 두 사이즈로 돌리면 이 물음에 **모델 스케일 축**(110M→2.4B→7.8B)이 추가된다.
- **80G 개정(2026-07-12):** GPU가 40G 가정 → **80G 실확인**. 바뀌는 것은 티어③ 상향뿐 — 7.8B LoRA + 여유 batch가 무리 없고, 원래 "또는"이던 후보 선택(§8-①)이 병행 실행으로 해소된다. 병목은 VRAM이 아니라 **데이터(730문항·불일치 160)**이므로 게이트/split/판정 매트릭스는 무변경, 80G는 옵션이지 성능 보장이 아니다.
- ③은 ②가 오라클에 근접하면 축소 가능(과적합 위험 명시 — 소량 데이터 SFT, **7.8B일수록 과적합 리스크가 더 큼**: LoRA rank 낮게 + val 기준 early stopping + 골든 holdout 무손실 수용선 유지).
- **G2 게이트**: 합성 test에서 ② 선택기 정확도가 static 규칙(항상 b 배정) 이상일 것. 미달이면 ③ 진행 전 데이터/피처 재점검.

## 4. G3 — 평가와 H3 판정

세 구성 대조(+오라클 상한): **(a) 최강 단일(solar) / (b) static_map / (c) 학습 선택기 / oracle**.

| 평가셋 | 지표 | 목적 |
|---|---|---|
| 골든 holdout(미학습 79문항) | DB질의 정답률·라우팅 정확도·지식응답 승률* | 기존 표와 직접 비교 |
| 합성 test(15%) | 선택기 정확도, end-to-end 정답률 | 학습 성립 검증 |
| **합성 test 불일치 부분집합** | (c) vs (b) 정답률 | **H3 주판정** — 여기가 (c)의 존재 이유 |

*지식응답은 (c)가 solar 외를 고른 문항만 추가 judge(소량).

**판정 매트릭스** (수용선: 골든에서 (c) ≥ (b) 무손실 필수):
- (c) > (b) [불일치 부분집합 유의 우위] → **H3 지지**: 문항 단위 학습 선택 재현.
- (c) ≈ (b) → **H3 기각·(b) 충분**: "태스크 라벨이 이미 대부분의 신호" — 정직 보고(oracle 근접 G0 근거와 일관).
- (c) < (b) [골든 손실] → 학습 실패 분석(데이터 부족/과적합) 후 1회 재시도, 재실패 시 그대로 보고.

## 7. 리스크와 대안
- **불일치 희소**(가장 큼): 모델들이 합성 문항에서 대부분 동시 정답 → 학습 신호 없음. → hard-type 과표집(이모지 DB명, groupby 모호형 — D2 실측 약점 기반), 그래도 희소하면 "(b) 충분" 결론으로 전환(판정 매트릭스에 내장).
- **합성-실사용 분포 차**: 템플릿 편향. → query_runs 실로그 시드 + LLM 패러프레이즈로 완화, 골든 holdout이 최종 심판.
- **소량 데이터 LLM SFT 과적합**(③): ①② 하한이 있어 해석 가능, ③은 스트레치로 명시. 80G로 7.8B가 가능해졌지만 데이터는 그대로라 **모델 상향 = 과적합 리스크 상향** — 2.4B와 7.8B를 같은 split으로 대조해 스케일 이득이 실재하는지로 판단.
- **A.X RPS3**: 라벨 생성 병목. → 야간 배치, solar/exaone 먼저 병렬.
- **A100 환경**: CUDA/transformers 셋업 리스크 → 7/11 학습 전 day-0 스모크(소배치 1회).
- **누출**: 골든↔합성 dedupe(정규화 텍스트), split 고정 seed.
