# F2 — wiki-빈근거 → structured 결정론 폴백 사전선언 (2026-07-23)

> 상태 **등록(구현·측정 전)**. Metric ⑥ 잔여 routing 실패 9건 대응 — owner 지시 "더 올릴 수 있을까".

## 1. 근거 (측정 완료 사실)

- flow 잔여 routing 실패 9건(B-g2-0001..0009)은 **전 arm(프론티어 포함) 동일 실패**: 집계형 질문
  ("…전체 합계만 세어 줘", 이모지 DB 표면)을 routing LLM이 wiki로 보냈고, wiki 답은 "근거 없음" 공답.
- 코드에는 이미 역방향 회복이 존재한다(C3-a `routing_gate_reject_wiki_recover`: structured
  게이트-리젝 → wiki 재질의, wiki.sources 있을 때만 서빙). F2는 그 대칭이다.
- B1 글루 사다리의 L4(probe-0 + null 폴백)와 동일 패턴 — "공답이 확실할 때만 다른 평면 시도".

## 2. 설계

served wiki 답변의 `sources`가 빈 경우(=근거 0 공답) structured를 시도하고, **sqlglot 검증
게이트 전부 통과(validation.passed)일 때만** structured로 서빙. 게이트 리젝이면 기존 wiki 공답
유지. 플래그 `ORTHUS_ROUTING_WIKI_EMPTY_STRUCTURED_RECOVER` **default false(fail-closed, 현행
byte-identical)**. 비federated 경로만(연합은 후속). TN-환각 방어는 C3-a와 동일 논리의 대칭:
지식형 질문이 잘못 넘어오면 환각 컬럼으로 게이트가 리젝한다.

## 3. 등록 예측

1. flow routing 실패 9건 중 **7건 이상 구제** (t3 골드 기반 집계 질문이므로 게이트 통과 예상).
2. **파손 0**: 기존 pass 플로우(74/84 중 73) 전부 유지 — wiki 근거가 있으면 폴백이 아예 안 열림.
3. t5 라우팅 tier-A 회귀 무변화(분류기 자체는 불변), t3/t6 등 타 작업 회귀 무변화.

## 4. 측정 계획

orchestrator arm(F1 k=3 + F2 on) flow 재실행 + 신규 실패/구제 항목 단위 diff. tier-A 스모크
(t5/t6)로 회귀 확인. prod 활성화는 owner 결정(코드 default off 머지 가능).

## 5. F2 v1 실측 기각 + F2b 수정 등록 (2026-07-23, 재측정 전)

**v1 기각**: 표적 9건 전부 구제(예측① 초과)했으나 기존 pass 15건 파손(예측② 대실패, 73→67).
원인 — flowbench fixture에서는 **올바르게 wiki로 간 지식 질문("연차 정책", "환불 정책"…)도
근거 0 공답이 흔해** "sources 빈 = 오라우팅" 전제가 성립하지 않고, DB-인접 표면이라 검증
게이트도 통과했다(C3-a 대칭 논리의 한계 실측). v1 결과는 그대로 기록하고 폐기한다.

**F2b 설계(재측정 전 등록)**: 폴백 전제에 **결정론 집계-신호 어휘 조건**을 추가한다 —
질문에 {세어, 세줘, 건수, 행 수, 항목 수, 개수, 집계, 몇 곳, 몇 개, 몇 건} 중 하나가 있거나
{보여줘 + 포함된/항목} 결합일 때만 wiki-빈근거 폴백을 연다. 파손 15건은 전부 이 신호가 없고
(정책/요약/설명/관계/누구야), 표적 9건은 전부 있다 — 실측된 어휘 분리에 근거한 수정이다.

**F2b 등록 예측**: ① 표적 9건 구제 유지(9/9) ② 파손 0 복귀(15건 전부 wiki 유지) ③ 신호
어휘가 지식 질문과 충돌하는 잔여 위험("~보여줘"형 지식 요청)은 wiki-빈근거+게이트 이중 전제
뒤에 있으므로 flow 전체에서 신규 파손 0.
