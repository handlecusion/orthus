## 0. 한 줄 요약

`/ask`의 **structured(NL→SQL) 분기**가 지금은 답을 **한 번** 만들고 끝낸다. 검증 게이트는
*"유효하지 않은 SQL"* 은 막지만 *"유효한데 틀린 SQL"* 은 그대로 통과시킨다. **실행 결과가
"망가졌다"고 결정론적으로 말해 주는 신호**(게이트 실패·0행·결과가 `0`)가 이미 있는데 버려지고
있다. 그 신호가 켜질 때만 **다른 모델로 한 번 더 묻자**는 제안이다.

실측(E1): 현행 운영 모델 기준 DB질의 정답률 **77.8% → 100%**(오라클), 추가 호출 **1.22×**,
손실 0, **LLM 판단 0회**(전부 결정론 신호).

## 1. 문제 정의

### 1.1 지금 무슨 일이 일어나는가

`orthus/structured/query.py::_query_structured`(:285)는 **컴파일 → 검증 → 실행**을 한 번 수행하고
`AssistantResult`를 반환한다. 검증 게이트(`orthus/assistant/validate.py`)는 5종 reject를 막지만,
**게이트를 통과한 SQL이 정답이라는 보장은 없다.**

E1이 실회사 데이터(`orthus_company`)에서 실측한 대표 실패:

```text
질문: "회사 미팅 기록 총 몇 건?"            (정답 28)
모델: SELECT COUNT(*) … WHERE db_name='회사 미팅 기록'
                        AND properties->>'미팅 기록' IS NOT NULL     ← 없는 컬럼을 지어냄
결과: [[0]]                                                          ← 게이트 통과, 실행 성공, 오답
```

사용자에게는 **숫자 `0`이 확신에 차서** 전달된다. 에러도, 경고도 없다.

### 1.2 핵심 관찰 — 신호는 이미 있다

**유효한 SQL이 아무것도 못 찾았다는 것**은, 이 도메인에서 대개 *"진짜 답이 0"* 이 아니라
**"모델이 없는 컬럼/값을 지어냈다"** 는 뜻이다. 그리고 그건 **답을 이해하지 않고도** 알 수 있다.

E1 실측: 현행 `gpt-4o-mini`가 골든 DB질의 18문항 중 **4문항을 틀리는데, 그 4문항이 전부**
검출 가능형이다 — 결과가 `0`(1건) / 빈 결과(2건) / 게이트 실패(1건).

> **정답을 만드는 것보다 틀린 답을 알아보는 것이 훨씬 쉽다.** SVC는 이 비대칭 하나에 기댄다.

### 1.3 왜 지금 하나 — "안전 장치가 품질 장치다"

orthus는 **sqlglot 게이트 + 실DB read-only 실행**이라는 결정론 검증기를 이미 갖고 있다. 그건 원래
**품질이 아니라 안전**을 위해 만든 것이다(AGENTS.md 설계원칙 1·4). SVC는 **그 장치를 품질 신호로
재활용**할 뿐, 새 검증기를 만들지 않는다. 대부분의 LLM 앱은 이 장치가 없어서 같은 것을 하려면
LLM judge 같은 비싸고 불확실한 대체물을 써야 한다.

## 2. 목표 / 비목표

**목표**

- structured 분기의 **조용한 오답**(유효 SQL → 틀린 결과) 중 **검출 가능한 부분**을 회수한다.
- 추가 비용은 **트리거 발동 시에만** 발생한다(평균 호출 1.05~1.29× 예상, §7.1에서 실측 필요).
- **기존 동작은 flag off에서 byte-identical**로 유지한다.

**비목표 (명시적 out)**

- 지식응답(wiki QA) 확장 — **결정론 검증기가 없다**(§6.3). E1 결론을 여기로 확대하지 않는다.
- 라우팅 확장 — 규칙(현행) = 오라클, 헤드룸 0(E1 §1).
- **다수결 투표 / self-consistency** — E1에서 캐스케이드에 **정확도·비용 양쪽에서 졌다**(§5).
- 모델 confidence 기반 분기 — **절대룰 위반**(§4).
- 국내 모델 도입 — **무관하다.** SVC는 "오류가 비상관인 두 번째 모델"만 요구한다(§3.3).

## 3. 설계

### 3.1 계약

```text
1차: 현행 경로 그대로 실행 (_query_structured)
검증: _retry_signal(result) → None | "gate_fail" | "not_executed" | "empty_rows" | "zero_answer"
     └ None  → 1차 결과 반환                      (변경 없음)
     └ 발동  → 2차 모델로 재실행
              └ 2차도 신호 발동 → **1차 유지**    (진짜 0인 답을 보존 — 오발동 방어)
              └ 2차 정상        → 2차 채택
```

**변경 지점은 `orthus/structured/query.py::query_structured`(:268) 한 곳**이다.
`_query_structured` 본문(컴파일/검증/실행/scope rewrite)은 **건드리지 않는다.**

### 3.2 신규 조각 (셋뿐)

| 조각 | 위치 | 계약 |
|---|---|---|
| `_retry_signal(result: AssistantResult) -> str \| None` | `orthus/structured/query.py` | **순수 함수·LLM 0회.** `not result.validation.passed` → `gate_fail` / `result.status != "executed"` → `not_executed` / `result.row_count == 0` → `empty_rows` / 결과 rows의 정수집합 == `{0}` → `zero_answer`. **`AssistantResult`의 기존 필드만 읽는다**(`validation`, `status`, `row_count`, `rows` — canonical.py:161). 모델 confidence를 보지 않는다 |
| `get_fallback_chat_model() -> ChatModel \| None` | `orthus/models/registry.py` | 현행 `get_chat_model()`(:46)은 **인자 없는 단일 슬롯**이다. 그 시그니처를 깨지 않고 **형제 함수**를 추가한다. `llm_fallback_model` 미설정이면 **`None`**(fail-closed) |
| `llm_fallback_model: str = ""` | `orthus/settings.py` | env `ORTHUS_LLM_FALLBACK_MODEL`. **빈 값 = 기능 off**(현행 설정에 없음 = 신규). base_url/api_key는 기존 `llm_base_url`(:102)/`llm_api_key` 재사용 — 다른 벤더가 필요하면 `llm_fallback_base_url`/`_api_key`를 함께 추가 |

**감사(설계원칙 3):** 발동 시 `audit("structured.fallback")` 스팬에 `trigger`, `adopted`(bool),
`primary_model`, `fallback_model`을 기록한다. **신규 테이블 불필요** — 기존 `query_runs.result_meta`로
충분하다. 2차 실행은 자체 `query_id`를 갖는 정규 run이므로 `query_runs`에 그대로 남는다
(PII redaction 경로 불변).

**주입된 `chat_model`은 불개입:** 호출자가 `chat_model=`을 명시 주입한 경우(실험/테스트 하네스)에는
캐스케이드를 발동하지 않는다 — 그래야 기존 테스트와 실험 하네스의 단일 모델 측정이 오염되지 않는다.

### 3.3 2차 모델 선정 — "정확도"가 아니라 "오류 비상관"

E1 실측: 국내 3종의 오답 집합이 **쌍별로 한 문항도 겹치지 않았다**(Jaccard = **0.00**). 캐스케이드가
작동한 이유가 이것이다 — 2차가 1차와 **다른 문항에서 틀려야** 회수가 일어난다.

> **주의:** E1은 **교차 벤더**(OpenAI ↔ Upstage/LG/SKT)만 측정했다. *"같은 벤더의 더 큰 모델"* 이
> 오류 비상관을 주는지는 **미측정**이다. §7.1의 shadow mode로 저렴하게 비교할 수 있다.

### 3.4 ★ 1차 모델 선택 기준이 넓어진다

캐스케이드는 **"티가 나는 오답"만** 잡는다. 따라서 1차는 정확도만으로 고르면 안 된다.

| 1차 후보 (E1 실측) | 정확도 | 잔여 오답의 성격 | 캐스케이드 결과 |
|---|---|---|---|
| 현행 gpt-4o-mini | 77.8% | **전부 zero/empty/gate_fail** | 14 → **18/18** ✅ |
| Solar | 94.4% | `0` 반환 (시끄러움) | 17 → **18/18** ✅ |
| EXAONE | 94.4% | 부분 집계 누락 (조용함) | 17 → 17/18 — **트리거 미발동** |

**정확도가 같은 94.4%인데 성패가 갈린다.** → 1차 선정 기준 = **정확도 × 실패모드 검출가능성.**

## 4. 절대룰 정합성 (AGENTS.md)

| 룰 | 정합 근거 |
|---|---|
| **confidence routing 금지** | 트리거는 **실행 결과의 결정론 속성**(게이트 통과 여부·행 수·결과 정수집합)이다. 모델 확신도·logprob·self-report를 **일절 보지 않는다.** LLM 판단 0회 |
| **검증 게이트 우회 금지** | 2차 SQL도 **동일 게이트를 그대로 통과**해야 실행된다(`_query_structured` 재사용). 우회 경로가 생기지 않는다 |
| **LLM-only 실행 금지** | 채택 여부를 **결정론 코드**가 정한다 — P3 policy gate 철학("LLM은 후보를 만들고, 결정은 결정론 gate가")의 연장 |
| **read-only** | 재시도도 `SELECT` 전용 + `orthus_ro` 롤. 이중 방어 불변 |
| **PII redaction** | 2차 run도 기존 `query_runs` 경로를 타므로 `redact_pii_text()` 통과 불변 |
| **감사** | 호출 단위 `audit()` 스팬 추가(설계원칙 3) |

→ 설계원칙 1(*"LLM은 초안을 만들고, 실행 안전은 typed guard가 통제한다"*)에 정확히 부합한다.
**이번엔 그 guard가 안전에 더해 품질까지 통제한다.**

## 5. 대안 비교

| 옵션 | 정확도(E1 실측) | 호출 | 판단 |
|---|---|---|---|
| **A. 결정론 캐스케이드 (본안)** | 골든 **100%** / 합성 **90.0%** | **1.05×** | **채택** |
| B. 다수결 투표 (2-of-3) | 골든 100% / 합성 **89.1%** | 2.15× | **기각** — 비용 2배인데 어려운 분포에서 더 나쁘다. **오답 수렴**(2+ 모델이 같은 오답에 합의: 합성 63문항 중 7건)에 다수결이 **오답을 확정**한다 |
| C. 학습 선택기 | 골든 92.3% (< 규칙 94.9%) | 2.00× | **기각** — G3에서 이미 기각(`e1-results.md` §0) |
| D. LLM judge로 답 검증 | 미측정 | 2.00× | **기각** — 비싸고, judge 편향 문제를 새로 떠안는다. 결정론 검증기가 있는데 LLM을 부를 이유가 없다 |
| E. 아무것도 안 함 (현행) | 77.8% | 1.00× | 기준선 |

**B가 진 이유가 이 설계의 핵심 논거다.** 투표는 *"누가 인기 있나"*(모델 간 합의 = 상대적)를 묻고,
캐스케이드는 *"이 답이 망가져 보이나"*(답 자체의 속성 = 절대적)를 묻는다. 후자는 다수와 무관하므로
**상관 오류에 구조적으로 면역**이다.

## 6. 리스크 / 엣지 케이스

### 6.1 ★ "정답이 진짜 0인 질문" (최대 리스크)

`zero_answer`/`empty_rows` 트리거는 **정답이 실제로 0/빈 결과인 질문**에서 오발동한다.

- **구조적 방어:** 2차도 신호가 발동하면 **1차를 유지**한다(§3.1) — 두 모델이 독립적으로 "없다"고
  하면 진짜 없는 것으로 본다.
- **미측정 노출:** E1 골든의 채점 대상 18문항 중 **gold에 0이 포함된 문항이 0건**이라, 이 케이스의
  오발동을 **실측하지 못했다.** 프로덕션 분포에서는 다를 수 있다.
- **보수적 변형:** `zero_answer`만 끄고 `gate_fail`/`not_executed`/`empty_rows`만 쓰는 구성이
  가능하다. 단 E1의 회수는 대부분 `zero_answer`에서 나왔으므로 이득도 함께 줄어든다.
- **완화 순서:** §7.1 shadow mode로 **먼저 재본다.**

### 6.2 트리거 발동률 = 추가 비용 (미확정)

E1에서 발동률이 **7.9%(합성 63문항) ~ 28.6%(골든 전 28문항)** 로 폭이 크다. 프로덕션 질문 분포에서
몇 %가 발동하는지가 **곧 비용**이다(1.08× ~ 1.29×). **shadow mode 없이 켜지 말 것.**

### 6.3 지식응답에는 적용 불가 (경계)

wiki QA에는 **결정론 검증기가 없다.** "답이 비었는가" 정도는 되지만 "답이 틀렸는가"는 판정 불가다.
같은 방법을 쓰려면 LLM judge가 필요한데, 그건 대안 D로 이미 기각됐다. **E1의 결론을 여기로 확대
적용하지 않는다.**

### 6.4 지연

발동 문항은 LLM 호출이 2회가 되어 **그 문항의 지연이 약 2배**가 된다(전체 p50이 아니라 발동분만).
단 E1 실측상 국내 모델이 현행보다 빨라(DB질의 p50 −44%) 모델 교체를 병행하면 상쇄된다.

### 6.5 2차 모델의 비결정성 (E1 TS15)

세 모델 모두 `temperature=0`에서 **비결정적**이었다(SQL 동일률 46~76%). 즉 **같은 질문이 언제든
망가진 답을 낼 수 있다** — 이는 SVC의 근거를 오히려 강화하지만, **재현 테스트를 SQL 문자열 일치로
작성하면 안 된다**는 뜻이기도 하다. 테스트는 `_retry_signal`(순수 함수)에 대한 단위 테스트로 고정하고,
모델 호출은 mock으로 대체한다.

## 7. 마일스톤 + 검증 게이트

### 7.1 SVC.0 — Shadow mode (관측 전용) ★ 선행 필수

**트리거만 기록하고 재질의는 하지 않는다.** `audit("structured.fallback_shadow")` 스팬에
`trigger`만 남긴다. flag: `ORTHUS_STRUCTURED_FALLBACK_MODE=shadow|off|on` (default `off`).

**게이트 (1~2주 운영 후):**
1. 실 발동률이 측정됐다 → 추가 비용 상한이 확정된다.
2. 발동 로그를 사람이 스팟체크해 **"정답이 진짜 0"인 질문의 비율**이 나온다(§6.1).
3. 발동률이 비상식적으로 높으면(> 30%) 트리거 정의를 조정하고 재측정한다.

### 7.2 SVC.1 — 캐스케이드 활성 (현행 모델 유지)

`ORTHUS_LLM_MODEL`은 **그대로 두고** `ORTHUS_LLM_FALLBACK_MODEL`만 설정한다.

- **기대(E1 실측):** DB질의 77.8% → **100%**, 호출 1.22×, 손실 0, 미측정 노출 0.
- **리스크 최저:** 1차 동작 불변, 되돌리기는 env 한 줄.
- **게이트:** flag off에서 기존 structured 테스트 **전부 무변화**(byte-identical) + `_retry_signal`
  단위 테스트(4종 트리거 + 미발동) + 발동 시 audit 스팬 존재 확인.

### 7.3 SVC.2 — 1차 모델 교체 (선택)

배정 규칙(실험 §6.6)에 따라 1차를 DB질의 최강 모델로 바꾼다.

- **기대:** 94.4% → 100%, 호출 1.05×.
- **게이트:** 후보 모델의 **잔여 오답이 검출 가능형인지 확인**(§3.4) — 정확도만 보고 고르면
  캐스케이드가 무력화된다(EXAONE 사례).
- **주의:** 이건 **모델 교체 결정**이라 SVC와 독립적으로 판단해야 한다. SVC.1만으로도 이득의 대부분을
  가져간다.

## 8. 열린 질문

1. **2차 모델을 무엇으로 둘 것인가** — 교차 벤더가 유리할 가능성이 높으나(§3.3) 같은 벤더의 다른
   모델은 미측정. shadow mode 로그로 비교 가능.
2. **프로덕션에 "정답이 0"인 질문이 얼마나 흔한가** — §6.1. shadow mode가 답한다.
3. **`empty_rows`를 필터형 질문에서만 끌 것인가** — "조건에 맞는 행이 없음"이 정상인 질문 유형을
   결정론으로 구분할 수 있는지(질문 유형 태깅 없이) 미검토.
