# Fugu-KO 측정 캠페인 — 결과 요약 (대회 공개판)

> 이 문서는 원본 실험 리포트에서 **사내 데이터(질문 원문·메일 본문·위키 슬러그·실명)를
> 전부 제거하고 수치와 경향성만 보존**한 요약본이다. 원본 golden set은 라이브 사내
> 위키/DB에서 역생성한 것이라 공개 레포에는 싣지 않는다. 측정 하네스(러너/스코어러/
> 저지/분석기)는 이 디렉터리에 그대로 있으므로, 자기 노드의 위키로 golden을 다시
> 만들면 전 측정을 재현할 수 있다.

## 0. 캠페인 개요

Fugu-KO는 한국어 사내 지식 에이전트 파이프라인의 **모든 LLM 호출 지점(작업 슬롯)**을
분리해, 슬롯별 golden set을 만들고 후보 모델을 홀드아웃으로 실측한 캠페인이다.
측정 대상 슬롯은 13종:

`structured`(NL→SQL) · `routing`(경로 분류) · `intent`(명령/질문 판정) ·
`decompose`(복합질문 분해) · `synthesize`(부분답 합성) · `graph_bind`(KG 의도+명사구) ·
`delegation_extract`(위임 판별) · `email_draft` · `gap_suggest` · `claim_headline` ·
`wiki_qa`(그라운딩 답변) · `distill`(위키 저작) · `followup_rewrite`(후속질문 재작성)
— 그리고 별도 트랙으로 **retrieval embedding 슬롯**.

최종 결론: **전 슬롯 Solar 단일 배정**. 아래는 그 근거가 된 수치들이다.

## 1. Chat 슬롯 홀드아웃 (판별 작업)

main 코드 + 신규 홀드아웃으로 재측정한 Solar 성적:

| task | n | Solar | 비고 |
|---|---|---|---|
| structured (NL→SQL) | 59 | **86.4%** | 후보군 중 최고 |
| routing | 28 | 92.9% | 최고와 1문항 차, p=1.0 |
| intent | 20 | **100%** | 전 후보 동률 → 최속 모델 채택 |
| decompose | 16 | **81.2%** | 후보군 중 최고 |
| graph_bind | 32 | **100%** | 동률 최고 |
| delegation_extract | 22 | 95.5% (FP=1) | 결정론 가드 2중 뒤에 배치 |
| latency p50 | — | **698ms** | 후보군 중 최속 |
| tool-call | — | **native** | 후보 중 tool-call을 무시하는 모델 존재 |

핵심 발견 두 가지:

1. **후보 모델 간 어떤 쌍대 차이도 유의하지 않았다** (McNemar p > 0.05, 전 작업).
   즉 "작업별로 다른 모델을 쓰면 이긴다"는 초기 가설은 홀드아웃에서 기각됐다.
2. 유의차가 없는 동점 구간에서는 **운영 특성이 결정 변수**가 된다: Solar는
   최속(p50 698ms)이고, 요청 속도 제한이 가장 느슨하고, tool-calling이 네이티브로
   동작하며, JSON 모드 실패가 0건인 유일한 후보였다. → 전 슬롯 Solar 단일화.

### 낙관 편향 교훈

초기 측정(작업별 분할 배정이 +7.7%p 이긴다는 결론)은 **기각**됐다. 원인 두 가지:
규칙을 뽑은 그 골든셋에서 채점한 in-sample 낙관 편향 + main보다 52커밋 뒤처진
체크아웃으로 측정한 코드 결함. n=16 골든에서 유의해 보이던 차이도 n=160으로
재측정하자 사라졌다. **"지표가 표본보다 먼저다."**

## 2. Chat 슬롯 (생성 작업)

| task | n | Solar | 비고 |
|---|---|---|---|
| wiki_qa (grounded) | 30 | **12승 0패** | 근거 문서를 본 저지 판정 |
| email_draft | 30 | fabrication 5/30 | 차점자와 p=1.000 — 차이 없음 |
| gap_suggest | 12 | **off-spec 0** | 타 후보 4/12 |
| claim_headline | 20 | 전원 동률 | → 최속(514ms) 채택 |
| distill (위키 저작) | — | **8.4 claims/doc, 정밀도 100%, 9.3s/doc** | 오염 0% |

### distill의 "커버리지 트레이드"는 프롬프트 artefact였다 (T14)

초기 측정에서 Solar distill은 정밀도 100%(40/40 클레임이 소스-리딩 저지에게
지지됨)였지만 문서당 4.8 클레임으로 기존 대비 얇아 보였다. 재분석 결과 프롬프트가
클레임을 8개로 **상한**하고 있었고, 비교 대상 모델도 25문서 중 14건이 잘리고
있었다. 상한을 해제하자 Solar는 **8.4 claims/doc @ 100% 정밀도**로 기존(7.2)보다
두꺼워졌다. 모델 특성으로 보였던 것이 프롬프트 결함이었던 사례.

### email_draft 표본 확대 교훈

12문항 초기 측정은 3 vs 1로 "차점자 우세"로 읽혔다 — 골든을 30문항으로 넓히자
5/30 vs 4/30, p=1.000. 표본이 작으면 노이즈가 결론을 쓴다.

## 3. Embedding 슬롯 (`experiments/fugu-ko/embedding/`)

현행(text-embedding-3-small, 1024d) 대비 **Solar `embedding-passage`**:

| 지표 | 현행 | Solar | Δ |
|---|---|---|---|
| retrieval MRR (vec-only) | 기준 | **+0.080** | p<0.001 |
| retrieval MRR (hybrid) | 기준 | **+0.112** | p<0.001 |
| 질의 지연 p50 | 241ms | **69ms** | 꼬리 8배↓ |

측정이 **유의하게 기각**한 배선 3종 (하지 말 것):

1. **비대칭 query/passage 분리** — 벤더 문서가 권하는 배선인데 4/4 조건 p<0.001로
   나빴다. `embedding-query`는 passage 공간에서 멀리 떨어져(top-1 cos 0.489 vs
   0.624) 순위도 나쁘고 하이브리드 병합의 lexical arm에도 진다. **대칭(양쪽
   passage)이 최적**이고, 그것이 코드의 기본값이다.
2. **4096차원 마이그레이션** — `dimensions` 파라미터는 matryoshka 절단이 아니어서
   부호가 슬라이스마다 뒤집힌다(cos≈0.04). 1024 유지.
3. **블렌드 재보정** — 비대칭 배선 탓의 오진이었다.

운영 함정: **`model_version` 혼재는 "깨짐"이 아니라 "조용한 오답"**이다 — 옛 벡터가
난수 점수로 순위 경쟁에 참여한다. 임베딩 교체는 전량 재임베딩과 한 세트다.

## 4. 오케스트레이션 구조 실험

- **학습된 셀렉터 vs 상수 테이블**: 질문 단위 학습 셀렉터(3티어, 최대 7.8B 로컬
  모델까지)를 만들어 상수 배정 테이블과 붙였다 — **상수 테이블이 이겼고** 요청당
  추론 1회도 아꼈다. 확신도 라우팅을 금지하는 설계 원칙과도 일치. 현행 배정은
  결정론 dict lookup이다 (`orthus/models/orchestration.py`).
- **SVC(구조화 검증 캐스케이드)**: 1차 답이 결정론 신호(게이트 실패/0행/전부 0)를
  띄울 때만 2차 모델로 재질의. E1 측정에서 structured 77.8% → **100%** 회수.
  2차 모델의 요건은 정확도가 아니라 **탈상관 오류**(1차와 다른 문항에서 틀리는
  것) — Solar 단일 빌드에서는 같은 벤더의 다른 모델(solar-mini)을 2차로 쓴다.
- **E3 decompose 프리필터 확장**: 기존 접속/열거 신호가 "랑/이랑/각각/비교" 복합
  질문을 LLM 게이트에 도달조차 못 하게 잘라냈다(누락형 recall 0/40). 티어별 신호
  확장(T3) 채택 시 **recall 100%**, 자연 트래픽 지연 증분 **+0.0%p**, 최종 오분해
  0%.
- **delegation_extract 안전 설계**: 이 슬롯의 지표는 정확도가 아니라 **false
  positive**다(오탐 1건 = 팀원 머신에서 full-access 에이전트 실행). 적대적
  홀드아웃(함정 24개)에서 어떤 모델도 FP 0이 아니었다 → 모델 단독 가드를 포기하고
  결정론 프리필터 + draft_for_review 강제라는 2중 결정론 가드를 모델 뒤에 세웠다.
  "어느 모델이 낫나"보다 중요한 결론: **어떤 모델도 유일한 가드가 되면 안 된다.**

## 6. 재현 방법

1. 자기 노드 위키를 구축한다 (`make seed` + `make wiki-rebuild`, `ORTHUS_LLM=solar`).
2. 슬롯별 golden을 만든다 — 각 러너의 `--cases`/입력 포맷은 러너 상단 docstring 참조.
3. 러너 실행 (예: `uv run python experiments/fugu-ko/harness_e2e.py --help`).
4. retrieval 평가는 `python -m orthus.wiki.eval_retrieval --cases <golden.json>`.

## 7. 대회 공개 실측 (중간결과보고서, 2026-07)

전국민 AI 경진대회(AI Champion) 중간결과보고서에 제출된 확장 측정. 위 §1~§4의
슬롯 홀드아웃과 별도로, 실운영 아카이브(위키 claim 12,123건·문서 2,480건) 위에서
골든 1,884문항 + 사전선언·블라인드 채점·McNemar 쌍대 검정으로 측정했다.

| 측정 | 결과 |
|---|---|
| 자연어→SQL (n=1,438) | Solar bare 72.8% → 하네스 5단 98.6% (+25.8%p) |
| 하네스 이득의 일반성 | bare 성능에 반비례 — 최약 모델 +41.2%p, 최강 프론티어 +6.0%p; 적용 후 4모델 격차 37.6%→4.9%p 수렴 |
| 모델 교체 효과 | ±2%p (하네스 이득의 1/10~1/20) · 슬롯별 모델 선택 효과 1,750문항 중 17건(≈1%p) |
| vs 파인튜닝 | SFT 학습기 94.3% vs 규칙 스택 98.8% (p=3.6e-12) |
| 학습 셀렉터 | 13개 구성 중 홀드아웃 463문항에서 규칙표 유의 우위 0개 → 폐기 |
| E2E 업무 완수율 (168문항) | 하네스 조립 98.2% — 2위 해외 프론티어 91.1% |
| 실사내 6작업 (n=200) | 프론티어 9종 중 유의하게 앞선 비교군 0종 |
| 이메일 생성 아레나 (9모델·2,160표) | Solar+하네스 78.3점 1위 (Opus 4.8 70.4·GPT-5.3 60.8); 하네스 없는 Solar 41.0 |
| 응답 지연 p50 | 417~746ms vs 프론티어 1,612~2,061ms (3.2~4.6배) |
| 질문당 원가 | Solar 0.33원 vs GPT-4o ≈5.6원·Sonnet ≈6.6원 |
| distill 근거 이탈률 | 9.4% → 0.6% |
| SVC 캐스케이드 | 비상관 2차(Jaccard 0.24)가 오답 11/11 회수(동일 모델 2차는 0/11) · 적대 표본 오발동 13.6%→0% |
| 안전 | 쓰기·DDL 오실행 0건 · 정상 위임 오차단 0건 |
| 정직 항목 | 하네스 없는 자유 루프는 프론티어 2~3배 우위(WildBench-KO·BFCL) · 자율 루프 70% vs 95~100% — 자유 루프 대신 결정론 스캐폴드를 선택한 근거 |

언어 전환 검증: 같은 골든셋을 영어/한국어로 각각 실행하면 이 시스템은 한국어에서
+2.00%p **올라가는** 유일한 시스템급이었다(프론티어 5종은 −0.25~−2.76%p 하락) —
한국어 업무 환경에서 영어 벤치마크 성적을 할인 적용할 필요가 없다는 실무적 함의.
