# 한국어 우위 가설 검증 실험계획서 (Korean Advantage Plan)

작성: 2026-07-27 · 3차 전면 개정 (가설을 "한국어라서"의 **인과 검증**으로 재정의, 신규 데이터셋 제작 전제)
선행 문서: `FRONTIER_PARITY_PLAN.md`(1·2차) — 그 계획은 "동급성"만 답할 수 있고 **본 가설의 인과는 검증 못 한다**(§0 참조). 본 문서가 SoR.

## 0. 왜 계획을 다시 짜는가

사용자 가설은 **"우리 오케스트레이터는 한국 모델로 조립했으니 *한국어라서* 성능이 잘 나온다"** 이다. 원인 변수는 **언어(한국어)** 다.

기존 e2e(n=1,750, 8태스크)·arena(n=1,589, 13태스크) 자산은 이 가설을 검증할 수 없다:

1. **교란(confounding)**: 측정 대상이 SQL 생성·JSON 툴콜·계약 추론·라우팅 분류다. contract에서 조립이 지는 건 법률추론 실패지 한국어 독해 실패가 아니고, toolcall 실패는 포맷 준수 문제라 언어와 무관에 가깝다. 언어능력과 과업능력이 한 점수에 뒤엉켜 있다.
2. **대조군 부재**: 전 문항이 한국어뿐이라 "영어였다면 어땠는가"가 없다. 비교 기준이 없으면 "한국어라서"는 원리적으로 측정 불가다.
3. **실측이 가설과 반대 방향**: 국내 단일 모델은 arena에서 solar 68.97%·ax 69.86%·exaone 64.19%로 gpt-4o(70.42%)에도 못 미치고, e2e에서 solar 단독 vs sonnet은 p=0.00019로 **프론티어가 유의하게 이긴다**. 즉 "한국어라서 국내 모델이 낫다"는 증거가 현재 0이다.

**따라서 본 계획의 핵심 설계는 "같은 문항의 한국어판 ↔ 영어판 대조쌍(parallel pair)"이다.** 조사 결과 저장소에 parallel 셋·공개 한국어 벤치(KMMLU/HAE-RAE 등)·번역 유틸이 **전무**하므로(가장 근접한 `prism/gen/{honorific,mood,jamo}.py`도 과업 강건성 변환기이지 언어능력 채점기가 아님) **신규 제작한다.**

## 1. 가설 (재정의)

- **H-KO (주가설, 인과):** 국내 모델(Solar/EXAONE/A.X)은 프론티어 대비 **한국어에서의 상대적 우위**를 가진다. 즉 언어를 한국어→영어로 바꿨을 때 성능 하락폭이 프론티어보다 작다(혹은 한국어에서만 앞선다).
  - 검정량은 **단순 점수차가 아니라 언어×모델 상호작용(interaction)**: `Δ = (국내_ko − 국내_en) − (프론티어_ko − 프론티어_en)`. **Δ > 0 이어야 "한국어라서"가 성립**한다.
  - 국내 모델이 ko/en 양쪽에서 똑같이 낮으면 → 한국어 우위 없음(그냥 약한 모델).
  - 국내 모델이 ko/en 양쪽에서 똑같이 높으면 → 한국어 우위 아님(범용 강함).
- **H-KO2 (한국어 고유현상):** 우위가 있다면 그 원천은 **한국어 고유 언어현상**(존댓말 체계, 종결어미, 조사, 동음이의어, 띄어쓰기 중의성, 관용구, 문화·업무 맥락)이다. 영어로 번역하면 소멸하거나 무의미해지는 항목에서 격차가 커야 한다.
- **H-ORCH (부가설):** 조립(오케스트레이션)이 만드는 이득은 언어 우위와 **별개 축**이다. 조립 이득이 ko/en 양쪽에 동일하게 나타나면 그것은 한국어 효과가 아니라 엔지니어링 효과다.
- **H2 (조합 개선):** 기존 계획의 C2(E2E best-per-slot)·V3(Arena 3슬롯 교체)는 유지하되, 본 실험에서는 **한국어 고유현상 축에서 재평가**한다.

**판정 기준 (실행 전 고정):**
- **채택**: 상호작용 Δ의 95% 부트스트랩 CI 하한 > 0.
- **"≈0"(등가) 밴드**: Δ의 95% CI가 **[−1.0%p, +1.0%p]** 안에 완전히 들어가면 "차이 없음"으로 판정. CI가 밴드를 걸치면 "불확정(inconclusive)"으로 보고하며 사후에 밴드를 넓히지 않는다.
- **부트스트랩**: 문항쌍(`pair_id`) 단위 재표집, **반복 10,000회, seed=20260727** 고정.
- 단순 ko 점수 우위만으로는 채택하지 않는다(교란 배제 불가).

### 2.3 축 정의

**A군 — 언어 중립(Language-neutral)**: 산술·논리·일정계산·표 읽기·인과 판정 등 언어 무관 추론. ko/en 번역이 손실 없이 성립. → *여기서 국내 모델이 프론티어에 뒤지는 폭이 "기본 능력 격차"이며, 상호작용 계산의 baseline.*

**B군 — 한국어 부하(Korean-loaded, 번역 가능)**: 한국 업무 맥락(회의록·메일·보고서·공지)에서의 요약·추출·의도판정. 영어로 번역해도 태스크가 성립. → *A군 대비 격차가 국내 쪽으로 좁혀지면 H-KO 지지.*

**C군 — 한국어 고유(ko-only, 번역 불가)**: 6개 하위축 × **각 66문항 + C1에 4문항 추가 = 총 400** (하위축별 McNemar 검정력 확보를 위해 균등 배분)
| 하위축 | 예시 판정 대상 |
|---|---|
| C1 존댓말/화계 | 상대·상황에 맞는 높임 선택, 압존법, 과잉존대(사물존칭) 탐지 |
| C2 종결어미/서법 | 평서·의문·명령·청유 구분, 완곡 표현의 실제 의도 |
| C3 조사/문법 | 은/는·이/가, 을/를, 받침에 따른 조사 선택, 조사 오류 탐지 |
| C4 중의성 | 띄어쓰기 중의(`아버지가방에들어가신다`형), 수식 범위 모호, 생략된 주어 복원 |
| C5 어휘/관용 | 동음이의어, 한자어·고유어 뉘앙스, 관용구·속담, 신조어·직장 은어 |
| C6 문화·업무 맥락 | 직급·호칭 체계, 한국 기업 관행(품의·결재·회식), 간접화행("검토해보겠습니다"의 실제 의미) |

C군은 **minimal pair** 우선(한 요소만 다른 두 문장 중 적법/자연스러운 쪽 고르기) — 채점이 객관적이고 사전지식 교란이 적다.

### 2.2b E군 — 슬롯 커버리지 (**owner 승인 2026-07-27 추가**)

**추가 사유 (사전등록 §9.1 개정 근거).** 초기 설계는 "과업능력이 언어능력과 섞인다"는 이유로 SQL/JSON/코드 생성을 배제했다. **이 근거는 과했다** — Δ 상호작용 설계가 과업 난이도를 이미 상쇄하기 때문이다:

```
Δ = (국내_ko − 국내_en) − (프론티어_ko − 프론티어_en)
```

과업이 어려우면 ko·en 양쪽에 동일하게 반영되어 차분에서 빠진다. 따라서 **ko/en 대조쌍만 성립하면 어떤 슬롯이든 가설 검정이 유효하다.** 배제해야 할 것은 "어려운 과업"이 아니라 **"결정론 채점이 불가능한 자유생성"** 이다.

**해결하는 문제 2가지**
1. **조립 수렴** — 현행 A/B/C/W군은 `routing`·`wiki_qa`·`structured`(소수)만 도달해 V1/V2/V3가 사실상 한 모델로 뭉갠다(§3.1c). E군이 배정표가 실제로 갈라지는 슬롯을 덮으면 조립 비교가 의미를 갖는다.
2. **제품 표면 커버리지** — 현행은 "위키 QA에서의 한국어"만 잰다. E군은 "우리 제품이 실제로 하는 일에서의 한국어"로 확장한다.

**구성 (250쌍 = ko 250 + en 250)**

| 하위축 | 슬롯 | 정답 형태 | 채점 | 쌍 수 |
|---|---|---|---|---|
| `intent` | intent | **8-way enum** (read 3 + `COMMAND_FAMILIES` 5) | 완전 결정론 | 60 |
| `delegation` | delegation_extract | `{is_delegation, assignee(이메일), mode, runner}` — **"기한" 필드는 존재하지 않음**, `instruction`은 자유문장이라 gold 제외 | 결정론(4필드 완전일치) | 60 |
| `graph_bind` | graph_bind | **(template, params) 전체** — `_bind`가 `max_hops`/`depth`까지 생성 | 완전 결정론 | 50 |
| `decompose` | decompose | 하위질문 목록 | 준결정론(개수+내용 매칭) | 40 |
| `structured` | structured | NL→SQL → **결과 집합 비교**(t3 counts-only 방식) | 결정론 | 40 |

**제외(자유생성 → 판정자 필요)**: `email_draft`, `distill`, `claim_headline`, `gap_suggest`, `synthesize`, `followup_rewrite`.

**structured 축의 데이터 소스**: W군 가상 회사(루미넥스소프트)의 `fact_base.json`(엔티티 91)을 **표 형태 fixture**로 파생시켜 사용한다. 같은 가상 회사를 쓰므로 실제 orthus 데이터 의존이 없고, W군과 세계관이 일관된다. 채점은 t3 선례대로 **결과 집합의 정수 카운트만 비교**(문자열 라벨 제외).

**주의**: E군은 과업 성격이 강하므로 **A/B/C/W군과 합산한 총점을 주 지표로 쓰지 않는다.** 군별로 Δ를 따로 내고, "언어중립(A) → 업무맥락(B) → 한국어고유(C) → 위키근거(W) → 제품슬롯(E)" 스펙트럼으로 보고한다.

### 2.2c R군 — routing 슬롯 (**신규 문항 0 · 파생 라벨링**, 2026-07-27 추가)

**왜 필요한가.** `routing` 슬롯(`orthus/router/route.py::classify`, `Route =
Literal["structured","wiki","graph"]`)은 조립 레인에서 **내부 단계로 실행만 되고 채점은 안
된다** — 정답 라벨이 없기 때문이다. E군 `intent` 축은 다른 함수(`classify_intent`, 8-way
{read|command})라 routing이 아니다. 그런데 routing 정답 라벨은 **새 문항 없이** 만들 수
있다: 이미 있는 문항의 축 정의가 곧 정답이다.

**구성 (파생 — 생성 호출 0회, LLM 0회)**

| 출처 | 정답 route | 정답 근거 |
|---|---|---|
| `group_w.json` 전량 | `wiki` | W군 정의 = "사내 위키 페이지를 근거로 답하는 질문"(§2.2 W군) |
| `group_e.json` `subaxis=structured` | `structured` | 축 정의 = 사내 DB 집계 질의(NL→SQL) |
| `group_e.json` `subaxis=graph_bind` | `graph` | 축 정의 = 관계/충돌/출처 질의(KG 템플릿 바인딩) |

**A/B/C군은 넣지 않는다** — 언어 퍼즐(산술·존댓말·조사)이라 "올바른 route"가 논쟁적이다.
정답이 방어 가능한 것만 넣는다. 생성기는 `koparity/gen/gen_r.py`이고 **멱등**이다
(`--check`로 드리프트 검사). 원 문항이 늘면 다시 돌려 R군을 갱신한다.

- 문항 텍스트는 원 문항의 **질문 한 줄만** 가져온다(위키 발췌·SQL 스키마·선택지 제거).
- `gold_type="route_label"`, `subaxis ∈ {route_wiki, route_structured, route_graph}`.
- `id = koparity-R-<출처군><출처일련번호>-<lang>` (예: `koparity-R-W0001-ko`) — 출처가 id에
  박혀 있어 원 문항이 늘어도 재번호되지 않는다. 원 문항 id는 `provenance.source_id`.

**실측 규모 (2026-07-27 · W/E 재생성이 진행 중이라 원 문항이 늘면 함께 늘어난다 —
`gen_r.py` 재실행으로 갱신하고 `--check`로 드리프트를 본다):** 580문항 / 290쌍 =
W 200쌍(`wiki`) + E structured 40쌍 + E graph_bind 50쌍. ko 규칙 종결 109건(37.6%) ·
en 0건(0.0%) · `pair_branch` both_llm 181 / mixed 109 · 규칙 충돌 7건 · 원 문항 드롭 0건.

**프롬프트 = 실제 프로덕션 라우팅 프롬프트.** `route.py::_SYSTEM`을 그대로 쓴다(지어내지
않는다). 제거하는 것은 맨 끝 출력형식 문장(`Respond with JSON only: {"route": ...}`) 하나뿐
이다 — KO-PARITY는 출력형식을 `koparity_prompts.build_user`가 `{"answer": ...}`로 전 군
통일해 붙이므로, 두 형식 지시가 충돌하면 채점이 형식 싸움이 된다(E군이 프로덕션 슬롯
프롬프트에서 출력형식 줄을 뺀 것과 같은 규약). 원본 `_SYSTEM`과 제거 문장의 sha256을
`provenance.production_prompt`에 남겨 대조 가능하게 한다.

**ko/en 모두 같은 영어 프롬프트를 쓴다.** 프로덕션은 질문 언어와 무관하게 이 영어 system
하나를 쓴다. 번역본을 만들면 프로덕션에 없는 프롬프트를 지어내는 것이고, ko/en 대비에
"지시문 텍스트 차이"라는 교란이 하나 더 붙는다. ⚠️ **그 결과 en 문항 prompt에도 한글이
들어간다** — `_SYSTEM`의 structured/graph 예시가 한국어이기 때문이다("'개수', '목록',
'상태별', '담당자'", "'A와 B는 무슨 관계'"). 이건 결함이 아니라 **측정 대상**(프로덕션
라우팅 표면의 한국어 편향)이며, `validate.py`의 `en_item_contains_hangul` 검사는 R군에서만
면제한다(카브아웃 주석 명시).

#### 파생 관계와 홀드아웃 오염 방지 (**규약**)

R 문항은 원 문항의 파생이므로 **원 문항과 같은 split에 있어야 한다** — 원본이 개발셋인데
파생이 홀드아웃이면 그 질문의 튜닝 정보가 홀드아웃으로 샌다. 관례가 아니라 구조로 막는다:

1. R 문항은 **원본 `pair_id`를 그대로 재사용**한다(자기 pair_id를 만들지 않는다).
2. `koparity/freeze.py`의 분할 단위가 `pair_id`이므로 원본과 파생이 **같은 단위**로 묶여
   자동으로 같은 split에 떨어진다. `check_pair_integrity`가 그것을 사후 검사한다.
3. 그 대신 한 단위 안에 group/subaxis가 다른 행이 공존하므로, freeze.py에 `DERIVED_GROUPS`
   예외를 넣어 그 공존만 허용했다. **층(stratum)은 언제나 원본(비파생) 행이 정한다** —
   파생은 원본이 가는 곳으로 따라간다(그래서 `freeze.lock.strata`에 R 행은 없다).
4. 원본↔파생은 질문 텍스트가 같으므로 `overlap_check` 키도 같다. freeze의 내부 정확중복
   리포트는 **같은 단위 안**(`same_unit_duplicate_groups`, 설계상 기대 — 실측 180군 =
   E structured 80 + graph_bind 100)과 **다른 단위끼리**
   (`dataset_internal_exact_duplicate_groups`, 진짜 결함 — 실측 0)를 분리해 센다.
5. R군은 A/B군 주판정(Δ)에 합류하지 않는다. 파생셋이고 다른 슬롯이므로 **별도 블록**으로만
   보고한다(`koparity_analyze.r_routing_breakdown`). 군 합산 총점에도 넣지 않는다 — 같은
   질문이 두 번 세어진다. 같은 이유로 `koparity_run.py --groups` 기본값에서도 빠져 있다
   (`--groups R` 명시 지정).

**실측 검증(2026-07-27):** 전체 데이터셋 동결 후 R 580문항 **전부** 원 문항과 같은 split
(불일치 0), dev↔holdout exact duplicate 0.

#### routing_source 분리 보고 의무 (**어기면 결론이 뒤집힌다**)

프로덕션 `classify()`는 LLM을 항상 부르지 않는다:

```
_rule_based_route(q)  → 결정되면 즉시 반환 (LLM 호출 0)
_quantity_route(q)    → 결정되면 즉시 반환 (LLM 호출 0)
그 외                 → _SYSTEM으로 LLM 1콜
```

그리고 그 결정론 앵커(`_STRUCTURED_TERMS`/`_GRAPH_TERMS`/`_WIKI_TERMS`/`_QUANTITY_TERMS`)는
**전부 한국어**다. 실측(R군 290쌍): **ko는 37.6%가 규칙에서 종결되는데 en은 0.0%** —
290건 전량이 LLM 분기로 간다. 파일럿(n=20 표본)에서도 같은 방향이 관찰됐다(ko 34% vs en 0%).

두 성분을 분리하지 않으면 "한국어 규칙만 짜놨다"는 **엔지니어링 사실**이 "한국어를 더 잘
이해한다"는 **언어능력 주장**으로 둔갑한다. 따라서 R군 보고는 **항상 셋으로 쪼갠다**:

| 층 | 정의 | 무엇을 말하는가 |
|---|---|---|
| **전체(제품 e2e)** | 규칙 발화분은 규칙 결과, 나머지는 모델 결과 | 제품이 실제로 내보내는 route |
| **rule-종결분** | 규칙 결과 vs gold | 결정론 한국어 앵커의 성능. **모델 무관 = 전 시스템 상수** |
| **LLM-분기분** | 모델 결과 vs gold (규칙이 침묵한 문항만) | **H-KO의 유일한 근거** |

- `routing_source ∈ {rule, llm}`는 `gen_r.py`가 **프로덕션 함수를 직접 호출해**
  `provenance.routing.source`에 박는다(재구현 사본이 아니라 import — 규칙이 바뀌면 재생성).
- 채점기(`koparity_score.py`)는 그 값을 채점행 최상위 `routing_source`로 내보내고
  `summary.r_diagnostics`에 세 층을 함께 낸다. 집계 셀에도 `routing_source` 축을 추가했다.
  제품 e2e 계산은 프로덕션 fail-safe(무효 라벨 → `wiki`)까지만 재현하고, 런타임 플래그인
  `_apply_wiki_default`는 재현하지 않는다(켜면 structured 축 측정 자체가 사라진다).
- 분석기(`koparity_analyze.py::r_axis_breakdown`)는 `rule_layer` / `by_system.by_lang` /
  `delta_llm_branch_pairs`를 낸다. **H-KO 인용은 `delta_llm_branch_pairs`와
  `acc_llm_branch_pct`만** 허용한다(PREREG §9.1c / §14.9).

⚠️ **선택 편향(반드시 함께 보고).** ko의 LLM-분기 표본은 "한국어 앵커가 놓친 잔여"라 ko
전체와 같은 분포가 아니다. 쌍 단위 Δ는 ko/en **양쪽이 모두** LLM 분기인 쌍
(`pair_branch=both_llm`, 실측 290쌍 중 181쌍)으로 제한해 계산하지만, 그래도 잔여 편향은
남는다. 결론 문장에 이 한계를 함께 싣는다.

⚠️ **규칙 충돌 문항은 버리지 않는다.** 결정론 규칙이 gold와 다른 문항(실측 7건 — 한국어
graph 질문이 `_WIKI_TERMS`에 먼저 걸리는 경우, "몇 개월/몇 명"이 든 위키 질문이
`_STRUCTURED_TERMS`에 걸리는 경우)을 지우면 벤치마크가 **현행 규칙을 정답으로 삼는 순환**이
된다. `provenance.routing.rule_correct=false` 플래그만 남기고 민감도 분석("이 7건을 빼면
결론이 바뀌는가")에 쓴다.

### 2.3f 프롬프트 튜닝 반영 (**owner 재확정 2026-07-27: 반영함 — 글루 3단계로 승격**)

⚠️ **선결 사실**: 기존 튜닝안 6건은 `delegation_extract`/`distill`/`compile`/`email_draft` 프롬프트를 수정하는 것인데, **KO-PARITY 문항(A/B/C군)은 그 프롬프트를 타지 않는다.** 따라서 6건을 프로덕션에 반영해도 본 실험에서는 무효과다. "튜닝을 먹인다"를 의미 있게 만들려면 **KO-PARITY 글루 프롬프트 자체를 튜닝**해야 한다.

**→ 글루를 2수준에서 3수준으로 확장한다:**

| 수준 | 정의 |
|---|---|
| `bare` | system 없음 |
| `glue` | orthus 프로덕션 스타일 role·제약 system 1겹 (튜닝 전) |
| **`tuned`** | **개발셋 20%에서 튜닝한 글루 프롬프트** (신규) |

**튜닝 프로토콜 (prereg 준수):**
1. 튜닝은 **개발셋 20%에서만** 수행한다. 홀드아웃 80%는 절대 보지 않는다(prereg §9 홀드아웃 튜닝 금지).
2. 튜닝된 프롬프트는 홀드아웃 측정 전에 **동결**하고 해시를 기록한다.
3. **튜닝 결과물은 국내·프론티어 양쪽에 동일하게 적용한다** — 비대칭 금지 원칙(§3.1)의 연장. 우리 쪽만 튜닝하고 프론티어에 튜닝 안 된 프롬프트를 주면 "베이스라인 핸디캡"으로 §7 리스크 1번에 정면으로 걸린다.
4. 튜닝이 국내 모델 특성에 과적합될 수 있음은 **한계로 명시 보고**한다(튜닝을 국내 모델로 돌렸다면 그 사실 자체를 공개).

**이 확장이 만드는 추가 판정축:** `Δ_tuned` — 튜닝까지 얹은 최대치 상태에서도 한국어 우위가 남는가. §5 시나리오 표는 `Δ_bare`/`Δ_glue`/`Δ_tuned` 3열로 확장한다.

**기존 튜닝안 6건 처리:** KO-PARITY와 무관하므로 본 실험 대상이 아니다. 실험 종료 후 별도 owner 게이트로 다룬다(유의한 것은 delegation A·distill A 둘뿐).

## 3. 실험 조건 (셀 설계) — 글루를 **제2 요인으로 승격**

### 3.0 왜 글루가 핵심 교란인가 (실측 근거)

기존 실험이 이미 답을 갖고 있다. **R+ ablation**(`train/rplus_ladder.py`, D8 n=1,438):

| 구성 | 정확도 |
|---|---|
| solar 단일 1회 (글루 없음) | 73.5% |
| + db_name 스냅 글루 **하나** | 96.2% (**+22.7%p**) |
| R+ 전체(자기일관성 k=5 + 스냅 + AST 수리 2종 + null 폴백 + probe-0) | **98.8%** (+25.3%p) |

즉 **성능의 대부분이 모델이 아니라 결정론 글루에서 나온다.** 학습기(SFT c8, 94.3%)마저 R+가 p=3.62e-12로 이겼다.

이것이 본 가설에 치명적인 이유: **글루를 켠 채 측정하면 "한국어라서 이겼다"와 "글루라서 이겼다"를 구분할 수 없다.** 반대로 글루를 전부 끄면 실제 제품과 다른 것을 재게 된다. 어느 한쪽만 하면 실험이 무의미하다.

또한 프로덕션은 구조적으로 **항상 glue**다 — `orthus/models/base.py:22`의 `complete(self, system: str, user: str, ...)`가 system을 **필수 위치 인자**로 강제해 bare 구조가 코드상 존재할 수 없다(예외: `adapters/cli.py:242` 등 3곳은 system+user를 병합해 bare로 붕괴).

### 3.1 4-Arm 구조 (확정)

두 개의 서로 다른 주장을 섞지 않기 위해 arm을 분리한다. **Arm D가 가설 검정, Arm A vs B가 제품 주장**이다.

| Arm | 구성 | 무엇을 주장하나 | 필수성 |
|---|---|---|---|
| **A. 우리 제품** | 국내 3종 + 글루 + 조립(V1) (+튜닝 반영 시 그 버전) | 실제 배포 상태의 성능 | 필수 |
| **B. 공정 비교** | 프론티어 6종 + **동일 수준 글루** | "같은 조건에서도 우리가 되는가" — **여기서 이겨야 진짜 승리** | **필수 (생략 불가)** |
| **C. 순진한 베이스라인** | 프론티어 6종 맨몸(system 없음) | "그냥 API 부르면 이 정도" 참조선 | 필수(저비용) |
| **D. 가설 검정** | 국내 3종 + 프론티어 6종, **양쪽 모두 맨몸** × ko/en | **"한국어라서"의 유일한 검정** (Δ 상호작용) | **필수** |

**설계 원칙 — 비대칭 금지:** 글루는 시스템 프롬프트 한 겹이라 비용·기술 장벽이 없다. 프론티어에만 안 주고 이긴 결과는 심사에서 즉시 기각된다("베이스라인을 핸디캡했다"). arena도 18개 시스템 전부에 bare/glue 양쪽을 측정한 것이 기존 관행이다.

**우리 고유 자산은 글루가 아니라 그 위에 있다:** 조립(태스크별 배정) · SVC 2차 검증 · R+ 결정론 스택은 프론티어에 그냥 얹어줄 수 없다. Arm A가 Arm B를 이긴다면 그 이득은 여기서 나온 것이고, 그것이 정당한 엔지니어링 승리다.

### 3.1b 요인 정리

| 요인 | 수준 | 역할 |
|---|---|---|
| **언어** | ko / en | **주 관심 변수** (Arm D) |
| **글루** | `bare`(system 없음) / `glue`(orthus 프로덕션 스타일 role·제약 system 1겹) / **`tuned`(개발셋 20%에서 튜닝한 글루, §2.3f)** | **교란 통제 변수** (Arm B·C 대비). **3수준** |
| **스택** | 단일모델 / 조립(V1) | 엔지니어링 효과 분리 (Arm A) |
| 모델 | 국내 3종(solar/exaone/ax) · 프론티어 6종(Sonnet 4.6, Opus 4.8, GPT-5.3, GPT-5.6-sol, DeepSeek V3.2, GLM-5.2) | |

glue 정의는 arena를 그대로 계승한다(`arena_prompts.py:345 build_prompt(task, condition, input)`) — **few-shot·재시도·파서 보정은 glue에 포함하지 않는다**(arena에서 코드로 확인된 정의). 변수를 한 겹으로 유지해야 해석이 가능하다.

**판정 시 반드시 글루 수준별로 Δ를 따로 낸다:**
- `Δ_bare` = 글루 없는 순수 모델 상태의 언어×모델군 상호작용 → **H-KO의 진짜 검정**
- `Δ_glue` = 프로덕션 상태의 상호작용 → **실제 제품에서 체감되는 효과**
- `Δ_bare > 0` 이지만 `Δ_glue ≈ 0` 이면: 한국어 우위는 존재하나 **글루가 그것을 덮어버린다**(= 실무적으로는 무의미).
- `Δ_bare ≈ 0` 인데 `Δ_glue > 0` 이면: 한국어 우위가 아니라 **글루-모델 궁합** 효과다. 가설 기각.

### 3.2 R+ 풀스택의 위치

R+(자기일관성·db_name 스냅·SQL AST 수리·probe-0)는 **SQL/structured 전용 결정론 스택**이라 KO-PARITY의 A·B·C군(언어 이해 과제)에는 적용 대상이 아니다. 따라서 요인에 넣지 않고 **참조축**으로 별도 보고한다:

> "언어를 바꿔 얻는 이득(Δ) vs 글루를 쌓아 얻는 이득(+25.3%p)" 를 같은 축에 놓고 비교한다. 이 대비 자체가 본 실험의 가장 강한 발표 메시지가 될 가능성이 높다.

### 3.3 프롬프트 튜닝 버전 고정 (필수 선결)

`.worktrees/prompt-tuning` 제안 6건은 **프로덕션 반영 0/6**이다(`git diff main -- orthus/` 0줄, `results/SUMMARY.md`가 직접 명기). 그중 통계적으로 유의한 것은 둘뿐:

| 제안 | 태스크 | 효과 | 상태 |
|---|---|---|---|
| delegation A | delegation_extract | 함정 FP **7→0** (n=36) | 미반영 |
| distill A | distill | 근거이탈률 9.4%→0.6% (**−8.8%p**, n=25문서) | 미반영 |
| compile A | structured | AX rejected 1→0 (n=28, 소표본) | 미반영 |
| email 9c-V1 | email_draft | Solar 대조에서만 5/30→3/30 (n=30, 유의 불가) | 미반영 |
| routing/decompose | routing·decompose | p=1.0 무효 + p95 **+283%** 악화 | 기각 |
| wiki_qa | wiki_qa | 전 조건 악화 | 기각 |

**본 실험은 프로덕션 baseline 프롬프트로 고정해 실행한다.** 이유: (1) 튜닝안이 코드에 없어 재현 기준이 baseline이고, (2) 튜닝안을 섞으면 "한국어 효과"에 "프롬프트 품질 효과"가 또 하나 얹혀 3중 교란이 된다. 튜닝안 반영 여부는 본 실험과 **분리된 owner 게이트 결정**으로 남기며, 반영된다면 실험 전에 반영을 끝내고 그 버전을 동결한다(실험 도중 변경 금지).

### 3.4 지시문 언어 통제

`experiments/prompt-lab/korean-experiment.md`가 "한국어 지시문은 언어이해 정합이 아니라 **행동 프라이어**를 바꾼다"고 이미 관측했다. 따라서 ko 문항은 ko 지시문, en 문항은 en 지시문이 기본이되, **"ko 문항 + en 지시문" 교차 셀**을 A·B군 각 100문항에 넣어 콘텐츠 언어와 지시 언어의 효과를 분리한다.

## 4. 실행 단계

### Phase A — 데이터셋 제작 (신규, 최우선)
1. 스키마 확정: `{id, group(A|B|C), subaxis, lang, prompt, gold, pair_id, provenance}` — `pair_id`로 ko/en 연결.
2. 제3벤더(Nova Pro / Llama 3.3 70B)로 초안 생성 → 역번역 의미동치 검사 → 인간 표본 검수 → freeze(해시 동결 + `MANIFEST.sha256`).
3. **사전등록(prereg) 작성**: 가설·판정식(Δ)·검정법·표본크기·중단규칙을 실행 **전에** 고정. arena V3가 홀드아웃 튜닝으로 무효화된 전철을 밟지 않기 위함.
4. 개발셋(20%) / 홀드아웃(80%) 분할 — 프롬프트·배정 조정은 개발셋에서만.

### Phase B — Arm C·D 측정 (맨몸, H-KO 본체) — **최우선**
국내 3종 + 프론티어 6종 × {A·B군 ko/en, C군 ko} × **bare** 실행.
→ Arm D(가설 검정 Δ_bare)와 Arm C(순진한 베이스라인)를 **한 번의 실행으로 동시 확보**한다(같은 셀이므로 중복 호출 없음).
실행량: 9모델 × 1,600문항 = **14,400 호출**.

### Phase C — Arm A·B 측정 (글루, 제품 주장)
1. **Arm B**: 프론티어 6종 × 동일 문항 × **glue** = 9,600 호출.
2. **Arm A**: 국내 3종 glue(4,800) + 조립 V1(1,600) = 6,400 호출.
3. → `Δ_glue` 및 A vs B 직접 비교 산출. 조립 이득이 ko/en 양쪽에 동일하면 언어효과가 아니라 엔지니어링 효과.
4. **글루 사다리 참조**: A·B군 일부(각 100쌍)에 자기일관성 k=5를 얹어 "글루 한 겹 더"의 이득을 재고, R+ SQL 실측(+25.3%p)과 같은 축에 놓는다 → §3.2 대비 메시지 근거.

**총 실행량 = 30,400 호출** (Phase B 14,400 + Phase C 16,000). 규모 축소가 필요하면 **arm이나 조건이 아니라 문항 수로 조절**한다 — arm 하나를 빼면 주장 하나가 통째로 사라진다.

### Phase D — 통계 판정
- **가설 검정(Arm D)**: 언어 × 모델군 × 글루 3원 상호작용. 문항쌍 단위 부트스트랩 CI가 주, 혼합효과 로지스틱 회귀(문항 랜덤절편) 보조.
- **제품 주장(Arm A vs B)**: 동일 글루 조건에서 조립 vs 프론티어 McNemar + 비열등 마진(CI 하한 −2.0%p). **Arm A > Arm B 가 성립해야 "우리 시스템이 낫다"고 말할 수 있다.** Arm C(맨몸 프론티어)만 이긴 결과는 발표에서 근거로 쓰지 않는다.
- 보고 필수 5수치: `Δ_bare`, `Δ_glue`, `글루 주효과(모델군별)`, `언어 주효과`, `A−B 차이 + CI`.
- C군: 국내 vs 프론티어 직접 비교(McNemar + Holm), 하위축(C1–C6)별 분해 × 2조건.
- 다중비교 Holm 보정, discordant<25 자동 증거부족(arena 관행 계승).

### Phase E — 조합 재평가 (H2)
C2·V3 아이디어를 **C군(한국어 고유) 기준으로** 재평가. 한국어 축에서 더 나은 배정이 있으면 그것이 본 가설에 맞는 개선안. 단 배정 변경의 이득이 글루 이득보다 작으면 그 사실을 명시한다.

### Phase F — 보고
"한국어 우위 있음/없음"을 Δ와 CI로 명시하되 **반드시 글루 수준을 함께 표기**한다("bare에서는 우위 있음, glue에서는 소멸" 같은 형태). 없으면 없다고 그대로 쓴다 — 기존 과업 벤치 결과(동급/비동급)와 함께 병기해 어느 축의 주장인지 혼동되지 않게 서술.

## 5. 예상 시나리오와 해석 (미리 고정)

| Δ_bare | Δ_glue | 해석 |
|---|---|---|
| > 0 | > 0 | **H-KO 완전 채택** — 한국어 우위가 실재하고 제품에서도 살아남는다. 가장 강한 서사. |
| > 0 | ≈ 0 | **부분 채택 (가장 유력 시나리오)** — 한국어 우위는 실재하나 **글루가 그것을 덮어버린다**. 정직한 결론: "언어 선택보다 글루 설계가 지배적이다" (R+ ablation과 정합). |
| ≈ 0 | > 0 | 가설 기각 — 언어가 아니라 **글루-모델 궁합** 효과. 국내 모델이 orthus 스타일 시스템 프롬프트에 잘 맞는다는 별개 발견. |
| ≈ 0 | ≈ 0 | 한국어 우위 없음. 조립 이득은 순수 엔지니어링. |
| < 0 | 임의 | 국내 모델이 오히려 영어에서 상대적으로 나음 — 가설 명확히 기각. |

부가: A군 열세 + B/C군 대등이면 "기본 추론은 뒤지나 한국어 과업에서 따라잡는다"는 부분 지지로 보고한다.

### 5.1 제품 주장(Arm A vs B) 판정

과거 실측 기준선: 14개 시스템 × 2,899 = 40,586 호출을 c=6으로 전부 돌린 wall-clock 합계 446.7분(7.4h), 최장 단일 레인 deepseek 106분. **z.ai를 제외하면 429가 한 건도 관측되지 않았다**(Bedrock throttling 미관측이 3개 문서에 기록) — 동시성 상향 여유가 코드·실측 양쪽에서 확인됨.

### 6.4 배치 API — 도입하지 않음

저장소 전체에 `/v1/batches`·`message_batches`·`CreateModelInvocationJob` **0건**. 도입 검토 결과 **기각**:
- OpenAI Batch: 신규 200-300줄 필요(submit/poll/merge로 전면 개편), **비용 50% 절감이지만 24h 턴어라운드 = 속도 100배 손해**.
- Bedrock batch: S3 in/out + boto3/SigV4 필요, 현 어댑터는 raw httpx + Bearer라 인증 스택부터 신규.
- Anthropic Batches: 해당 없음(Claude는 전부 Bedrock Converse 경유).

**배치는 비용 레버지 속도 레버가 아니다.** 본 실험 규모에서 지렛대는 `--concurrency` 상향 + 벤더 레인 병렬이다.

### 6.5 샤딩 규칙

- 같은 벤더 내 추가 샤딩이 필요하면 **`--out-dir` 분리 + `--tasks` 분할** 후 병합. 여러 프로세스가 같은 파일에 append하면 `write_lock`이 프로세스 로컬이라 깨진다(`run_shard.py`의 RAW_DIR 리다이렉트 선례).
- A.X 레인을 **가장 먼저 발사**한다(하드 스로틀로 단축 불가한 임계 경로).
- ⚠️ **A.X는 절대 샤딩 금지 — 반드시 단일 프로세스.** `_throttle()`의 lock이 **프로세스 로컬**이라 2프로세스로 나누면 2.5×2 = 5 req/s로 팀 캡(3 req/s)을 위반한다. 단일 프로세스에서는 스레드 수와 무관하게 0.4s 간격이 직렬 강제되므로 `--concurrency 9`도 안전하다.

### 6.6 하네스 구현 결과 (완료)

- `arena_run.py` 패치 2건 반영: `load_done_pairs()`가 `(id, condition)`별 **마지막 행 기준**으로 error 없는 행만 done 처리(실패 문항 재시도 복구), `--cost-cap-usd` 기본 8.0 → **100.0**.
- **신규 `koparity_run.py`** — arena 확장이 아닌 **형제 러너**. arena는 `task` 축(집중6=bare+glue / 회귀7=bare)에 로직이 묶여 있는데 KO-PARITY는 `group/lang/instr_lang` 축이라 한 러너에 넣으면 이중 분기로 arena 회귀 위험이 생긴다. **실행 계층(`VendorClient`/`build_client`/`PRICING`/`estimate_cost_usd`)은 import 재사용**하고 데이터 계층만 신규.
- 체크포인트 키를 `(id, condition, **instr_lang**)`으로 확장 — §3.4 교차 셀(ko문항+en지시문)이 같은 `(id, condition)`으로 돌면 서로를 done으로 덮어쓴다. 기본 `--instr-lang match`에서는 arena와 동작 동일.
- 신규 `koparity_prompts.py` — bare/glue × 지시문 ko/en. 출력은 `{"answer": …}` 단일 JSON, 타입은 `gold_type`(choice_index/boolean/short_string)에 맞춤.
- dry-run 검증 통과: 로드·필터·카나리·조건확장·재개·실패행 재시도·cost-cap 중단·교차셀 키 분리 + arena 무회귀.
- 실행·모니터링·결과 요약은 전부 서브에이전트에 위임(대량 출력 컨텍스트 격리).

## 7. 리스크 체크리스트

- [ ] **비대칭 글루 금지** — 프론티어에만 글루를 안 주면 심사에서 "베이스라인 핸디캡"으로 즉시 기각된다. Arm B(프론티어+동일 글루)는 생략 불가이며, Arm C만 이긴 결과를 승리로 인용하지 않는다.
- [ ] **글루 요인을 빼면 실험 자체가 무효** — R+ ablation이 보여주듯 성능 대부분이 글루에서 나오므로, 글루 고정 상태로 언어만 비교하면 "한국어라서"와 "글루라서"가 영원히 분리되지 않는다.
- [ ] glue 정의를 arena와 동일하게 **system 프롬프트 한 겹**으로 유지 — few-shot·재시도·파서 보정을 섞으면 변수가 뭉개진다.
- [ ] **프롬프트 튜닝안(6건)은 실험 중 반영 금지** — 반영하려면 실험 전에 끝내고 동결. 도중 변경 시 전 측정 무효.
- [ ] arena의 "glue 주판정" 규칙은 prereg에 없던 **사후 결정**이었음(`arena_judge.py:127` docstring 자백) — 본 실험은 양 조건을 대등하게 사전등록해 같은 지적을 받지 않도록 한다.
- [ ] `adapters/cli.py:242` 등 3곳은 system+user를 병합해 **bare로 붕괴** — 측정 시 어댑터 경로가 조건을 오염시키지 않는지 확인.
- [ ] ⚠️ **Bedrock 레인의 bare는 완전한 system-free가 아니다** — `json_only`일 때 "Return only a valid JSON object" 한 줄이 system 블록으로 들어간다(`claude-*`, `glm-5-bedrock`). 전 레인·전 언어에 대칭이라 Δ 상호작용에는 영향 없으나, **bare/glue 대비를 보고할 때 반드시 이 바닥값을 명시**한다.
- [ ] **A.X 단일 프로세스 강제** — 샤딩 시 프로세스 로컬 lock이 무력화되어 팀 rate cap 위반.
- [ ] ⚠️ **DeepSeek 슬러그 확인** — arena 계열 raw에는 `deepseek-v4-pro`만 있고 plain V3.2가 없다. owner 지정은 **V3.2**이므로 `deepseek` 슬러그로 신규 레인을 돌리되, **카나리에서 실제 호출 성공을 먼저 확인**한다. 두 버전을 혼동해 보고하지 않는다.
- [ ] **`Δ_tuned` 슬롯은 데이터에 `condition="tuned"`가 실제 존재할 때만 산출** — 없으면 "미측정"으로 남으며 조용히 채워지지 않는다(분석기가 fail-closed로 구현됨).
- [ ] **번역 품질이 곧 실험 타당성** — en판이 어색하면 프론티어가 부당하게 손해. 역번역 검사 + 인간 검수 필수.
- [ ] ko/en 난이도 비대칭(예: 한국 문화 고유명사가 en판에 그대로 남음) — A·B군에서 문화 특수 고유명사 제거.
- [ ] 지시문 언어 교란(§3) — 교차 셀로 통제하지 않으면 "한국어 효과"가 사실은 "지시문 언어 효과"일 수 있다.
- [ ] 생성기 격리: 평가 대상 9모델은 문항 생성에 절대 사용 금지(자기채점 편향).
- [ ] **prereg 선작성** — 판정식을 데이터 보고 고르지 않는다(arena V3 실패 사례).
- [ ] C군 정답의 규범성 논란(존댓말·띄어쓰기는 규범 vs 실사용 괴리) — 국립국어원 기준 등 근거 명시, 논란 문항은 제외.
- [ ] 모델별 토크나이저 차이로 한국어 길이 비용이 다름 — 지연·비용 지표는 참고만, 정확도 판정에 섞지 않는다.
- [ ] A.X 3 req/s 캡, EXAONE timeout 120s, Bedrock `us.` prefix 유지.
- [ ] raw는 gitignore — 백업 필수. 산출 통계만 커밋.
